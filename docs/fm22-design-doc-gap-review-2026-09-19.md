## 三个真缺口

### ① 无球跑动的统一价值场缺失（**唯一有实质价值的缺口**）

文档 §6 描述的是：**同一个前锋**根据环境在 6 种跑位间选择
（拉开中卫 / 身后前插 / 回撤接球 / 拉到边路 / 压迫中卫 / 封锁 DM 传球线路）。

VCFM 里这些行为**都有**，但散在多个互不知情的机制中：

| 机制 | 位置 |
|---|---|
| 队形锚点 | `engine.js` 的 `_applyExplicitShapeAnchor()` |
| 集体防守补位 | `js/collective-defense.js` |
| 压迫 | `engine.js` 的 pressing 分档 |
| 无球目标 | `js/off-ball-movement.js` |

**每个机制各自都对，但没有一处做「哪个更有价值」的横向比较。**

🔑 这正是用户反复报的那类现象的**结构性解释**（球员卡在场边、跑位看起来不合理）：
**单个机制各自正确，合起来缺一个仲裁层。**

**这类缺陷的特征**：无法通过「读某个机制的源码」发现 —— 每个机制的源码都是对的。
只能通过「量出它们同时给出冲突目标」的频率来发现。

⇒ 切入点必须是**只读探针**：先量出「6 种机制在什么情况下给出冲突目标、
频率多高、冲突时的实际落点是什么」，再决定要不要合流。
**不先量就合流 = 又一次「先改后标定」，本项目已反复吃过这个亏。**

### ② 更新频率分档（性能项，**建议先不动**）

文档 §12 建议：近球 100~150ms / 相关 200~300ms / 远球 500~1000ms。
VCFM 现在 22 人**每步全算**。

- 这是**纯性能优化，不影响正确性**；
- 且它**会改变随机流消费顺序** ⇒ **必须全量重标定**（24~96 场的那套全部作废）；
- ⇒ 只有当性能真的成为瓶颈（如移动端卡顿实测）才值得动。

### ③ Utility 打分制（**建议明确拒绝**）

文档 §4/§15 建议「生成候选动作 → 逐个算 Utility → 选最高分」。

VCFM 现在的「第一层意图门槛 + 第二层概率链」是**经过实测加固的等效解**
（`beat` 原语就是照这个模式做的：`intentP` 门槛 → `p` 结算概率 → `clamp`）。

改成候选+打分会对**所有**行为重新洗牌，代价是全部标定作废，
而**收益是零**（现有解已达到文档想要的效果）。

⇒ 文档这一节是写给新项目的，**不是给 VCFM 的**。

## 建议

如果要从这份文档里取一件事做，就取 **①**：

**先写一个只读探针，量化无球跑动目标冲突的实际频率** ——
不改引擎、不消费随机数，符合「测量优先」纪律；
量出频率后再决定是否引入仲裁层。
