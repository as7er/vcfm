## 3. A 线：判决与依据（本轮核心）

### 3.1 探针

`scripts/_segment-boundary-displacement.mjs`（**新增，未提交**）
命令：`node scripts/_segment-boundary-displacement.mjs 75 live`

做法：**绕开诊断器**，包住 `matchView.applySimSnapshot`，
在每次调用前后各拍一次全部 26 个实体的坐标（22 球员 + 球 + 3 官员），
按 `x×0.68 / y×1.05` 换算成米（与 `matchview.js` 的 `OFFICIAL_MX/MY` 同源）。

为什么必须绕开诊断器（上一份交接的结论，本轮确认仍成立）：

- `_display-layer-motion-probe.mjs` 报的 `totalIncidents = 0` 不可用 ——
  `isMotionBoundary`（`dt>0.55` / `discontinuity` / `restartType`）**整段豁免**，
  而用户看到的整队瞬移**常就发生在那里**；
- `match-motion-integrity-audit.mjs` 喂 `record(snapshot, snapshot)`，
  引擎帧与显示帧是同一对象 ⇒ `display-divergence` 结构上不可达。

### 3.3 判决

**签名 = 场景切换（剪辑），不是物理 bug。**
后三次**全队一起跳**（中位 14.3 / 24.0 / 35.0 m = 普通帧中位的 180~440 倍；
第 3 次 **26/26 全体 >6m**）。「所有实体一起跳」= 换了场景，不是某实体运动学坏了。
四次 `sceneCut` 全 `true`，与设计一致：切段时**刻意关掉 relocate 缓动**
（`js/matchview.js:480` `if (sceneCut) entity._relocAt = 0`），改用一次 260ms 淡场讲成换镜头。

**但遮罩不够 —— `fadeOpacity` 四次恒为 `0.72`。**
跳变那一帧遮罩最浓时只有 72%，**观众仍能看见 28% 的整体位移**，这正是用户报的瞬移。
⇒ **不要判成「已修好」。**「换场景」的事实确认了，「遮住」没做到位。

## 4. A 线：待修的两处缺陷 + 一个真 bug（**都没改**）

### 缺陷 1：淡场峰值只到 72%（主因）

`css/style.css:3770`：

```css
@keyframes mp-seg-cut-fade {
  0% { opacity: 0.72; }     /* ← 峰值 72%，跳变帧从这里开始衰减 */
  100% { opacity: 0; }
}
```

跳变发生在 `0%` 那一帧，此时只有 72% 遮罩；之后**一路变淡**，后半程更薄。
改法（**未实施，待用户拍板**）：把 `0%` 提到接近 1.0（如 `1`），
并考虑加一段「先全遮住、再淡出」的关键帧（如 `0%:1 → 35%:1 → 100%:0`），
否则一跳完立刻开始变透，观感上仍会漏出后半段。
⚠ 改 CSS 动画曲线属于**观感变更**，建议在真机/录屏上确认节奏，不要只看数字。

### 缺陷 2：`prefers-reduced-motion` 下遮罩被完全去掉

`css/style.css:3774`：

```css
@media (prefers-reduced-motion: reduce) {
  .mp-field.mp-seg-cut::before { animation: none; opacity: 0; }
}
```

`animation: none` 让 `::before` 停在**初始态的 `opacity`**，
而规则显式写成 `opacity: 0` ⇒ **完全透明，等于没有遮罩**。
于是「一跳 76 m」在开了「减少动态效果」的设备上**原样裸露**。
这恰好与该分支的本意相反：用户要的是**少动**，不是**少遮**。
改法（**未实施**）：改成一个**静态**的全遮罩（`animation:none; opacity:1`），
配合 `_playSegmentCut` 的定时器（`SEGMENT_CUT_MS + 40 = 300ms`）到时移除 class
—— 不引入动画，但仍遮住跳变。这比现在的行为更符合该偏好的语义。

### 真 bug 3：每场开球多闪一次淡场

`js/matchview.js:277`（构造函数）与 `:1709`（重建）把 `_segLastEndSimT` 初值设为 **`null`**；
`:1236` 的守卫是：

```js
const prevEnd = Number(this._segLastEndSimT);   // Number(null) === 0  ← 陷阱
if (!Number.isFinite(prevEnd) || !Number.isFinite(t0)) return { mode: "first" };
```

`Number(null) === 0` 且 `Number.isFinite(0) === true` ⇒ **守卫拦不住初值**，
`gapSec = 0.1 − 0 = 0.1 ≠ 0` ⇒ 判成 `cut` ⇒ **开球凭空多闪一次淡场**。
（`undefined` / `NaN` 才会被拦住 —— 已实测确认。）

证据：本探针在点 `#btn-sim-live` **之前**就装了钩子，仍抓到第 1 条 `t0=0.1` 的 `cut`。
⇒ **推翻**了 `docs/measurements/segment-cut-verify-2026-09-21.txt` 里
「`first=0` 是钩子打晚了」的解释（那条只测到「探针启动晚」，没测到根因）。

改法（**未实施**）：把守卫改成对「没有上一段」显式判定，例如
`if (this._segLastEndSimT == null || !Number.isFinite(prevEnd) || !Number.isFinite(t0))`
（`== null` 同时覆盖 `null` 与 `undefined`），
或把初值从 `null` 改成 `NaN`（`Number(NaN)` 仍是 `NaN`，守卫自然生效）。
⚠ 后者改动更小但语义隐晦；前者更明确。**二选一，待拍板。**

## 5. B 线与 C 线现状（本轮未动）

### B. 体能经济量级 —— 需用户先定方向

方案 D 已落地（`docs/measurements/halftime-fitness-per-player-2026-09-21.txt` §6）：
按**逐人跑动距离**占比分摊球队总耗能，**总量守恒、零重标定**，
面板从「全员 87」变成 **86~89**（均值仍是 87）。

**极差只有 3 点**的原因不是分摊公式错，而是**总量口径太小**：
`perPlayer = max(1, round(fitW + extra))` 默认档只有 **1 点**，×3 次结算 = 每人每半场扣 3 点。

两个方向（**都会动换人阈值 / 伤病率 / 评分，需单独标定**）：

1. 调大 `perPlayer`（提高总量）；
2. 延长结算间隔（现每 15 分钟一次）。

护栏已标定：主指标「队内 max/min 比值」实测 **3.889**，2×SD = 0.574，
建议带 **[3.32, 4.46]**；判决力好（SD 0.287 ⇒ 辨出 Δ=0.3 只需 4 场）。
⚠ 带宽**必须用以比赛为批单位的 SD（0.287）**，不能用球队级 SD（0.723）——
主客两队共享比赛条件，那是伪重复，会把带宽算宽 2.5 倍。

**不要**再试「读引擎 `agent.fitness` 回写」—— 已实测 spread 仅 0.39，
四舍五入仍是 87（`engine.js:5851` 的 `stamina` 项被压到总倍率仅 1.064×）。

### C. 同步路径补 `weather.pace` extra —— 先不要改

默认档 `perPlayer = max(1, round(fitW + extra))` **跨不过 `round(1.5)`**
（雨/热下 `weatherTeamImpact.fatigue` 把 `fitW` 压得更低，反而更够不着），
所以同步路径「缺 extra」在默认档**观测不到差异**，补上也不会让面板从 −3 变 −6。
要验证 extra 本身，必须**显式构造高压迫 / 高防线 / attack 档**让 `fitW` 靠近 1.5。
