# 无球目标「锚点翻转」与画面瞬移 —— 根因诊断（2026-09-16）

> 用户报告（本轮）：
> **「比赛中，画面的过渡还是存在瞬移的现象，是不是没有把淡化过渡做普及？」**

> 上一轮（同一线程）我原本在查「无球跑位四层管线」，连续 4 个假设被实测推翻，
> 最后转向**上游目标生成**。本轮把那条线走完了，得到的结论**正好解释了用户的瞬移报告**：
> 两条线索**同源**。

---

## 0. 一句话结论

**`_chooseAttackOffBallTarget` 在两条分支之间来回翻转，而这两条分支的纵向锚点完全不同
（一条锚在「球位」、一条锚在「固定阵型位」），相距可达 70 m。**

- 翻转由 `this.random() < p` 决定，每 **0.42~1.32 s** 重掷一次骰子（无球跑位节流周期）。
- 实测：**锚点翻转使「目标大跳（≥15 m）」的概率提升 11.2 倍**。
- 球员真的照新目标跑：**726 例「球没动却跳 ≥15 m」里，637 例（87.7%）球员真实位移 ≥8 m，max 71.65 m**。

而画面**没有把这 71 m 的跳变讲成过渡** —— 因为渲染层的缓动
`relocate()` 只在**死球/庆祝/点球**三个窗口武装（`restartFrame`），
活球跑位的大跳**一律硬置**：实测 **591/726（81.4%）** 的大跳落在无豁免帧。

⇒ 用户看到的瞬移，是**引擎层锚点抖动**经**渲染层无缓动**放大后的结果。**两个缺陷叠加**。

---

## 1. 定位路径（为什么前几轮没找到）

前几轮查瞬移时，先量了「段内平滑度」——**结论是教科书级正确**：

| 实体 | stepMedianM | stepMaxM |
|---|---|---|
| ball | 0.046 | 0.585 |
| player | 0.004–0.080 | 0.095–0.241 |
| referee | 0.022 | 0.068 |

段内之所以平滑，是因为 `applySimSnapshotLerped` 的插值永远发生在**相邻帧之间**
（`fr[sp.i]` 与 `fr[sp.i+1]`，间隔恒为 0.1 s）。**相邻帧位移天然 ≤ 速度 × 0.1 s。**

所以瞬移**不可能**来自插值。它只能来自：
1. **段边界**（前两轮已修：`SEGMENT_CUT_MS` 淡场 + 倒带判定）—— 见
   `docs/matchview-teleport-investigation-2026-09-16.md`
2. **相邻帧之间的引擎侧真实大位移**（本轮发现的缺口）

第 2 类被长期忽略，因为「相邻帧」看上去天然安全 —— 但它**只保证「不是插值造成的」**，
不保证「引擎没在一个 tick 里把目标扔出 70 m」。

## 2. 引擎层：锚点翻转（根因一）

### 2.1 两条分支的锚点不同

`engine.js:4123-4160`（前锋分支，`MID`、边锋、边卫分支同构）：

```js
if (a.role === "ATT") {
  const drop = prog < 0.68 && (nearest || core || this.random() < 0.22 + ...);
  if (drop) {
    // ⚠ 纵向锚 = 球位
    a.ty = clamp(b.y + dir * dropDepth, 8, 92);      // dropDepth = 10~22
    a.fsm = "support";
    return;
  }
  // 纵向锚 = 固定阵型位
  const fwdTargetY = clamp(a.baseY + dir * ((getsForward ? 18 : 16) + roleDepth * 5), 3, 97);
  a.fsm = "home";
  return;
}
```

**两个锚的距离可以极大。** 取实测最坏一例：

```
球在自己门线上（home 队 b.y = 96，prog = 0.04）
  走 drop 分支 → a.ty = 96 - 15.4 = 80.6      （回撤到球边）
  走 else 分支 → a.ty = 22 - 16   =  6.0      （前插到锋线）
```

**同一球员、同一 tick、同一个球位，两个候选目标相距 74.6 m。走哪条由随机数决定。**

这不是「回撤 vs 前插」的战术选择问题 —— 战术选择**可以**存在，
但它**不该由每秒重掷的骰子决定**，也不该在球位不变时来回横跳。

### 2.2 直接量测：锚点翻转 vs 上移幅度

只读探针 `scripts/_offball-layered-attribution-probe.mjs`（6 场 / 152,182 次重算）。
用产出点与「球位」/「阵型位」的接近程度反推走了哪条分支（不消费随机数）：

| 条件 | n | 上移中位 | ≥15 m 大跳率 |
|---|---:|---:|---:|
| **锚点翻转**（ball ↔ base） | 10,985 | **7.25 m** | **26.5 %** |
| 锚点不变 | 141,197 | 1.30 m | 2.4 % |

**⇒ 锚点翻转使大跳概率提升 11.2 倍。**

翻转样本只占提交量的 **7.2 %**，却贡献了 **2,906 / 6,229 = 46.7 %** 的 ≥15 m 大跳。

### 2.3 球员真的照新目标跑

「球没动（< 2 m）却跳 ≥ 15 m」的样本里，反查球员在**下一次提交前**的真实位移：

```
实际跑出 >=8m: 637      几乎没动(<0.5m): 1      max 71.65m
```

**87.7 % 真的跑出 ≥8 m。** 这不是「目标算了但没执行」，而是**真真切切的整场折返跑**。

三种「这不是 bug」的辩护逐一量测后全部不成立：

| 辩护 | 成立比例 |
|---|---:|
| (a) 球权 `ownerId` 变了 | 20.7 % |
| (b) 阶段 `phase` 变了 | 4.4 % |
| (c) 旧点年龄 < 0.5 s（刚定完就翻脸） | 5.0 % |
| **三者全不成立** | **75.5 %** |

### 2.4 节流周期让它每秒重掷

`engine.js:2100-2105`：

```js
a.attackThinkUntil = this.t
  + clamp(0.62 - (tempo - 3) * 0.055, 0.42, 0.82)
  + this.random() * 0.5;
```

周期 **0.42 ~ 1.32 s**（探针读到的「旧点年龄中位 1.00 s」正是它）。
每次到期都重跑 `this.random() < p` ⇒ **每秒有 22 %~72 % 的概率翻转分支**。

### 2.5 为什么租约拦不住

上一轮我怀疑 `holdPrevious` 租约是缺陷。**实测推翻了**：

- `holdPrevious` 拦住的大位移样本中，球员 **98.4 % 正在接近旧目标**（中位 4.72 m/s）
- 也就是说租约**拦的是对的**（旧目标是对的），但它**只拦下 26.7 %**（265/991）
- 剩下 726 例没拦住 —— 因为 `holdPrevious` 的四个条件
  （`sameContext`/`targetChanged`/`reversal`/`oldTargetRemaining`）**全部只引用球员自身，没有一条引用球**，
  而锚点翻转时「球没动」，球员自身状态看没有任何异常

⇒ **租约是拦截者，不是缺陷。真正的错误源在上游目标生成。**

## 3. 渲染层：缓动只豁免死球窗口（根因二）

### 3.1 缓动武装条件

`matchview.js:457-474`：

```js
const relocate = (entity, tx, ty, jumpLimit, metric = false, followOwner = false) => {
  if (sceneCut) entity._relocAt = 0;
  ...
  if (adjacent && restartFrame && !entity._relocAt &&
      (distance > jumpLimit + 1e-8 || followOwner)) {
    // 武装缓动（0.7 s ease-out）
  }
  if (!entity._relocAt) return null;   // ← 不武装 ⇒ 调用方 pl.x = tx 硬置
  ...
};
```

`restartFrame` 的来源（`engine.js:472-486`）：

```js
export function motionContextOf(eng) {
  const deadBall = !!(eng.deadBallUntil && eng.t <= eng.deadBallUntil + 1e-6);
  const celebrating = !!(eng.celebrateUntil && eng.t <= eng.celebrateUntil + 1e-6);
  return { discontinuity: !!(deadBall || celebrating || eng.pendingPenalty), ... };
}
```

**`discontinuity` 只在死球 / 庆祝 / 点球三个窗口为真。** 活球跑位期间恒为 false。

### 3.2 那批大跳几乎全在无豁免帧

```
落在死球/庆祝/点球窗口内（缓动可豁免）: 34   (5.0%)
带 restartType 标记:                    58   (8.5%)
⇒ 既不豁免、又无 restartType 的:        591   (81.4%)   ← 硬置
```

**81.4 % 的活球大跳没有任何缓动。**

### 3.3 为什么是「共用开关」而不是「忘了普及」

`restartFrame` 这个条件**同时**承担两个语义：

1. **缓动武装**（`relocate`）—— 「这里允许我缓动」
2. **告警豁免**（`match-motion-integrity.js:167-173` 的 `isMotionBoundary`）—— 「这里不要报瞬移」

`engine.js:465-471` 的注释写得很清楚：这个标记是为了让表现层
**「豁免重启单 tick 搬位的瞬移告警」**。于是它被**借用**成了缓动的准入条件。

⇒ 想给活球大跳加缓动，**不能只放宽 `restartFrame`** ——
那会同时让 `isMotionBoundary` 失守，`match-motion-integrity` 会把每次活球跑位拐点都当瞬移上报。
**必须把「允许缓动」与「豁免告警」两个语义解耦。**

用户猜的「淡化过渡没做普及」，方向是对的；**准确说法是「缓动与告警豁免共用一个只剩死球语义的开关」**。

## 4. 两条链的耦合

```
engine._chooseAttackOffBallTarget
  ├─ drop 分支：ty = 球位 + dir*深度
  └─ else 分支：ty = 阵型位 + dir*...
        ↑
        └─ 每 0.42~1.32s 用 this.random() 重掷
              ↓
        目标点跳 15~71 m（7.2% 的提交，46.7% 的大跳）
              ↓
        holdPrevious 租约只拦 26.7%
              ↓
        球员真的跑 → 目标位从 A 换到 B
              ↓
        matchview.relocate
          restartFrame = false（活球）  ← 81.4% 的情况
              ↓
        pl.x = tx（硬置，无缓动、无淡场）
              ↓
        ★ 用户看到的「瞬移」
```

## 5. 修复方向（**未实施**，需用户确认）

### 方向 A：引擎层 —— 消掉锚点抖动（治本）

三条互斥的备选，**必须只选一条**（都会改随机流，需全量 verify + 进球率复核）：

1. ~~**`drop` 判据加迟滞（hysteresis）**~~ —— **已用探针证伪，放弃。**
   迟滞只在 `prog` 落回 `0.68` 附近时生效，而实测 **77.5 % 的翻转发生在 prog 深处**
   （0.00~0.60 占 65.7 %）。带宽 0.15（极大）也只消除 **18.8 %** 的翻转、**9.5 %** 的大跳：

   | 迟滞带宽 | 翻转数 | 被消除 | 消除率 | 大跳数 | 其中被消除 |
   |---:|---:|---:|---:|---:|---:|
   | 0.00（现状） | 11,356 | 0 | 0.0 % | 2,946 | 0 |
   | 0.03 | 11,356 | 454 | 4.0 % | 2,946 | 116 |
   | 0.06 | 11,356 | 767 | 6.8 % | 2,946 | 170 |
   | 0.10 | 11,356 | 1,125 | 9.9 % | 2,946 | 212 |
   | 0.15 | 11,356 | 2,132 | 18.8 % | 2,946 | 279 |

   **⇒ 病根不在 `prog` 门，而在门内侧的 `nearest` / `this.random() < p` / `dropDepth` 随机项。**

2. **把 `drop` 的纵向锚从「球位」改成「球位与阵型位的加权」**，例如
   `ty = lerp(baseY, b.y + dir*dropDepth, 0.65)` —— 消掉 74 m 的间距，
   但**降低回撤幅度**，需要复核「前锋回撤要球」的行为强度。← **推荐**（直接对准根因）

3. **把 `drop` 翻转移交给确定性状态机**：把 `nearest`（依赖其他球员实时位置、会抖）
   与 `random() < p`（每秒重掷）换成**稳定的角色分配 + 迟滞**。
   例如「按 `baseX` 排序取最近的两名前锋轮换回撤名额」，并把 `dropDepth` 的
   `random()` 换成基于球距的确定性函数。← **根治**，但改动最大

### 方向 A 的补充证据：翻转位置分布

| prog 档 | 翻转数 | 占比 | 其中大跳 | 大跳率 |
|---|---:|---:|---:|---:|
| 0.00~0.20 | 2,016 | 14.2 % | 442 | 21.9 % |
| 0.20~0.40 | 3,191 | 22.5 % | 540 | 16.9 % |
| 0.40~0.60 | 4,122 | 29.0 % | 777 | 18.9 % |
| **0.60~0.68（门内侧）** | 1,558 | 11.0 % | 578 | **37.1 %** ← 最高 |
| 0.68~0.80（门外侧） | 1,638 | 11.5 % | 185 | 11.3 % |
| 0.80~1.00 | 1,679 | 11.8 % | 201 | 12.0 % |

**`0.60~0.68` 的大跳率是 `0.68~0.80` 的 3.3 倍** —— 这正是「门内 = `drop` 分支（锚在球位）、
门外 = `else` 分支（锚在阵型位）」两个锚点分居球两侧的指纹。

### 方向 B：渲染层 —— 给活球大跳加过渡（治标，与 A 独立）

1. **解耦两个语义**：给 `relocate` 传一个**独立的** `allowGlide` 参数
   （例如「位移 > 该帧物理上限」即为真），不再借用 `restartFrame`。
2. `isMotionBoundary` 保持原样 ⇒ 告警口径不变。
3. ⚠ **风险**：活球期间球员本就有 3~6 m/s 的真实速度，若把 `jumpLimit` 放宽到
   「物理上限」，正常跑动不会触发；但**锚点翻转的 71 m 跳变会变成 0.7 s 的 101 m/s 扫掠**
   —— 比硬切更难看（这正是 `SEGMENT_CUT_MS` 注释里否决 ease 的同一理由）。
   ⇒ **方向 B 只对「中等幅度」跳变（如 8~25 m）有意义**，对 71 m 级仍应显式剪辑。

**建议的组合**：先做 **A1（迟滞）**把大跳的**发生频率**压下来，
再用 **B** 覆盖残余的中等幅度跳变。**不建议只做 B** —— 那只是把抖动画得慢一点。

### 方向 C：先量「修好 A 之后还剩多少」

在动手前，用探针**模拟 A1 的迟滞**（不改引擎，只在探针里按迟滞口径重算「若加了迟滞，
这次会不会翻转」），得到「预期消除的大跳比例」。**这一步没有成本，应当先做。**

## 6. 量测边界（这套读数的适用范围）

- 样本：6 场、种子 `381000~381005`、**半场时长**（`SIM_SECONDS/2`），152,182 次重算。
- 打法：双方 `pressing/tempo/defensiveLine = 3`、`style = balanced`、`4-3-3`、能力 15。
  **未覆盖**：非常规打法（`possession` 风格会额外触发 `supportPull` 拉拽）、
  替补登场后的阵型变化、非 4-3-3 阵型（`5-3-2` 的五后卫会走 `_isFullback` 分支）。
- 「锚点」是**反推**的（比较产出点更靠近球位还是阵型位），不是引擎自报的分支名。
  两个锚偶尔等距（回归到 `|产出-球| ≈ |产出-base|`）时会误判，量级估计
  **< 2 %**（与 §2.2 的「锚点不变」桶内 2.4 % 的残余大跳同量级）。
- 渲染层的 591/726 是用**引擎侧窗口标记**（`deadBallUntil`/`celebrateUntil`/`pendingPenalty`）
  判定的，与 `matchview` 实收的 `compactSimFrame.motionContext` 同源但**未在浏览器里端到端复测**。
  若要实施方向 B，**必须先补一个浏览器侧探针**核实这 81.4 % 的比例。
