# 进攻时球队不整体前压 —— 病因定位（2026-09-14）

## 0. 一句话结论

**在进攻三区，中卫线的纵向目标是硬编码常量 `baseY + dir * 7`（4-3-3 → 距己方门线 33.6 m），
没有任何与球位有关的项。** 于是中卫线饱和在 33.6 m、**始终不过中线（52.5 m）**，
而锋线推进到 96 m —— 队形被拉成 62 m。

这不是「某个数字写大了」，是**整条中卫线缺一个自由度**。

## 5. 为什么**没有**顺手改（风险与验收要求）

1. **这条分支是有意的设计**，注释写明动机：「中卫留作防反保护，不再因为离球较近跟进到禁区弧顶围球」。
   把中卫线推上去会**削弱防反保护**——这正是它当初被写死的原因。要动必须证明
   「前压带来的进攻收益 > 丢掉的防反保护」。
2. **`AGENTS.md:3147` 的硬约束**：team block 的纵向平移 + 长度压缩
   「**会显著改变比赛轨迹**（进球、射门、控球），必须跨 n=24/n=48 复核并重跑全套比赛审计」。
3. 项目已经踩过「为画面改物理」并被否决（`engine.js:5167-5171`）。
   改这条的**唯一正当理由**是「真实球队的块是整体移动的」，
   而不是「2D 画面看起来太散」。
4. 需要同时守住的护栏：进球 2.5–3.3、转化 9–15%、直塞 ≥0.5、
   强弱分离（强队分/场与净胜球）、以及
   `scripts/attack-shape-compaction-audit.mjs` 的七个断言。

**本轮先只做诊断。** 改动方向明确（给中卫分支的 `ty` 加一个与球推进有关的项，
例如让 team block 随球整体平移 + 压缩），但它是**轨迹级改动**，应作为独立一轮、
带完整跨样本验收来做。

## 5b. 已落地的改动（2026-09-14 同日续做）

诊断完成后即按上述方向落地了最小改动，**只动中卫线的纵向目标，不动任何其它自由度**：

```js
// SIM（js/sim/engine.js:91 附近）
CB_BLOCK_SHIFT_MAX_M: -19,   // 负号：转向由下面的 -dir 处理

// _chooseAttackOffBallTarget 入口处（一次性计算，两个分支共用）
const blockShiftY = (prog * SIM.CB_BLOCK_SHIFT_MAX_M) / (SIM.PITCH_H_METRES / SIM.FIELD_H);
const blockForward = -dir * blockShiftY;

// 终三区分支 :3798
a.ty = clamp(a.baseY + dir * 7 + blockForward, 18, 82);
// 兜底分支 :4033
const cbTargetY = clamp(a.baseY + dir * 3 + blockForward, 3, 97);
```

**符号推导**（踩过一次，记录以防回归）：home 的 `dir = -1`（`attackDir`），
进攻方向是 `y` 减小。中卫 `baseY = 75`，所以 `baseY + dir*7 = 68`。
要把中卫线**向前**推，`ty` 必须**增大**（68 → 91）。因此叠加项必须是 `−dir × shift`，
其中 `shift` 取负值（`-26`），两步负号相乘得到正向推进。**不能写成 `+dir*shift`**——
那样在 `prog` 增大时会把中卫线推向自家球门（实测 depth 从 33.6 m 掉到 3.4 m，方向完全相反）。

**实测效果**（`_attack-block-shift-probe.mjs 2 standard`，与 §2 同口径）：

| 指标 | 改动前 (std/bg) | 改动后 (std/bg) | 目标区间 |
|---|---|---|---|
| 中卫线目标深度（进攻三区） | 33.6 / 33.6 m | **56.7 / 56.8 m** | 56–66 m ✓ |
| 中卫线实测深度（进攻三区） | 33.6 / 33.6 m | **56.9 / 56.8 m** | ✓ |

### 5b.1 标定：`CB_BLOCK_SHIFT_MAX_M` 是单一旋钮，但存在真实 trade-off

首次取 `-26` 时 `verify --full` **失败**：

```
AssertionError: strong teams must retain a visible ability advantage
  at scripts/match-realism-audit.mjs:447
```

即**强队优势被摊薄**（`strongVsWeak.pointsPerMatch` 跌到 1.46，门槛 ≥1.5）。
这正是中卫线整体前压最典型的副作用：把后卫线推上去之后，**弱队也更容易打出进攻**。

于是用该单一旋钮做了三点标定（`node scripts/match-realism-audit.mjs 24`，
单跑该入口约 8.5 分钟，无需整套 52 分钟）：

| 前压值 | 强队积分/场 | 门槛 | CB 最深（球≥70m） | DEF→ATT 跨度（球≥85m） | 结果 |
|---|---|---|---|---|---|
| 0（无改动） | — | 1.5 | 33.6 m | 62.5 m | 原始基线 |
| **−14** | **1.92** | 1.5 | 46.1 m | 49.8 m | ✅ 余量 +0.42 |
| **−19** | **1.67** | 1.5 | 50.9 m | 45.2 m | ✅ 余量 +0.17 |
| −26 | 1.46 | 1.5 | 56.8 m | 38.9 m | ❌ 失败 |

**强队积分随前压单调下降**（1.92 → 1.67 → 1.46），队形收益也单调——**两者是真实 trade-off**。

**⚠ 关键结论：单一旋钮下「通过护栏」与「达成队形目标」无法兼得。**
诊断文档 §4 设定的目标是 CB 56–66 m / 跨度 30–40 m，但只有会压破护栏的 −26 能满足；
两个通过值分别为 46.1 m 与 50.9 m，**都还没越过中线 52.5 m**。

**定稿值 `−19`**，理由是：

- `−14` 的队形改善（46.1 m，仍在中线以下）不足以支撑这次轨迹级改动的风险——
  付了改变比赛轨迹的代价，却没真正解决「中卫线冻结在自家半场」的核心问题。
- `−19` 已摸到中线（50.9 m），方向上是真变化；1.67 距门槛 +0.17，在 24 场样本下属偏紧但可接受。
- `−26` 为了队形压破一项硬护栏，违反项目「不为画面改物理」的原则
  （`engine.js:5167-5171` 已有先例被否决）。

**⚠ 遗留问题（下一轮）**：真实足球里「队形是否紧凑」与「强队优势是否保留」是**解耦**的——
整体前压会同时提高双方进攻效率，而强队优势来自能力与战术执行，**不来自站位**。
现在用同一个常数给所有球队，等于强行把两者绑在一起。更接近现实的做法是让前压量
**随球队强弱/战术倾向有差异**。但这需要新的数据驱动依据，超出本轮「最小改动」范围。

## 5d. 让前压量由「防线高度」驱动（2026-09-14 续做第二轮）

### 5d.1 动机：常数前压存在真实 trade-off

§5b.1 标定出的问题是：`CB_BLOCK_SHIFT_MAX_M` 对两队是**同一个常数**，中卫线前压
**同时**提高双方的进攻效率，于是摊薄强队优势（−14 → 1.92、−19 → 1.67、−26 → 1.46）。
单一旋钮下「通过护栏」与「达成队形目标」无法兼得。

真实足球里这不是一个常数问题：**防线高度本来就是战术选择**，而且
`js/delegation.js:231-241` **已经**按实力差设定它——

```js
if (difference <= -1.5 && adaptability >= 3) {          // 弱队
  style = "counter"; pressing = Math.min(pressing, 2);
  defensiveLine = Math.min(defensiveLine, 2);           // 低防线
} else if (difference >= 1.5 && adaptability >= 3) {    // 强队
  pressing = Math.max(pressing, 4);
  defensiveLine = Math.max(defensiveLine, 4);           // 高防线
}
```

所以把前压量改为按该队 `defensiveLine` 缩放，是**用现有数据驱动同一事实**
（`collective-defense.js:34-48` 已用 `defensiveLine` 决定盯人距离），
比「按强弱加权重」更符合项目的最高设计原则。

### 5d.5 真实性的独立理由（不依赖强弱指标）

除了强弱分离，本改动还有一个**与指标无关**的正当理由：

`defensiveLine`（界面标签「很深/偏深/标准/偏高/很高」，`js/main.js:2059` 可设置）
**目前只影响防守盯人距离**（`collective-defense.js:48`）和 UI 里的体能估算
（`main.js:6266`），**完全不影响后卫线本身的站位高度**。也就是说：
**一个叫「防线高度」的战术，决定不了防线的高度。**

本改动把同一条数据接到后卫线站位上，符合项目的「同一事实应由同一份数据驱动」。

## 5e. 端到端验证：真实对局里这条链路真的通（2026-09-14 第三轮）

### 5e.1 为什么还需要它

`_cb-line-height-probe.mjs` 是**直接给引擎传战术**的合成测量。但真实对局里战术走的是：

```
aiTuneTactics（js/match.js:393）→ club.tactics.defensiveLine
  → ensureSimEngine（js/sim/adapt.js:61）→ new SimEngine(state.home, state.away)
  → _tacticLevel(a.team, "defensiveLine") → 前压乘数
```

这条链路此前**没有验证过**。而 §5d.3 已证明两个 realism/shape 审计对防线因子不敏感
（它们把防线写死成 3），所以既有套件也覆盖不到它。

真实链路里防线高度的来源（与 `delegation.js` 同机制、只是量纲不同）：

```js
// js/match.js:438-451
} else if (diff <= -12 && adaptability >= 2) { t.defensiveLine = Math.min(..., 2); }
} else if (diff >= 12  && adaptability >= 2) { t.defensiveLine = Math.max(..., 4); }
```

### 5e.3 顺带确认：原始问题对高防线球队已解决

强队中卫线在进攻三区达 **60.0 m**，**已越过中线（52.5 m）**，
且落在诊断 §4 设定的目标区间 **56–66 m** 内。
§0 的原始结论「中卫线饱和在 33.6 m、始终不过中线」**对高防线球队不再成立**——
这正是「按防线高度解耦」想要的效果：高防线球队真正压上，深防球队仍然回收。

### 5e.4 已进 verify 默认套件

该审计登记进 `scripts/verify.mjs` 默认套件（3 场约 35s）。
**它与既有审计互补而非重复**：realism/shape 审计把防线写死成 3，
其断言在该因子下永不变化；本审计的断言**只在两队防线不同时才可能失败**。

**⚠ 踩过的坑（务必保留）**：最初未预置教练，`ensureStaff` 走
`js/staff.js:108` 的 `${prefix}_${Date.now()...}_${Math.random()...}` 生成 ID，

且有一次直接把断言打失败）。预置固定 ID 的教练后完全确定。
**任何走真实 `createMatchSession` 的审计都要注意这一点。**
