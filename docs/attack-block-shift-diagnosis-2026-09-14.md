# 进攻时球队不整体前压 —— 病因定位（2026-09-14）

## 0. 一句话结论

**在进攻三区，中卫线的纵向目标是硬编码常量 `baseY + dir * 7`（4-3-3 → 距己方门线 33.6 m），
没有任何与球位有关的项。** 于是中卫线饱和在 33.6 m、**始终不过中线（52.5 m）**，
而锋线推进到 96 m —— 队形被拉成 62 m。

这不是「某个数字写大了」，是**整条中卫线缺一个自由度**。

## 5. 为什么**没有**顺手改（风险与验收要求）

1. **这条分支是有意的设计**，注释写明动机：「中卫留作防反保护，不再因为离球较近跟进到禁区弧顶围球」。
   把中卫线推上去会**削弱防反保护**——这正是它当初被写死的原因。要动必须证明
   「前压带来的进攻收益 > 丢掉的防反保护」。
2. **`AGENTS.md:3147` 的硬约束**：team block 的纵向平移 + 长度压缩
   「**会显著改变比赛轨迹**（进球、射门、控球），必须跨 n=24/n=48 复核并重跑全套比赛审计」。
3. 项目已经踩过「为画面改物理」并被否决（`engine.js:5167-5171`）。
   改这条的**唯一正当理由**是「真实球队的块是整体移动的」，
   而不是「2D 画面看起来太散」。
4. 需要同时守住的护栏：进球 2.5–3.3、转化 9–15%、直塞 ≥0.5、
   强弱分离（强队分/场与净胜球）、以及
   `scripts/attack-shape-compaction-audit.mjs` 的七个断言。

**本轮先只做诊断。** 改动方向明确（给中卫分支的 `ty` 加一个与球推进有关的项，
例如让 team block 随球整体平移 + 压缩），但它是**轨迹级改动**，应作为独立一轮、
带完整跨样本验收来做。

## 5b. 已落地的改动（2026-09-14 同日续做）

诊断完成后即按上述方向落地了最小改动，**只动中卫线的纵向目标，不动任何其它自由度**：

```js
// SIM（js/sim/engine.js:91 附近）
CB_BLOCK_SHIFT_MAX_M: -19,   // 负号：转向由下面的 -dir 处理

// _chooseAttackOffBallTarget 入口处（一次性计算，两个分支共用）
const blockShiftY = (prog * SIM.CB_BLOCK_SHIFT_MAX_M) / (SIM.PITCH_H_METRES / SIM.FIELD_H);
const blockForward = -dir * blockShiftY;

// 终三区分支 :3798
a.ty = clamp(a.baseY + dir * 7 + blockForward, 18, 82);
// 兜底分支 :4033
const cbTargetY = clamp(a.baseY + dir * 3 + blockForward, 3, 97);
```

**符号推导**（踩过一次，记录以防回归）：home 的 `dir = -1`（`attackDir`），
进攻方向是 `y` 减小。中卫 `baseY = 75`，所以 `baseY + dir*7 = 68`。
要把中卫线**向前**推，`ty` 必须**增大**（68 → 91）。因此叠加项必须是 `−dir × shift`，
其中 `shift` 取负值（`-26`），两步负号相乘得到正向推进。**不能写成 `+dir*shift`**——
那样在 `prog` 增大时会把中卫线推向自家球门（实测 depth 从 33.6 m 掉到 3.4 m，方向完全相反）。

**实测效果**（`_attack-block-shift-probe.mjs 2 standard`，与 §2 同口径）：

|---|---|---|---|
| 中卫线目标深度（进攻三区） | 33.6 / 33.6 m | **56.7 / 56.8 m** | 56–66 m ✓ |
| 中卫线实测深度（进攻三区） | 33.6 / 33.6 m | **56.9 / 56.8 m** | ✓ |

### 5b.1 标定：`CB_BLOCK_SHIFT_MAX_M` 是单一旋钮，但存在真实 trade-off

首次取 `-26` 时 `verify --full` **失败**：

```

  at scripts/match-realism-audit.mjs:447
```

即**强队优势被摊薄**（`strongVsWeak.pointsPerMatch` 跌到 1.46，门槛 ≥1.5）。
这正是中卫线整体前压最典型的副作用：把后卫线推上去之后，**弱队也更容易打出进攻**。

于是用该单一旋钮做了三点标定（`node scripts/match-realism-audit.mjs 24`，
单跑该入口约 8.5 分钟，无需整套 52 分钟）：

| 前压值 | 强队积分/场 | 门槛 | CB 最深（球≥70m） | DEF→ATT 跨度（球≥85m） | 结果 |
|---|---|---|---|---|---|

| −26 | 1.46 | 1.5 | 56.8 m | 38.9 m | ❌ 失败 |

**⚠ 关键结论：单一旋钮下「通过护栏」与「达成队形目标」无法兼得。**
诊断文档 §4 设定的目标是 CB 56–66 m / 跨度 30–40 m，但只有会压破护栏的 −26 能满足；
两个通过值分别为 46.1 m 与 50.9 m，**都还没越过中线 52.5 m**。

**定稿值 `−19`**，理由是：

- `−14` 的队形改善（46.1 m，仍在中线以下）不足以支撑这次轨迹级改动的风险——
  付了改变比赛轨迹的代价，却没真正解决「中卫线冻结在自家半场」的核心问题。
- `−19` 已摸到中线（50.9 m），方向上是真变化；1.67 距门槛 +0.17，在 24 场样本下属偏紧但可接受。
- `−26` 为了队形压破一项硬护栏，违反项目「不为画面改物理」的原则
  （`engine.js:5167-5171` 已有先例被否决）。

**⚠ 遗留问题（下一轮）**：真实足球里「队形是否紧凑」与「强队优势是否保留」是**解耦**的——
整体前压会同时提高双方进攻效率，而强队优势来自能力与战术执行，**不来自站位**。
现在用同一个常数给所有球队，等于强行把两者绑在一起。更接近现实的做法是让前压量
**随球队强弱/战术倾向有差异**。但这需要新的数据驱动依据，超出本轮「最小改动」范围。

## 5d. 让前压量由「防线高度」驱动（2026-09-14 续做第二轮）

### 5d.1 动机：常数前压存在真实 trade-off

§5b.1 标定出的问题是：`CB_BLOCK_SHIFT_MAX_M` 对两队是**同一个常数**，中卫线前压
**同时**提高双方的进攻效率，于是摊薄强队优势（−14 → 1.92、−19 → 1.67、−26 → 1.46）。
单一旋钮下「通过护栏」与「达成队形目标」无法兼得。

真实足球里这不是一个常数问题：**防线高度本来就是战术选择**，而且
`js/delegation.js:231-241` **已经**按实力差设定它——

```js
if (difference <= -1.5 && adaptability >= 3) {          // 弱队
  style = "counter"; pressing = Math.min(pressing, 2);
  defensiveLine = Math.min(defensiveLine, 2);           // 低防线
```

### 5f.3 病因：同一个「常量」病，`dBall < 55` 把它锁死

`_chooseAttackOffBallTarget` 的边卫分支（`engine.js:4008-4038`）：

球在 85–105 m、远侧边卫在 38 m 时，它与球的直线距离约 58 m > 55，

### 5f.11 `verify --full`：第一次失败，但失败点是**既有的 flaky 审计**（顺带修掉）

```
    at file:///F:/VCFM/scripts/player-attributes-audit.mjs:140:8
```

**失败点在球员属性成长，与本轮改动无关**，证据三条：

1. 该审计的依赖链（`js/models.js`、`js/player-attributes.js`、`js/player-habits.js`）
   **零处**引用 `js/sim/engine.js`（`grep -c "sim/engine"` 三个文件都是 0）。
2. 单独连跑 **20 次失败 1 次（5%）**——它本来就是随机的。
3. 失败断言读的是 `sample.find(p => p.attributeArchetype === "playmaker")`，
   而 `createPlayer` 走 `Math.random()`（`js/models.js:66,74,82`），
   取到的是**随机样本里的第一个** playmaker。

`weightedDevelopmentAttributes` 的 `< 20` 候选过滤（`js/player-attributes.js:258`）

**修法**（只改取样，不改断言语义）：

```js
const developmentFixture = sample.find(

    && player.attrs.passing < 20 && player.attrs.tackling < 20

assert.ok(developmentFixture, "sample must contain an uncapped playmaker to measure development weighting");
const development = weightedDevelopmentAttributes(developmentFixture);
```

   把防线顶出去~~ —— **§5h 实测证伪**：对手后卫只是正常站在球的球门侧
   （球 8.3 m / 后卫 8.5 m），要达标必须让他们站到球前面，几何上不可达。
2. **先补后场发起的进攻质量。** 本轮与门将出球调查（`docs/gk-distribution-choice-2026-09-14.md`）
   都观察到同一个现象：**压缩队形 / 改善出球都会掉进球**，掉的都是近距离转化率。
   如果进球产出真的依赖「阵型松散带来的乱战」，那它就不是可以靠站位参数调节的量，
   而应该先去把**深位组织的射门质量**修好。

## 5h. 第六轮：验证「方向 1（防守端压跨度）」的前提（2026-09-14，**方向 1 被证伪**）

§5g.5 把方向 1 记为「未验证的候选方向」。本轮把它当作待证假设来检验，结论是
**方向 1 不成立**，而且顺着检验发现了一个更重要的东西：**「进攻三区跨度」这个指标
本身是被相位混杂污染的**。

### 5h.1 待证假设

> 进攻三区跨度 47.3 m 的上端是 ATT 98.0 m，被 `_clampOffside` 钳在**对手最后一名后卫**
> 的线上。两队深度都从各自门线量起，故有恒等式 `我方 ATT 深度 + 对手最后一名后卫深度 = 105 m`。
> 若对手后卫退得太深，让防守方在球进本方三区时把防线顶出去，就能在不动进攻方中卫线的
> 前提下压短跨度。

检验需要三个数：① 恒等式是否真的成立；② 对手后卫到底站多深；③ 要达标他们得站到哪。

### 5h.2 工具

- `scripts/_attack-span-endpoints-probe.mjs` —— 本轮重写为第二版：持球帧收紧为
  `owner 存在 + ball.state ∈ {held, control} + 球不在持球方自己禁区内`，并**取消**
  「只看进攻三区」的采集限制，改为全帧采集、按节过滤，从而能输出**全场块高剖面**。
- `scripts/_ball-depth-occupancy-probe.mjs`（新增）—— 独立量「球到底有多少时间待在
  对方禁区一带」，用来交叉验证上一条的样本是否相位同质。

两档均为 4 场、种子 `372000..372003`、每 0.5 秒采样，与队形审计同种子。

### 5h.3 恒等式成立（假设的前提是对的）

| 指标（进攻三区持球帧） | 标准 | 后台 |
|---|---:|---:|
| `我方 ATT 深度 + 对手最后一名后卫深度` 中位 | **104.88** | 104.85 |
| 均值 | 104.80 | 104.93 |
| 被钉住（残差 \|x\| ≤ 2 m）占比 | **58.6%** | 53.3% |
| 残差中位 | −0.12 | −0.15 |

恒等式成立，而且 `_offsideLineY`（`engine.js:4965`）返回的是**倒数第二名防守者**
（把门将计入 `defenders`）——**Law 11 实现正确，没有越位线用错人的缺陷**。
所以「降跨度只能靠抬高对手防线」这句推理本身是站得住的。

### 5h.4 但对手后卫站的位置是**对的**

85–105 档（球距对方门线 <20 m）实测：

| 量 | 中位 |
|---|---:|
| 对手最后一名后卫离其门线 | **8.5 m** |
| 对手后卫线中位深度 | 12.1 m |
| 对手挤在自家 18 m 内的外场人数 | **6 人** |
| **球本身**离对手门线 | **8.3 m** |

也就是说：球在门前 8.3 m，对手倒数第二名防守者在 8.5 m —— **对手只是正常地站在球的球门侧**，
并不是「退得过深」。要让我方 ATT 退到 90.7 m（跨度 ≤ 40 m），对手最后一名后卫必须站到
**离其门线 ≥ 14.3 m**，即比球还靠前 6 m —— 那等于要求防守方把防线放到球**后面**。
**几何上不可达，方向 1 被证伪。**

### 5h.5 顺带发现的真问题：指标被相位混杂污染

`_attack-span-endpoints-probe.mjs` 的全场块高剖面（标准档；后台档逐位一致）：

| 球深度 | 队帧 | CB 最深 | 中场最深 | ATT 最深 | 跨度 | 块长 |
|---|---:|---:|---:|---:|---:|---:|
| 0–15 | 309 | 9.6 | 28.8 | 40.0 | 31.2 | — |
| 25–35 | 1674 | 25.8 | 40.8 | 47.9 | 19.6 | 22.0 |
| 35–45 | 1934 | 33.5 | 49.0 | 53.9 | 18.9 | 20.0 |
| 45–55 | 2519 | 38.0 | 57.1 | 61.4 | 22.8 | 23.6 |
| 55–65 | 3129 | 40.0 | 66.5 | 70.4 | 29.2 | 30.3 |

**「球 85–105」占进攻三区持球帧 80.8%。** 所以审计里那个 47.4 m
**几乎全由深入帧贡献**；而在块长这个概念成立的阶段（球还没进对方 20 m 区），
块长已经是 **36.9 m —— 就在 30–40 m 目标带内**。

独立口径交叉验证（`_ball-depth-occupancy-probe.mjs`，标准 / 后台）：

| 量 | 标准 | 后台 |
|---|---:|---:|
| 球距最近门线 <16.5 m 的全帧占比 | 49.4% | 48.4% |
| 球距最近门线 <20 m 的全帧占比 | 55.3% | 54.2% |

6 场读数与 `AGENTS.md` 记录的 v253「六场标准/后台 679.62/772.30 秒」对齐：
后台差 0.5%（吻合），标准高约 12%。标准的差额来自**采样边界归属**——本探针每 0.5 秒采样、
审计每 0.1 秒，标准档 0.5 秒跨 5 个 step，回合首末帧会被整段归给采样瞬间的状态。
**这是采样伪影，不是引擎差异**，已写进探针注释：要精确对账请直接跑
`box-possession-sampling-audit.mjs`，不要把本探针当护栏。据此也确认
**本轮的 851.7 只是 4 场子集偏高，不构成护栏越界**。

口径既已对齐，**「进攻三区跨度中位」其实主要在量禁区围攻**，
而不是组织阶段的块长。

### 5h.6 结论

1. **块高是正常跟随的。** CB 最深随球深度**单调上移**：9.6 → 18.9 → 25.8 → 33.5 →
   38.0 → 40.0 → 43.3 → 47.0 → 49.9 → 51.3 m。「进攻时球队不整体前压」
   **在这个读数上不成立**。
2. **「进攻三区跨度 30–40 m」这个目标被误用到了禁区进攻阶段。** 它适用于组织阶段
   （实测 36.9 m，已达标），不适用于球已在门前 8 m 的围攻帧——那里的跨度由
   **对手的越位线**决定，而我方中卫线是唯一杠杆，§5g 已证明它用尽。
3. **方向 1 不成立**：对手后卫只是正常站在球的球门侧（球 8.3 m / 后卫 8.5 m），
   要达标必须让他们站到球前面，几何上不可达。
4. **剩余的真实缺口是禁区围攻本身**，而它已经有专门的护栏
   （`box-possession-sampling-audit.mjs`，上限 850 秒/场）——**不需要再用跨度断言去量它**。

### 5h.7 处置

- **不改引擎**。本轮没有可落地的改动，`js/sim/engine.js` 未改动。
- **不改护栏**。`attack-shape-compaction-audit.mjs` 现上限 `attackCeiling 54` / `span [30, 52]`
  在基线上是通过的（46.9 / 46.5），本轮**既没有放宽也没有收紧**它。
  把断言改成「只对组织阶段生效」是一个**口径变更**，需要单独一轮验证，本轮只记录结论。
- **主线应转向射门供给。** 全局跑位候选（`_backline-support-release-candidate.mjs`）
  的阻塞点是进球 2.21 / 2.16（需 ≥2.5），而不是队形；§5g.5 的方向 2
  （先补后场发起的进攻质量）与本轮观察一致：**压缩队形、改善出球都会掉进球，
  掉的都是近距离转化率**。交接文档给出的具体线索是
  `goalkeeper-relative-contact-audit.mjs` 复现出的「移动门将步末位置与球步中投影点混用」。
