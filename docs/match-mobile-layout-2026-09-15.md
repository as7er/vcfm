# 移动端比赛画面布局审计与修正（2026-09-15）

> 纯表现层改动：`css/style.css` 六处。**没有**碰引擎、数据、缓存、统计护栏或冻结参考。
> 本文所有数字都是真实浏览器（headless Edge + Playwright）逐元素量出来的，不是估算。

## 1. 结论先说

比赛画面里「球场」其实画在 `.mp-camera` 里，而 `.mp-camera` 为了让两侧看台露出来，
左右各内缩了 5.5%。**所有写比例的地方都把这 11% 漏掉了**，于是球场在屏幕上是纵向
拉伸的：中圈渲染成竖椭圆，禁区看起来比实际窄。手机档偏 8.3%，桌面档偏 12.4%。

修完（六档视口全部由 0.9166/0.8755 → **1.0004~1.0005**，即正圆）：

| 视口 | 中圈渲染宽高比 | 球场盒 | 相机宽高比 | <11px 文字数 |
|---|---|---|---|---|
| 360×640 | 0.9166 → **1.0004** | 337×506 → 337×463 | 0.5929 → **0.6479** | 57 → **30** |
| 390×844 | 0.9166 → **1.0005** | 367×551 → 367×505 | 0.5935 → **0.6475** | 56 → **29** |
| 414×896 | 0.9166 → **1.0004** | 391×587 → 391×538 | 0.5928 → **0.6468** | 57 → **30** |
| 844×390 | 0.9166 → **1.0005** | 638×957 → 638×877 | 0.5935 → **0.6477** | 30 → 30 |
| 768×1024 | 0.9166 → **1.0005** | 638×957 → 638×877 | 0.5935 → **0.6477** | 30 → 30 |
| 1440×1000 | 0.8755 → **1.0004** | 484×760 → 555×763 | 0.5671 → **0.6474** | 30 → 29 |

目标值 0.6476 = 68/105。「中圈渲染宽高比」= 中圈那个 `<ellipse>` 的
`getBoundingClientRect()` 宽/高；SVG 的 rx/ry 是按正圆标定的，所以这个比值就是
屏幕上的拉伸系数，1.0 才算对。相机 `scaleX == scaleY`，transform 本身是等轴的，
不是它造成的。

## 2. 三个已修缺陷

### 2.1 球场比例：把「球场盒」当成了「球场」

- 球场真正画在 `.mp-camera`（`index.html` 模板见 `js/matchview.js` 的 `mp-wrap` 段）。
- `.mp-stands` 与 `.mp-camera` 的内缩都是 5.5%，所以
  **相机宽 = 0.89 × 球场盒宽，相机高 = 球场盒高**。
- 于是 `球场盒宽高比 = (68/105) ÷ 0.89 = 0.6476 ÷ 0.89 = 0.7276 = 68 / 93.45`。
- 原值：`.mp-field` 写 `68/105`、`.fmm-match .mp-field` 与赛前/开赛中各写 `2/3`
  （=0.6667），四处都把球场盒当球场算。
- 球场 SVG 用 `preserveAspectRatio="none"`，这种拉伸**不会报任何错**，所以一直没被发现。

改动（四处必须同时改，只改一处会被更高特异性的规则盖掉）：

| 位置 | 原值 | 新值 |
|---|---|---|
| `.mp-field` | `68 / 105` | `68 / 93.45` |
| `.fmm-match .mp-field` | `2 / 3` | `68 / 93.45` |
| `.match-layout.pre-kickoff .fmm-match-body .mp-field` 等 | `2 / 3` | `68 / 93.45` |
| `.match-layout.live-kick / .ht-kick .fmm-match-body .mp-field` | `2 / 3` | `68 / 93.45` |

宽屏（≥1060px）还要加两条：

- 列宽公式 `calc((100vh - 250px) * 0.648)` → `* 0.78`，`minmax` 下限 340px → 260px。
  0.648 同样是「球场盒 = 球场」的错误系数。
- 宽屏开赛/中场让球场**按高度反推宽度**（`width:auto; height:100%; margin-inline:auto`）。
  宽屏行高是确定值，这样比例不受列宽公式里 250px 常数的影响。

  **这条必须写在 `.live-kick/.ht-kick` 基础规则之后**：同特异性下后写的才生效。
  第一版写在了文件前面的 `@media (min-width:1060px)` 里，被后面的基础规则盖掉，
  桌面反而从 0.8755 恶化到 1.0519（球场盒 583×762，相机 0.681，中圈横椭圆）。
  这是本轮唯一一次「修了反而更糟」，已修正并复测。

顺带的好处：球场盒变矮（390×844 下 551 → 505），小屏要滚的距离少了一截。

### 2.2 看台左右不对称

`.mp-stands` 原本 `z-index: 0`，在 `.mp-camera`（`z-index: 1`）之下。相机跟随球
平移时草坪跟着挪，一侧看台被完全盖住、另一侧露出一大条灰色条纹 —— 实测 360×640
下左边 0 条、右边约 13px，看着像渲染坏了（放大截图确认过：右边缘是 `.mp-stands`
的横向条纹，不是滚动条）。

改为 `z-index: 2`，看台变成固定画框。看台宽度正好等于相机的内缩量，所以相机在
1.0 倍时不会压到球场，只有放大/平移超出时才被切掉——这正是转播画框该有的行为。
修复后六档视口左右两侧看台宽度一致。

### 2.3 手机档场上文字过小

| 选择器 | 原值 | 新值 | 说明 |
|---|---|---|---|
| `.fmm-match .mp-num`（≤520px） | 0.64rem = 10.24px | 0.7rem = 11.2px | 球员号码，场上唯一必须读的字 |
| `.fmm-match .mp-name`（≤520px） | 0.46rem = 7.36px | 0.56rem = 8.96px | 持球人姓名 |
| `.fmm-match-bar .match-speed-bar .btn`（≤520px） | 0.68rem | 0.72rem | 倍速档 |
| `.fm-sb-comp`（≤520px） | 0.62rem | 0.68rem | 计分板上的轮次标签 |

手机档 <11px 文字数因此从 56/57 降到 29/30。减少的正好是 `.mp-num` 22 个与
`.btn` 5 个（倍速档）；剩下 29~30 个是 `.mp-bench-dot` 16 个（8px，替补席小圆点）、
`.mp-official` 3 个（9.5px）、`.mp-end-label` 2 个（8.8px）、`.mp-rec-badge` 1 个
（8.8px）、`.mp-bench-side` 2 个，以及 `fm-sb-comp`/`fm-sb-live`/`mp-fmm-speed`/
`fm-com-badge` 各 1 个——都是装饰性水印，不是必须读的信息。

## 3. 看过但**没有**改的

这些都是有意为之或需要独立决策，不是漏掉：

1. **横屏手机（844×390）**：球场盒 638×877 落在 390px 高的视口里，只能看到顶部约
   四分之一，其余靠滚动。`css/style.css` 里有一条明确注释说明这是故意的
   （「Let the page scroll instead」）——因为要真塞进 390px，扣掉计分板 107 +
   评论 55 + 底栏 57 + dock 50 之后只剩约 80px，球场会缩成一条 58px 宽的细缝。
   底栏是 `position: sticky; bottom: 0`，所以控制键始终可见，能接受。
   要真正改善得给横屏单独做一版布局（横置球场或隐藏评论栏），不在本轮范围。
2. **相机放大 1.28 倍**：`电视` 档固定裁掉球场约 22%。这是档位设计（另有`全场`），
   不是缺陷。
3. **触控目标**：图标键 30×36、评论折叠 27×27、数据条 343×26，低于 40px 建议值。
   一排 5 个图标键 + 5 个倍速档在 351px 宽度里已经排满，要放大就得改成两行、
   挤压球场高度。属于取舍，未动。
4. **`.mp-wrap` 溢出父容器**：360×640 下 wrap 561 / root 448（+113），横屏 +657。
   父级 `.fm-pitch-col` 有 `max-height: min(70dvh, 100%)`，但球场盒高度由宽度推出、
   且 `.match-pitch-root` 是 `flex: 1 1 auto`（basis auto → 百分比高度不解析），
   所以这个上限实际不生效。因为没有任何一级裁剪，视觉上只是「多出来」，无害。
5. **战术复核弹窗（`.motion-review-pitch`）同一类缺陷**：它 `viewBox="0 0 100 100"`
   配 `aspect-ratio: 68/105`，中圈用 `<circle r="9.15">` 画——渲染出来是 0.6476 的
   竖椭圆（偏 35%），球员点、球、文字同样被横向压扁。要修得把它按主球场那套
   `0 0 100 150`（y×1.5）坐标系重画，不是改一个 `circle→ellipse` 就完事
   （那样中圈圆了、球员还是扁的，反而不一致）。本轮未动。
6. **桌面「一键战报」模式**（`.match-report-only`）的球场比例未验证。该模式把
   `#match-pitch-root` 限到 `22dvh`，比例链与开赛档不同，需要单独跑。

## 4. 复现

```bash
# 逐视口量盒子、中圈圆度、画布 CSS/缓冲比例、<11px 文字、<40px 触控目标
node scripts/_match-mobile-layout-probe.mjs .tmp-continuity/match-layout-after

# 候选 CSS 实验台：一次开赛，注入 N 套候选并逐档复测（改 CSS 前先用它筛）
node scripts/_match-layout-lab.mjs .tmp-continuity/match-layout-lab --shots

# 放大看某张截图的局部（排查像素级细节，无需开赛）
node scripts/_image-zoom.mjs <源图> <输出图> x,y,w,h [倍率]
```

三者的坑（都踩过）：

- **探针/实验台的 `outDir` 用 `node:path` 拼绝对路径，不要传 `URL` 对象**：
  沙箱的 fs broker 会抛 `ERR_INVALID_URL_SCHEME`，脚本在第一次 `mkdirSync` 就死，
  一行产出都没有。
- **实验台注入的候选 CSS 必须复用真实选择器**。开赛时 `.match-layout` 带
  `.live-kick`，`aspect-ratio` 与 flex 尺寸都写在
  `.match-layout.live-kick .fmm-match-body .mp-field`（0,4,0）上；只写
  `.mp-field {...}`（0,1,0）会**静默失效**，量出来的「前后一致」是假的。
  第一轮实验就是这么被骗的。
- **`getBoundingClientRect()` 吃相机 transform**。相机固定 `scale(1.28)`，
  所以画布 rect 恒比布局盒大 28%（418 vs 327）。判断「有没有溢出容器」要用
  `clientWidth/clientHeight`，用 rect 会把正常的镜头缩放报成 15 项溢出。
