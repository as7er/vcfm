# 两处用户报告缺陷的定位与修复（2026-09-19）

本轮修两个**用户肉眼发现**的缺陷。共同点：**都不是引擎算错，而是"事实没被完整传递"** ——
一个断在表现层的 class 同步，一个断在榜单的样本门槛口径。

## 一、球员"比赛开始没多久就一直站在场边"

### 用户描述
> "帮我看看为什么有个球员比赛开始没多久后就一直站在场边"
> 截图：左边边线红色 15 号一直卡在那里不动。

### 定位过程（三段，每段都在排除上一个假设）

**第 1 段 · 引擎侧：确认这是设计行为，不是 bug**

`js/sim/engine.js:1971` 的 `_think`：

```js
if (a.sentOff) {
  // 被罚下：走向边线外并停住，不再参与任何决策/跑位。
  a.tx = a.team === "home" ? 1 : 99;
  a.ty = clamp(a.y, 4, 96);
  a.fsm = "off";
  a.intent = null;
  a.offBallTarget = null;
  return;
}
```

用 `Object.defineProperty` 给 `sentOff` 装 setter 抓调用栈，一击命中：

```
_rollFoulCard (engine.js:6627)
  ← _commitFoul   (engine.js:6678)
  ← _resolvePossession (engine.js:6215)
```

⇒ 该球员**作为抢断者下脚犯规、掷出直红**（`_rollFoulCard` 里 `card = "red"`），
引擎按设计让他走向本方底线并停住。**引擎侧无错。**

> 诊断踩的坑：第一版判据用"是否贴边"（`y < 2.5 || y > 97.5`）扫 4 场，
> 最长连续贴边只有 3~10s ⇒ **误判"未复现"**。改成"瞬时速度 < 0.05 场单位/秒
> 且持续 ≥ 60s"后立刻找到 `a-p8` 的 310s 低活动。
> **教训：判据选错会让你得出"没有问题"的结论。**

**第 2 段 · 事件通道：确认红牌信息本来就会被翻译**

`js/sim/adapt.js:697-714` 的 `pickFlavorEvents` **已经把 `foul` + 红牌转成 `type:"red"`**：

```js
} else if (e.card === "red" || e.card === "red2") {
  out.push({ minute, type: "red", team: e.team, agentId: e.agentId,
             secondYellow: e.card === "red2", t: e.t });
}
```

→ `js/match.js:1312-1323` 的 `pushSimFlavor` 产出带 `playerId` 的 `red` 事件
→ `js/matchview.js:6704` / `:7017` 的 `case "red"` 加 `.sent-off` class。

> ⚠ 我一度以为要在 `match.js` 里补一个 `foul` 分支，**写完才发现是死代码**
> （`item.type` 永远不会是 `"foul"`），已完整撤销。
> **教训：改之前先读完整条链路，别在中间加看似合理的分支。**

**第 3 段 · 表现层：真正的脱节在这里**

`js/matchview.js` 里 `.sent-off` **只由一次性事件分支设置**，而：

| 读取方 | 位置 | 读的是什么 |
|---|---|---|
| 画布绘制 | `drawList`，`:3524` | `!p.el.classList.contains("sent-off")` |
| 约 60 处选人逻辑 | 全场（最近的队友/对手、可接球者…） | 同上 |
| 动作诊断 | `:2907` | **从 class 反读**成 `sentOff` 字段 |

而 `applySimSnapshot`（`:426`）的球员循环**只读不写**：

```js
for (const pl of this.players) {
  if (pl.el.classList.contains("sent-off")) continue;   // 只读
  ...
}
```

⇒ **只要那一个红牌事件因为任何原因没被这一层消费到**（跳段、快进、事件重放、
`this.players` 在这一帧之前刚被重建过），class 就**永远补不上**，该球员此后
一直画在场上、一直参与选人。用户看到的就是这个。

（另外 `:722` 那行 `sentOff: !!(t < 0.5 ? a.sentOff : b.sentOff)` 把字段写进了
插值结果，但**全文件从未被读取** —— 是个半成品。）

### 修复

在 `applySimSnapshot` 的球员循环**开头**，按 compact frame 的 `sentOff` 同步 class：

```js
const s = byId.get(pl.id);
if (s) {
  const off = !!s.sentOff;
  if (off !== pl.el.classList.contains("sent-off")) {
    pl.el.classList.toggle("sent-off", off);
  }
}
if (pl.el.classList.contains("sent-off")) continue;
```

三个设计决定：

1. **放在快照路径，而不是继续依赖事件**：compact frame **每帧都带 `sentOff`**
   （`engine.js:8285`）。用它就能**自愈** —— 状态错了下一帧纠回来，
   不依赖任何一次事件是否送达。
2. **edge-triggered**（只在状态变化时写 DOM）：`applySimSnapshot` 是每帧热路径，
   无条件 22 次 `classList.toggle` 是纯浪费。
3. **不额外设落点**：引擎已经给了"走向底线"的轨迹，循环末尾的 `continue`
   会让它原样保留。事件分支另设的边线落点（`pl.ty = foulHome ? 102 : -2`）
   与引擎的底线落点不一致，在快照路径里以引擎为准。

### 验证

- `js/matchview-{fsm,coords,director}.test.js`：**17/17 通过**；
- `scripts/match-presentation-audit.mjs` / `match-continuity-audit.mjs`：通过；
- **新增源码断言**（写进 `match-presentation-audit.mjs`）：锁死
  `classList.toggle("sent-off", off)` 的存在、edge-trigger 形态、
  以及 `engine.js` 必须有 `sentOff: !!a.sentOff`（快照带这个字段是修复的前提）；
- **反假通过检查**：临时把修复换成 `classList.add("noop-guard")` 后，
  审计 `EXIT=1` —— 证明断言真的在测东西，不是恒真。

### 🔍 顺带发现的第二个缺陷：换人后新球员"继承"了离场标记

修完主缺陷后，顺着"谁还会读写 `.sent-off`"复查时发现 `applySubOnPitch`
（`js/matchview.js:2040`）是**身份替换 + 复用同一个 DOM 元素**：

```js
pl.id = inn.id;          // 换成新球员
pl.player = inn;
pl.el.dataset.id = inn.id;
```

**但它没有清 `.sent-off` / `.injured`** ⇒ 被换下的若是罚下/伤退者，
他的离场标记会被**新上场的球员继承**：

- 新球员一登场就是**淡出的**（`opacity: 0.25`）、**不可点**（`pointer-events: none`）、
  而且**不被画到画布上**（`drawList` 过滤掉）；
- 旧机制下这个 class **一旦加上就永远移除不了**（全文件没有一处 `remove("sent-off")`）。

这在旧代码里会表现为"换人之后那个人像幽灵一样"——用户这次没报，
但它和主缺陷是**同一个根因的两个症状**。

**修复**：在 `applySubOnPitch` 里、改 id 之前清掉两个标记：

```js
pl.el.classList.remove("sent-off", "injured");
```

> `.sent-off` 其实还有第二道保险 —— 改完 id 后 `applySimSnapshot` 每帧按**新 id**
> 查到 `sentOff === false`，会自动 toggle 掉。但 `.injured` 是纯表现层标记
> （引擎不导出），只能在这里清。两个一起清最稳。
> 已加进 `match-presentation-audit.mjs` 的断言。

## 二、评分榜里"出场不多但均分很高"的球员排在前列

### 用户描述
> "我发现球员评分榜里，只出场次数不多的高平均评分的竟然也可以上榜排在前列"

### 定位

两处榜单，门槛都很低：

| 榜单 | 位置 | 门槛（修前） |
|---|---|---|
| 联赛评分榜 | `js/engine.js:2546` | `apps >= 3` |
| 赛事评分榜 | `js/cup.js:482` | `apps >= 2` |

而评分公式（`js/match.js:3058-3086`）是**进球驱动**的：

```
r = 6.4 + (ovr-12)*0.04 + 体能/士气微调
    + 进球 × 0.95 + 助攻 × 0.55 + 门框 × 0.15
    - 黄牌 × 0.35 - 红牌 × 1.6
    ± 净胜球 0.28 / 0.05 / 0.22
    + 噪声 (rng-0.5) × 0.45
  单场封顶 9.6
```

**进球是小概率事件** ⇒ 出场数少的人，场均分的**方差极大**：
踢 3 场里蒙进 2 球 → 均分 8.x；踢 20 场进 0 球的后卫 → 均分 6.5。
门槛 `>= 3` 完全拦不住。

### ⛔ 我先犯的建模错误（值得记下）

第一版探针把评分当成"围绕真实水平加噪声"（`mean + ±0.225`），
模拟结果是"替补挤掉主力的概率 **0.00%**" —— **与用户报告直接矛盾**。

原因：噪声只有 ±0.225，round 到 1 位后**大量评分塌缩到同一个离散值**
（6.9 / 7.0 / 7.1），方差被抹平了。**真正的方差来源是"进了几个球"这个离散事件。**

换成进球驱动模型后**立刻复现**用户现象。

> **教训：建模前必须先读公式。凭直觉假设分布，会得出与事实相反的结论，
> 而且它看起来还挺"严谨"（有蒙特卡洛、有置信度）。**

### 量化（进球驱动模型，蒙特卡洛）

前 20 名里"出场 ≤5 场"的平均人数：

| 门槛 | ≤5 场人数 | ≤8 场人数 | 榜首平均出场数 |
|---|---|---|---|
| **3（旧）** | **7.82** | 9.77 | 4.1 ❌ |
| 5 | 2.70 | 5.11 | 8.9 |
| 8 | 0.00 | 2.67 | 12.3 |
| **10（新）** | **0.00** | **0.00** | **15.3** ✅ |
| 12 | 0.00 | 0.00 | 18.3 |

**门槛 10 是拐点**：≤8 场的人彻底清零，榜首出场数升到 15.3（像个真主力）。

另一条独立佐证：踢 3 场的前锋、场均分 ≥ 8.0 的概率是 **1.01%**；
踢 20 场的只有 **0.00%** ⇒ **小样本是唯一能上高分的途径**。

### 修复（用户 2026-09-19 拍板：提高门槛 + 默认直接生效）

- `js/engine.js:2546`：`apps >= 3` → **`apps >= 10`**
  （联赛 34 轮，10 场 ≈ 赛季 30%）；
- `js/cup.js:482`：`apps >= 2` → **`apps >= 4`**
  （洲际赛事总场次少，按规模折中；同尺子会把榜清空）；
- **文案 6 处同步**：`js/i18n.js`（中/英 × 联赛/赛事）、
  `index.html`（两处静态默认文本）、`js/ui/league-centre.js`（空榜提示）。
- **`js/intl.js:177` 的 `apps >= 3` 故意不动**：那是国家队征召的**内部评分**，
  场均分只是 `bounded(…, ±0.9)` 的加成项，样本少只会让它影响小，
  不会造成"谁该入选"的错判。已在原地加注释说明为何与评分榜口径不同。

> ⚠ 踩的坑：`Edit` 只替换**第一处**匹配。英文 `i18n.js:975` 与 `index.html:828`
> 的同类文案我第一次没改到（误以为匹配的是它们），审计断言准确地抓了出来。
> **改多语言/多处重复文案后必须 grep 复查，别信一次 Edit。**

### 验证

新建 `scripts/ratings-leaderboard-audit.mjs` 并接入 `verify.mjs`，做两件事：

## 三、这轮的两个通用教训

1. **判据选错比不做测量更危险**：第一轮的"贴边"判据让我得出"未复现"，
   第一版的评分模型让我得出"不存在这个问题"。两次都是**测量方法错了**，
   而输出看起来都挺正式。**每次得到"没问题"的结论时，先怀疑判据。**
2. **"一次性事件"是脆弱的同步机制**：`sentOff` 这件事同时存在于引擎状态、
   compact frame、DOM class 三个地方，而只有 frame 是**每帧重算**的。
   凡是"每帧都有的真相"，就不该靠"某一次事件是否送达"来维持。
