## 1. 为什么需要新原语（诊断结论回顾）

**实测确证**（`scripts/_one-on-one-dribble-probe.mjs`，12 场，两档）：

| 档位 | 核心摆脱率 | 普通摆脱率 | 比值 | 核心/普通 `dribbling` |
|---|---:|---:|---:|---:|
| tiered（18 vs 9） | **0.5%**（9/1912） | **1.32%**（107/8129） | **0.38×** | **2.00×** |
| uniform（同值 15） | 0.3%（8/2449） | 0.95%（97/10215） | 0.32× | 1.00× |

- **`dribbling` 差 2 倍，摆脱率反而低 0.38 倍 ⇒ 摆脱率与 `dribbling` 完全无关。**
- **uniform 档是决定性反证**：所有属性相同，摆脱率仍有差异 ⇒ 该差异**不来自属性**。
- 现有 1.2% 的"摆脱"是**几何副产品**（防守者移动惯性没跟上 / 抢断冷却 / 球权转移）。

**引擎已有的（不要重复造）**：防守者发起的抢断结算
（`engine.js:5969-6003`，`dribbling+strength` vs `tackling+marking`，
含护球朝向 `shieldAlignment`、相对速度动量 `momentumAdjustment`、犯规判定）。
⇒ **这套公式本身很好，缺的只是"持球者发起"的另一半。**

**缺的具体是什么**：`engine.js:2736-2750` 的 `dribble` 选项只设移动目标：

```js
if (aheadSpace > 0.2 || (isWing && ...)) {
  const burst = 0.6 * a.attr.dribbling + 0.4 * a.attr.pace;
  options.push({
    key: { act: "dribble" },
    w: (0.12 + 0.9 * burst) * spaceW * (1 - pressure * 0.55) * midBoost,
  });
}
```

⇒ 它是「**前方有空当就走**」，权重还随压力**下降**（`1 - pressure*0.55`）。
**没有「我要过掉眼前这个人」这个选项。**

## 2. 原语定义

### 2.1 一句话

> **持球者主动把球带向最近防守者，并按 `dribbling`/`balance` 对抗 `tackling`/`marking`
> 掷一次骰子；赢 ⇒ 该防守者短暂失位（`beat` 事件）；输 ⇒ 球权风险上升（可能被断）。**

关键词：**主动**（持球者发起）、**结算**（按属性掷骰）、**可观测**（`beat` 事件）。

### 2.2 与现有抢断的关系（正交，不重复）

| | 抢断（已有） | 突破（新增） |
|---|---|---|
| 发起方 | 防守者（`press` 职责球员） | **持球者** |
| 触发 | 防守者在 `CONTROL_RADIUS + …` 内 + 冷却到期 | **持球者在决策时选 `beat` 动作** |
| 结算 | `tackling+marking` vs `dribbling+strength` | **`dribbling+balance` vs `tackling+marking`** |
| 结果 | 球**换手** | 防守者**短暂失位**（不换手） |
| 冷却 | `tackleCdUntil`（36~60s 量级） | **`beatCdUntil`（待定，见 §5.3）** |

⇒ 二者**可以连续发生**：突破失败 ⇒ 防守者更贴近 ⇒ 抢断窗口更容易打开。
这正好是真实足球的因果链。

### 2.3 接缝位置（最小侵入）

**唯一改动点**：`_thinkAttackPossession`（约 `engine.js:2690` 的 `options` 构造）里
**新增一个 `beat` 选项**，与 `dribble`/`pass`/`longshot` 并列：

```js
// 新增：主动突破（仅在最近防守者进入可对抗距离、且有空当可越过时入池）
const duel = this._beatDuelCandidate(a);   // 新增 helper，返回 {opp, d, gapY} 或 null
if (duel) {
  const w = this._beatOptionWeight(a, duel, { core, isWing, pressure });
  options.push({ key: { act: "beat", opp: duel.opp }, w });
}
```

**执行分支**（与 `dribble` 并列，约 `engine.js:2801`）：

```js
} else if (choice.act === "beat") {
  this._attemptBeat(a, choice.opp);
}
```

**不碰**：`_pass`、`_shoot`、`_commitOffBallTarget`、`_clampOffside`、
抢断系统、越位系统、事件时间戳逻辑。

### 2.4 结算公式（草案，待标定）

对齐现有抢断公式的形状（`engine.js:5996`），但**表达"进攻方赢"**。
**注意：本原语是两层结构**（第一版只有一层，被实测证否，见 §2.4.1）。

**第一层 —— 意图门槛**（"我这次要不要过他"）：

```js
// 贴身 ≠ 想过人。真实足球在 ~1000 次持球接触里只挑出 ~17 次 take-on。
const intentP = INTENT_BASE + INTENT_PER_DRIBBLING * a.attr.dribbling;
if (this.random() >= intentP) return;   // 本次不尝试
```

**第二层 —— 越过结算**（"过不过得去"）：

```js
// 进攻方能力
const atk = 0.55 * a.attr.dribbling + 0.25 * a.attr.balance + 0.20 * a.attr.pace;
// 防守方能力（与抢断公式同项，权重对齐）
const def = 0.60 * opp.attr.tackling + 0.20 * opp.attr.marking;
// 侧向角：防守者站位偏离持球者前进线越多，越好过
const angleBonus = (dAng / Math.PI) * ANGLE_WEIGHT;
// 协防惩罚：每多一名 8m 内的协防者
const p = clamp(
  BASE + (atk - def) * ATTR_WEIGHT + angleBonus - helpers * HELP_WEIGHT,
  P_MIN,
  P_MAX
);
if (this.random() < p) {
  opp.beatenUntil = this.t + BEAT_STAGGER_SECONDS;   // 防守者失位
  this._emit("beat", a, { from: opp.id, distance: d });
}
```

#### 2.4.1 为什么必须是两层（第一版被证否）

**第一版只做了"冷却 + 结算"**（每次贴身都掷一次，靠冷却限频）。实测：

| 版本 | 单队尝试/场 | 真实基准 | 倍数 |
|---|---:|---:|---:|
| 第一版（仅冷却 4s） | **593.5**（双方 1187） | ~17 | **~35×** |
| 第二版（长度 1.2s + 冷却 3s） | **721.5** | ~17 | **~42×** |
| **加意图门槛后** | **35.4** | ~17 | 2.08× |

⇒ **根因**：引擎里"贴身"是**常态**（实测 53.5% 的持球样本最近对手 ≤3m、
46.8% 落在 2-3m 桶）。任何"贴身即触发"的方案都会**必然**给出比真实高 1~2 个
数量级的频次。**真实足球的 take-on 是有意图的动作**，不是"有人靠近"。
⇒ 故必须有**独立于冷却的意图门槛**，且它本身就是"球员差异"的第一层体现。

#### 2.4.2 `norm()` 压缩：属性差有个先天上限（重要）

引擎的属性在进 agent 前过 `norm()`（`engine.js:347`）：

```js
norm(v) = clamp(0.28 + clamp(v/20, 0.05, 1) * 0.64, 0.3, 0.92)
```

⇒ **`dribbling` 18 vs 9 在引擎里是 0.856 vs 0.568（比值 1.51），不是 2.0。**

这决定了**属性差的理论上限**。代入 §2.4 的公式（防守方 `def ≈ 0.56`）：

- 核心：`p ≈ BASE + (0.856 − 0.56) × W = BASE + 0.296W`
- 普通：`p ≈ BASE + (0.568 − 0.56) × W = BASE + 0.008W`
- ⇒ 理论差 `≈ 0.288W`，要 ≥ 0.15（15pp）需 **`W ≥ 0.52`**

⚠ **但实测达不到这个上限** —— 因为 `P_MIN` 与 `angleBonus` 会把**低位球员的成功率抬起来**，
逼近核心。第一轮扫描（4 场/组）显示 `W` 从 1.35 提到 1.90，属性差只在 **+5~10pp** 徘徊，
且样本小时会剧烈波动（有一组甚至读到 −15pp）。

⇒ **结论：`norm()` 压缩 + `P_MIN` 地板，共同限制了"球星 vs 普通"的可见差距。**
若落地后属性差仍不足，需要动的**不是** `ATTR_WEIGHT`，而是：

1. 让 `angleBonus` / `P_MIN` **只对高属性球员生效**（避免拉平低位球员）；
2. 或让 `beatenUntil` 的**时长**也随属性缩放（"过得更彻底"）；
3. 或接受一个更小的差距（**但必须在设计阶段就写明目标，不能事后调**）。

**设计取舍（写清理由，便于评审）**：
- **不直接换手**：失败 ⇒ 只是"没过去"，球还在脚下。若直接换手，等于把抢断系统重做一遍。
- **给防守者 `beatenUntil` 失位窗口**：这是"过掉了"的**真实后果**，也是唯一能让
  `dribbling` 传导到终局指标（多打一人、传中空当）的通道。
- **冷却是必需的**：否则每 tick 都会掷骰，退化成"高频重试"（与抢断的
  `tackleCdUntil` 同理）。

### 2.5 事件契约（新增 `beat`）

```js
this._emit("beat", a, { from: opp.id, distance: Number(d.toFixed(2)), angle: ... });
```

- **必须新增**：否则无法在审计里量化"本场过人 N 次"，也无法做标定。
- **审计接入点**：`scripts/match-realism-audit.mjs` 需新增一个统计项
  `beatsPerMatch`（**且必须同时给护栏** —— 见 §5.4，这是上文反复出现的教训）。

## 3. 为什么这**不是**"调权重"（防止走回老路）

已被证否的近似做法，明确排除：

| 做法 | 为什么不行 |
|---|---|
| 提高 `dribble` 权重 | 只改变「何时带球」，不产生「越过对手」事件；`uniform` 档实测已证摆脱率与 `dribbling` 无关 |
| 给 `dribble` 权重去掉 `(1 - pressure*0.55)` | 让球员在高压下更爱带球，但**仍无对抗结算** ⇒ 还是几何副产品 |
| 复用抢断公式反算 | 抢断是防守者发起的单次尝试；反算无法产生"进攻方赢"的事件语义 |

⇒ **必须新增动作 + 新增事件 + 新增结算**，三者缺一不可。

## 4. 影响面评估（改之前必须列清）

| 系统 | 是否受影响 | 说明 |
|---|---|---|
| 传球选择/落点 | ⚠ **间接** | 新增动作选项会**挤占** `pass`/`dribble` 的 softmax 份额 ⇒ 传球数可能下降 |
| 越位 | ⚠ **间接** | 突破成功 ⇒ 更靠近球门 ⇒ 越位风险变化 |
| 抢断 | ⚠ **间接** | 突破失败 ⇒ 防守者更贴近 ⇒ 抢断窗口更易打开 |
| 进球/射门 | ⚠ **间接** | `beatenUntil` 失位 ⇒ 空当 ⇒ 传导路径（这正是要验证的） |
| boxSec | ⚠ **间接** | 更靠前的带球 ⇒ 进禁区时间可能增加（**注意 850 护栏已判为不可判**） |
| **标准档基线** | ⚠ **会动** | 新增动作会改变**所有**比赛的决策分布 ⇒ `STANDARD_PROFILE_REFERENCE_24` **须整体重标定** |

⚠ **最后一条是最重要的成本**：这不是"只影响差异档"的改动 ——
**它在 uniform 档也会改变行为**（因为 `beat` 选项对所有球员都入池，
只是权重不同）。所以**必须重跑全部 24 场基线审计**。

### 4.1 落地方式（**用户已拍板：默认关闭的可选行为**）

针对上面那条成本，**有一条约零成本的路径**。核实结果：

引擎**已有**现成的档位机制，**不需要发明新东西**：

| 机制 | 位置 | 现状 |
|---|---|---|
| `opts.simulationProfile` | `engine.js:471`（默认 `"standard"`） | ✅ 已存在，已在 5 处分支（`:1565/:1589/:1624/:5227/:7934`） |
| `opts.separationMinDistanceUnits` | `engine.js:474-481` | ✅ **先例**：注释明写"参数化只为让标定探针能扫它，**默认值不要在别处改**" |

⇒ **`beat` 应做成同一型的开关**：`opts.beatPrimitive`（默认 `false`）。

**这样做的效果**：
- 标准档下 `beatPrimitive = false` ⇒ **`beat` 选项根本不入池** ⇒
  决策分布**逐位不变** ⇒ `STANDARD_PROFILE_REFERENCE_24` **无需重标定**，
  `verify.mjs` 应逐位通过，boxSec/直塞/越位三条**无需复核**。
- 探针/审计**显式开启**该开关 ⇒ `beat` 事件流真实产生 ⇒
  **§5.5 第 6 项（护栏 SA）当场可测**。

⚠ **必须验证的强断言**：开启开关 vs 关闭开关，在**同种子**下应产生
**逐位相同**的比赛（除了 `beat` 事件本身）。这是"零回归"的**唯一证据**，
必须做成一条自检（与 `_box-seconds-rebaseline-probe.mjs` 的桥接自检同型：
control 与审计逐位相同 679.53/693.30）。

⚠ **代价（如实说明）**：第一版不进标准档 ⇒ **看不到它对终局指标（进球）
的真实影响**。所以这是一个**分两步**的路线：
1. **本 PR**：开关 + `beat` 事件 + SA 测出带宽（**标准档零改动**）
2. **下一 PR**：在开关下拿到完整连带影响读数后，再决定是否开进标准档
   （那时才需要全套重标定，且是**有数据支撑的**决定，不是盲赌）

⇒ 这**恰好回应了 §4 的风险**：把"必然重标定"变成"**有证据后再重标定**"。

## 5. 标定与验收计划（落地前必须全部完成）

### 5.1 探针扩展（先做，不碰引擎）

扩展 `_one-on-one-dribble-probe.mjs`：
- 统计 `beat` 事件数/场（现在应为 0）

### 5.2 主验收指标（定义清楚，避免事后挑指标）

**真实足球基准（已查得，非拍脑袋）** —— 来源：Opta Analyst
《The Definitive Guide to Dribblers》（2023-11-21），五大联赛 2012/13–2022/23 十个赛季：

| 量 | 真实基准 |
|---|---|
| **联赛平均盘带成功率** | **47%（西甲）~ 52%（英超）** |
| **顶级盘带者成功率** | **66% ~ 78%**（Dembélé 78.1%、Verratti 77%、Hazard 63.2%、Messi 58.4%） |
| **场均盘带尝试（双方合计）** | **德甲 34~38 次/场**（2013-14 曾达 ~60，近季 34.3） |
| 高频盘带者门槛 | ≥6 次尝试/90 分钟 |
| 顶级球员成功数/90 分钟 | Traoré 6.1、Doku 5.4、Boufal 4.9、Messi 4.1 |

⇒ **据此换算成引擎口径**（单队、每场）：

| 指标 | 真实基准（单队/场） | 当前引擎值 | 目标 |
|---|---:|---:|---|
| 盘带尝试 | **~17~19**（35~38 的一半） | 无此事件 | 12~20 |
| **成功突破（`beat`）** | **~8~10**（尝试 × ~52%） | **0（不存在）** | **6~12** |
| **突破成功率** | **~47~52%** | — | **40~58%** |
| 顶级 vs 平均 成功率差 | **+20~30pp**（66~78% vs 47~52%） | **0**（实测 0.38× 反向） | **≥ +15pp** |

⚠ **我原先在初稿里拍的"8~20% 摆脱率"是错的**（低于真实基准一半以上）——
真实盘带成功率是 **~50%**，不是 10%。已按外部数据更正。

**主验收指标（单一、明确）**：
> **`beat` 成功率在「`dribbling` 高的球员」与「`dribbling` 低的球员」之间，
> 相差 ≥ 15 个百分点**（对照真实基准的 +20~30pp）。

这个指标的好处：**① 有外部基准可比；② 是差异量（避免整体偏移）；③ 与 §1 的
诊断指标（摆脱率比值）同向。**

### 5.3 需要外部标定的量

1. **`BEAT_STAGGER_SECONDS`**（防守者失位时长）—— **已找到正确做法：
   不引入外部数字，改为复用引擎既有的"失位词汇"。**

   我先按初稿去查外部数据，**结论是查不到**（见 §5.3.1）：公开的足球分析文献里
   "被过后多久归位"**没有任何量化基准**，只有教练术语（"快速回追"）。这类量
   本就极少被单独测量——它需要 tracking data 且定义边界模糊。

   ⇒ 于是转向**引擎内部一致性**：引擎里"防守者失位"已有成熟词汇：

   | 机制 | 现有取值 | 位置 |
   |---|---|---|
   | 下脚抢断者·个人冷却 | `36~50 + rnd*10` s | `engine.js:5966` |
   | 下脚抢断者·全队冷却 | `44 + rnd*10` s | `engine.js:5967` |
   | **被抢断者·追抢冷却** | **`8` s** | `engine.js:6012` |
   | **被抢断者·后撤距离** | **`4` 场单位**（朝己方） | `engine.js:6016` |

   `:6010-6017` 的注释正是这个问题的答案：
   > *"真实里丢球方会先失位、退一步再重新组织逼抢，不会瞬间贴脸抢回。"*

   ⇒ **`BEAT_STAGGER_SECONDS` 不应是新发明，而应是**：被过掉的防守者 =
   一个介于"被抢断者"（8s 冷却 + 后撤 4 单位）与"下脚失败者"（36~50s）之间的尺度。
   建议**初值 8~12s 冷却 + 后撤 4~6 单位**，并在落地后用 §5.5 的复核确认它
   没有制造"贴身乒乓"或"回追瞬移"。

   **理由**：引擎自洽优先于引入一个我查不到来源的外部数字。若未来找到硬数据，
   再替换；在当前证据下，**复用同一套词汇是可辩护的**。

2. **`beatCdUntil` 冷却**：**已在探针侧标定完成**（§6.3 C 组：
   `actionDurationSec: 1.2` + `cooldownSec: 3.0` + 意图门槛 ⇒ **18.4 次/队/场**，
   落在真实 ~17 的带内）。落地时沿用同一组值。
