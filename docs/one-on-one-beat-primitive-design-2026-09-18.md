## 1. 为什么需要新原语（诊断结论回顾）

**实测确证**（`scripts/_one-on-one-dribble-probe.mjs`，12 场，两档）：

| 档位 | 核心摆脱率 | 普通摆脱率 | 比值 | 核心/普通 `dribbling` |
|---|---:|---:|---:|---:|
| tiered（18 vs 9） | **0.5%**（9/1912） | **1.32%**（107/8129） | **0.38×** | **2.00×** |
| uniform（同值 15） | 0.3%（8/2449） | 0.95%（97/10215） | 0.32× | 1.00× |

- **`dribbling` 差 2 倍，摆脱率反而低 0.38 倍 ⇒ 摆脱率与 `dribbling` 完全无关。**
- **uniform 档是决定性反证**：所有属性相同，摆脱率仍有差异 ⇒ 该差异**不来自属性**。
- 现有 1.2% 的"摆脱"是**几何副产品**（防守者移动惯性没跟上 / 抢断冷却 / 球权转移）。

**引擎已有的（不要重复造）**：防守者发起的抢断结算
（`engine.js:5969-6003`，`dribbling+strength` vs `tackling+marking`，
含护球朝向 `shieldAlignment`、相对速度动量 `momentumAdjustment`、犯规判定）。
⇒ **这套公式本身很好，缺的只是"持球者发起"的另一半。**

**缺的具体是什么**：`engine.js:2736-2750` 的 `dribble` 选项只设移动目标：

```js
if (aheadSpace > 0.2 || (isWing && ...)) {
  const burst = 0.6 * a.attr.dribbling + 0.4 * a.attr.pace;
  options.push({
    key: { act: "dribble" },
    w: (0.12 + 0.9 * burst) * spaceW * (1 - pressure * 0.55) * midBoost,
  });
}
```

⇒ 它是「**前方有空当就走**」，权重还随压力**下降**（`1 - pressure*0.55`）。
**没有「我要过掉眼前这个人」这个选项。**

## 2. 原语定义

### 2.1 一句话

> **持球者主动把球带向最近防守者，并按 `dribbling`/`balance` 对抗 `tackling`/`marking`
> 掷一次骰子；赢 ⇒ 该防守者短暂失位（`beat` 事件）；输 ⇒ 球权风险上升（可能被断）。**

关键词：**主动**（持球者发起）、**结算**（按属性掷骰）、**可观测**（`beat` 事件）。

### 2.2 与现有抢断的关系（正交，不重复）

| | 抢断（已有） | 突破（新增） |
|---|---|---|
| 发起方 | 防守者（`press` 职责球员） | **持球者** |
| 触发 | 防守者在 `CONTROL_RADIUS + …` 内 + 冷却到期 | **持球者在决策时选 `beat` 动作** |
| 结算 | `tackling+marking` vs `dribbling+strength` | **`dribbling+balance` vs `tackling+marking`** |
| 结果 | 球**换手** | 防守者**短暂失位**（不换手） |
| 冷却 | `tackleCdUntil`（36~60s 量级） | **`beatCdUntil`（待定，见 §5.3）** |

⇒ 二者**可以连续发生**：突破失败 ⇒ 防守者更贴近 ⇒ 抢断窗口更容易打开。
这正好是真实足球的因果链。

### 2.3 接缝位置（最小侵入）

**唯一改动点**：`_thinkAttackPossession`（约 `engine.js:2690` 的 `options` 构造）里
**新增一个 `beat` 选项**，与 `dribble`/`pass`/`longshot` 并列：

```js
// 新增：主动突破（仅在最近防守者进入可对抗距离、且有空当可越过时入池）
const duel = this._beatDuelCandidate(a);   // 新增 helper，返回 {opp, d, gapY} 或 null
if (duel) {
  const w = this._beatOptionWeight(a, duel, { core, isWing, pressure });
  options.push({ key: { act: "beat", opp: duel.opp }, w });
}
```

**执行分支**（与 `dribble` 并列，约 `engine.js:2801`）：

```js
} else if (choice.act === "beat") {
  this._attemptBeat(a, choice.opp);
}
```

**不碰**：`_pass`、`_shoot`、`_commitOffBallTarget`、`_clampOffside`、
抢断系统、越位系统、事件时间戳逻辑。

### 2.4 结算公式（草案，待标定）

对齐现有抢断公式的形状（`engine.js:5996`），但**表达"进攻方赢"**。
**注意：本原语是两层结构**（第一版只有一层，被实测证否，见 §2.4.1）。

**第一层 —— 意图门槛**（"我这次要不要过他"）：

```js
// 贴身 ≠ 想过人。真实足球在 ~1000 次持球接触里只挑出 ~17 次 take-on。
const intentP = INTENT_BASE + INTENT_PER_DRIBBLING * a.attr.dribbling;
if (this.random() >= intentP) return;   // 本次不尝试
```

**第二层 —— 越过结算**（"过不过得去"）：

```js
// 进攻方能力
const atk = 0.55 * a.attr.dribbling + 0.25 * a.attr.balance + 0.20 * a.attr.pace;
// 防守方能力（与抢断公式同项，权重对齐）
const def = 0.60 * opp.attr.tackling + 0.20 * opp.attr.marking;
// 侧向角：防守者站位偏离持球者前进线越多，越好过
const angleBonus = (dAng / Math.PI) * ANGLE_WEIGHT;
// 协防惩罚：每多一名 8m 内的协防者
const p = clamp(
  BASE + (atk - def) * ATTR_WEIGHT + angleBonus - helpers * HELP_WEIGHT,
  P_MIN,
  P_MAX
);
if (this.random() < p) {
  opp.beatenUntil = this.t + BEAT_STAGGER_SECONDS;   // 防守者失位
  this._emit("beat", a, { from: opp.id, distance: d });
}
```

#### 2.4.1 为什么必须是两层（第一版被证否）

**第一版只做了"冷却 + 结算"**（每次贴身都掷一次，靠冷却限频）。实测：

| 版本 | 单队尝试/场 | 真实基准 | 倍数 |
|---|---:|---:|---:|
| 第一版（仅冷却 4s） | **593.5**（双方 1187） | ~17 | **~35×** |
| 第二版（长度 1.2s + 冷却 3s） | **721.5** | ~17 | **~42×** |
| **加意图门槛后** | **35.4** | ~17 | 2.08× |

⇒ **根因**：引擎里"贴身"是**常态**（实测 53.5% 的持球样本最近对手 ≤3m、
46.8% 落在 2-3m 桶）。任何"贴身即触发"的方案都会**必然**给出比真实高 1~2 个
数量级的频次。**真实足球的 take-on 是有意图的动作**，不是"有人靠近"。
⇒ 故必须有**独立于冷却的意图门槛**，且它本身就是"球员差异"的第一层体现。

#### 2.4.2 `norm()` 压缩：属性差有个先天上限（重要）

引擎的属性在进 agent 前过 `norm()`（`engine.js:347`）：

```js
norm(v) = clamp(0.28 + clamp(v/20, 0.05, 1) * 0.64, 0.3, 0.92)
```

⇒ **`dribbling` 18 vs 9 在引擎里是 0.856 vs 0.568（比值 1.51），不是 2.0。**

这决定了**属性差的理论上限**。代入 §2.4 的公式（防守方 `def ≈ 0.56`）：

- 核心：`p ≈ BASE + (0.856 − 0.56) × W = BASE + 0.296W`
- 普通：`p ≈ BASE + (0.568 − 0.56) × W = BASE + 0.008W`
- ⇒ 理论差 `≈ 0.288W`，要 ≥ 0.15（15pp）需 **`W ≥ 0.52`**

⚠ **但实测达不到这个上限** —— 因为 `P_MIN` 与 `angleBonus` 会把**低位球员的成功率抬起来**，
逼近核心。第一轮扫描（4 场/组）显示 `W` 从 1.35 提到 1.90，属性差只在 **+5~10pp** 徘徊，
且样本小时会剧烈波动（有一组甚至读到 −15pp）。

⇒ **结论：`norm()` 压缩 + `P_MIN` 地板，共同限制了"球星 vs 普通"的可见差距。**
若落地后属性差仍不足，需要动的**不是** `ATTR_WEIGHT`，而是：

1. 让 `angleBonus` / `P_MIN` **只对高属性球员生效**（避免拉平低位球员）；
2. 或让 `beatenUntil` 的**时长**也随属性缩放（"过得更彻底"）；
3. 或接受一个更小的差距（**但必须在设计阶段就写明目标，不能事后调**）。

**设计取舍（写清理由，便于评审）**：
- **不直接换手**：失败 ⇒ 只是"没过去"，球还在脚下。若直接换手，等于把抢断系统重做一遍。
- **给防守者 `beatenUntil` 失位窗口**：这是"过掉了"的**真实后果**，也是唯一能让
  `dribbling` 传导到终局指标（多打一人、传中空当）的通道。
- **冷却是必需的**：否则每 tick 都会掷骰，退化成"高频重试"（与抢断的
  `tackleCdUntil` 同理）。

### 2.5 事件契约（新增 `beat`）

```js
this._emit("beat", a, { from: opp.id, distance: Number(d.toFixed(2)), angle: ... });
```

- **必须新增**：否则无法在审计里量化"本场过人 N 次"，也无法做标定。

## 3. 为什么这**不是**"调权重"（防止走回老路）

已被证否的近似做法，明确排除：

| 做法 | 为什么不行 |
|---|---|
| 提高 `dribble` 权重 | 只改变「何时带球」，不产生「越过对手」事件；`uniform` 档实测已证摆脱率与 `dribbling` 无关 |
| 给 `dribble` 权重去掉 `(1 - pressure*0.55)` | 让球员在高压下更爱带球，但**仍无对抗结算** ⇒ 还是几何副产品 |
| 复用抢断公式反算 | 抢断是防守者发起的单次尝试；反算无法产生"进攻方赢"的事件语义 |

⇒ **必须新增动作 + 新增事件 + 新增结算**，三者缺一不可。

## 4. 影响面评估（改之前必须列清）

| 系统 | 是否受影响 | 说明 |
|---|---|---|
| 传球选择/落点 | ⚠ **间接** | 新增动作选项会**挤占** `pass`/`dribble` 的 softmax 份额 ⇒ 传球数可能下降 |
| 越位 | ⚠ **间接** | 突破成功 ⇒ 更靠近球门 ⇒ 越位风险变化 |
| 抢断 | ⚠ **间接** | 突破失败 ⇒ 防守者更贴近 ⇒ 抢断窗口更易打开 |
| 进球/射门 | ⚠ **间接** | `beatenUntil` 失位 ⇒ 空当 ⇒ 传导路径（这正是要验证的） |
| boxSec | ⚠ **间接** | 更靠前的带球 ⇒ 进禁区时间可能增加（**注意 850 护栏已判为不可判**） |
| **标准档基线** | ⚠ **会动** | 新增动作会改变**所有**比赛的决策分布 ⇒ `STANDARD_PROFILE_REFERENCE_24` **须整体重标定** |

⚠ **最后一条是最重要的成本**：这不是"只影响差异档"的改动 ——
**它在 uniform 档也会改变行为**（因为 `beat` 选项对所有球员都入池，
只是权重不同）。所以**必须重跑全部 24 场基线审计**。

### 4.1 落地方式（**用户已拍板：默认关闭的可选行为**）

针对上面那条成本，**有一条约零成本的路径**。核实结果：

引擎**已有**现成的档位机制，**不需要发明新东西**：

| 机制 | 位置 | 现状 |
|---|---|---|
| `opts.simulationProfile` | `engine.js:471`（默认 `"standard"`） | ✅ 已存在，已在 5 处分支（`:1565/:1589/:1624/:5227/:7934`） |
| `opts.separationMinDistanceUnits` | `engine.js:474-481` | ✅ **先例**：注释明写"参数化只为让标定探针能扫它，**默认值不要在别处改**" |

⇒ **`beat` 应做成同一型的开关**：`opts.beatPrimitive`（默认 `false`）。

**这样做的效果**：
- 标准档下 `beatPrimitive = false` ⇒ **`beat` 选项根本不入池** ⇒
  决策分布**逐位不变** ⇒ `STANDARD_PROFILE_REFERENCE_24` **无需重标定**，
  `verify.mjs` 应逐位通过，boxSec/直塞/越位三条**无需复核**。
- 探针/审计**显式开启**该开关 ⇒ `beat` 事件流真实产生 ⇒
  **§5.5 第 6 项（护栏 SA）当场可测**。

#### 4.1.1 ⚠ 零回归的判据（此处曾写错，已修正 —— 值得记下来）

**初稿写的是**：「开启开关 vs 关闭开关，在同种子下应产生逐位相同的比赛」。

**这是错的，而且在逻辑上不可能。** 打开开关后 `beat` 选项入池，
`weightedPick` 的输入变了 ⇒ 消费随机数的顺序必然改变 ⇒ 行为**本来就该不同**。
把"打开也相同"当判据，等于要求**新功能无效**。

**正确的判据是两条，缺一不可**（已实现在
`scripts/_beat-zero-regression-probe.mjs`）：

| | 断言 | 做法 |
|---|---|---|
| **[A] 默认口径无影响** | `beatPrimitive` **不传**（= 标准档真实调用方式）时，行为与**打补丁前**逐位相同 | `--emit` 子命令在 `git stash` 前后各跑一次，`diff` 必须无输出 |
| **[B] 开关确实生效** | 显式传 `true` 时**必须**真的产生 `beat` 事件，且行为**不再**与默认口径相同 | 自检内置；同时验 `false` 时 `beat` 必须为 0 |

⚠ **[B] 是 [A] 的反假通过保障**：**一个永远不生效的开关，当然能轻松通过"零回归"。**
所以必须同时证明"关掉无影响"和"打开有影响" —— 单独任一条都不是证据。

✅ **本条已于 2026-09-18 深夜实测通过**（见 §7.4）：
- `[A]` 补丁前后 3 场种子，22 名球员的 `x/y/vx` + 球位 + 全部事件计数**逐位相同**
- `[B]` 关闭时 `beat` = 0；打开时确有 `beat` 事件且行为改变

⚠ **代价（如实说明）**：第一版不进标准档 ⇒ **看不到它对终局指标（进球）
的真实影响**。所以这是一个**分两步**的路线：
1. **本 PR**：开关 + `beat` 事件 + SA 测出带宽（**标准档零改动**）
2. **下一 PR**：在开关下拿到完整连带影响读数后，再决定是否开进标准档
   （那时才需要全套重标定，且是**有数据支撑的**决定，不是盲赌）

⇒ 这**恰好回应了 §4 的风险**：把"必然重标定"变成"**有证据后再重标定**"。

## 5. 标定与验收计划（落地前必须全部完成）

### 5.1 探针扩展（先做，不碰引擎）

扩展 `_one-on-one-dribble-probe.mjs`：
- 统计 `beat` 事件数/场（现在应为 0）
- 按 `dribbling` 分桶统计摆脱率（现在应无相关）
- **加入"摆脱率 vs `dribbling` 差"的相关系数**（作为新原语的**主验收指标**）

### 5.2 主验收指标（定义清楚，避免事后挑指标）

**真实足球基准（已查得，非拍脑袋）** —— 来源：Opta Analyst
《The Definitive Guide to Dribblers》（2023-11-21），五大联赛 2012/13–2022/23 十个赛季：

| 量 | 真实基准 |
|---|---|
| **联赛平均盘带成功率** | **47%（西甲）~ 52%（英超）** |
| **顶级盘带者成功率** | **66% ~ 78%**（Dembélé 78.1%、Verratti 77%、Hazard 63.2%、Messi 58.4%） |
| **场均盘带尝试（双方合计）** | **德甲 34~38 次/场**（2013-14 曾达 ~60，近季 34.3） |
| 高频盘带者门槛 | ≥6 次尝试/90 分钟 |
| 顶级球员成功数/90 分钟 | Traoré 6.1、Doku 5.4、Boufal 4.9、Messi 4.1 |

⇒ **据此换算成引擎口径**（单队、每场）：

| 指标 | 真实基准（单队/场） | 当前引擎值 | 目标 |
|---|---:|---:|---|
| 盘带尝试 | **~17~19**（35~38 的一半） | 无此事件 | 12~20 |
| **成功突破（`beat`）** | **~8~10**（尝试 × ~52%） | **0（不存在）** | **6~12** |
| **突破成功率** | **~47~52%** | — | **40~58%** |
| 顶级 vs 平均 成功率差 | **+20~30pp**（66~78% vs 47~52%） | **0**（实测 0.38× 反向） | **≥ +15pp** |

⚠ **我原先在初稿里拍的"8~20% 摆脱率"是错的**（低于真实基准一半以上）——
真实盘带成功率是 **~50%**，不是 10%。已按外部数据更正。

**主验收指标（单一、明确）**：
> **`beat` 成功率在「`dribbling` 高的球员」与「`dribbling` 低的球员」之间，
> 相差 ≥ 15 个百分点**（对照真实基准的 +20~30pp）。

这个指标的好处：**① 有外部基准可比；② 是差异量（避免整体偏移）；③ 与 §1 的
诊断指标（摆脱率比值）同向。**

### 5.3 需要外部标定的量

1. **`BEAT_STAGGER_SECONDS`**（防守者失位时长）—— **已找到正确做法：
   不引入外部数字，改为复用引擎既有的"失位词汇"。**

   我先按初稿去查外部数据，**结论是查不到**（见 §5.3.1）：公开的足球分析文献里
   "被过后多久归位"**没有任何量化基准**，只有教练术语（"快速回追"）。这类量
   本就极少被单独测量——它需要 tracking data 且定义边界模糊。

   ⇒ 于是转向**引擎内部一致性**：引擎里"防守者失位"已有成熟词汇：

   | 机制 | 现有取值 | 位置 |
   |---|---|---|
   | 下脚抢断者·个人冷却 | `36~50 + rnd*10` s | `engine.js:5966` |
   | 下脚抢断者·全队冷却 | `44 + rnd*10` s | `engine.js:5967` |
   | **被抢断者·追抢冷却** | **`8` s** | `engine.js:6012` |

> 且不是由我某个测量口径错误造成的。

**为什么探针的尝试数天生偏大（它是上界，不是目标）**
（`scripts/_beat-counterfactual-probe.mjs:185-202`）：

- 探针**每 0.1s 采样一次**（`SAMPLE_INTERVAL = 0.1`，`:31`），
  每个采样点只要"贴身 + 不在冷却"就掷一次意图门槛；
- 引擎里 `beat` 只是 `_decideOnBall` 的**一个候选动作**，
  **只有被 `weightedPick` 选中**才会调用 `_attemptBeat`。

⇒ 大量"探针会计数的采样点"在引擎里**从未成为一次动作选择**。
**两者的分母不同构，不可直接比。**

#### ⚠️ 两侧通过率是否同构（**待验证，未定论**）

用探针归档反推"通过冷却的贴身样本"：

| 量 | 探针（0.1s 采样） | 引擎（每决策点一动作） |
|---|---:|---:|
| 通过冷却的贴身样本（**反推，见下**） | ~1431/场（双方）？ | **202.7**/场（单队） |
| 意图通过 | 36.75（双方）＝ **18.4**（单队） | **3.67**（单队） |
| 通过率 | ~2.57%？ | **1.81%** |

⚠️ **但上面的 1431 是"除以 30（冷却期 3s ÷ 0.1s）"反推的，自检不过**：
`blockedByCooldown ÷ 30 = 522/场`，而"从意图门槛进入的冷却触发"是 1431/场，
**比值仅 0.36**。原因是 `blockedByCooldown` 只记**贴身时**的冷却采样点，
冷却期内球员跑开就不再计入 ⇒ **1431 是高估**。

⇒ **"两侧通过率同构"这个结论证据不足，暂作为待验证项。**
**唯一确定的是**：`intentP ≈ 0.022~0.031` 在引擎侧如实生效（实测 3.19% 通过率，
略高于门槛是因为 `attempts` 含复检后的二次损耗）。

**这不影响下方的缺口量化** —— 缺口是用**引擎侧自己的读数 vs 真实基准**算的，
不依赖探针的通过率。

#### 🎯 缺口的量化（第 5 步的输入，**已算清**）

> **这是 §6.4 系列的结论所在。** 上方的插桩方法论与口径修正都是为了得到这张表。

引擎侧完整分解（单队/场，6 场汇总，`.tmp-bottleneck.mjs`）：

| 环节 | /场 | 占比 |
|---|---:|---:|
| 进 `_attemptBeat`（被选中） | 202.7 | 100% |
| ⇒ 意图通过（**≈ 真正发起尝试**） | **6.5** | **3.19%** |
| 　⇒ 成功产出 `beat` | **3.67** | 1.81% |
| 　⇒ 复检/结算失败 | 2.8 | 1.4% |

**对照真实基准**：

| 量 | 真实基准（单队） | 引擎现状 | 缺口 |
|---|---:|---:|---:|
| 发起尝试 | **~17~19/场** | **6.5/场** | **2.6×** |
| 成功 `beat` | **~8~10/场** | **3.67/场** | **2.2~2.7×** |

⇒ **两个缺口一致（都 ~2.6×）** ⇒ 说明这是**单一原因**（尝试数不足），
**不是**成功率偏低。**这是好消息**：修一处即可。

**要做到 17 次尝试/场，需要**：

```
意图通过率： 3.19%  →  8.39%   （需 ×2.6）
⇒ intentP：  ~0.031  →  ~0.081
⇒ INTENT_PER_DRIBBLING： 0.030  →  ~0.110
```

⚠️ **但这只是"频次"一维的解。`intentP` 同时影响成功率与核心/普通差异**
（因为核心球员 `dribbling` 归一后更高，通过率差异会放大）⇒
**必须用 `_beat-param-sweep.mjs` 重扫三项判据，不能只按频次调。**

**两个处理方向（第 5 步定，不现在定）**：

| 方向 | 做法 | 代价 |
|---|---|---|
| **(A) 调高 `intentP` ~2.6×** | 让尝试数达 ~17/场 | **改变成功率与核心/普通差异** ⇒ 重扫 + 重跑 24 场复核 |
| **(B) 接受 6.5/场** | 承认引擎动作频率天然低于采样频率 | 需明确论证"6.5 次尝试已足够体现属性差" | 

⚠️ **不建议**按 §6.4.1 的 (a) 提高入池权重 —— 202.7 已经足够多，**权重无助于过门槛**。

#### 当前的已知量级（据此定位瓶颈）

- 被选中 **202.7/场**，产出 **3.67/场** ⇒ 第二层总通过率 **1.81%**；
- **意图拦截 199.0/场、意图通过 3.67/场**（干净读数已补齐）⇒ 通过率 **1.81%**。

**⚠ 一个我自己犯过的算错（记录以免重犯）**：我曾用
`intentP = 0.005 + 0.03 × 18 = 0.545` 算出"若意图门槛单独生效应有 ~40% 通过"，
据此一度判断"意图门槛不是瓶颈"。**这是错的。**

**`a.attr.dribbling` 在引擎里是已归一化的值**（`norm()`，`engine.js:385-390`）：
```
dribbling 18 → norm = 0.28 + (18/20)×0.64 = 0.856
dribbling 11 → norm = 0.632
dribbling  9 → norm = 0.568
```
⇒ 真实门槛是 **`intentP` 核心 0.0307 / 普通 0.0220**，
**与实测通过率 1.81% 完全吻合**（略低于门槛，因为还有复检/结算的二次损耗）。

⇒ **结论回到最初判断：意图门槛就是唯一瓶颈，且它是"乘积式"的**
（`:1211` 每次调用都掷，通过率仅 ~2.2~3.1%）。

**出口分解（`.tmp-bottleneck.mjs`，6 场汇总，`/场`）** —— 三个数**完全闭环**：

| 出口 | /场 | 占比 | 判读 |
|---|---:|---:|---|
| 进入 `_attemptBeat` | **202.7** | 100% | — |
| 　意图门槛拦下（`:1211`） | **196.2** | **96.8%** | 🔴 **唯一瓶颈** |
| 　复检/结算失败（`:1219` + 结算） | 2.8 | 1.4% | 可忽略 |
| 　**成功产出 `beat`** | **3.67** | **1.8%** | 202.7 = 196.2 + 2.8 + 3.67 ✓ |

⇒ **复检失败（`duel.opponent !== opp`）不是问题**（仅 1.4%），
**不需要**动 `:1218` 的重取逻辑。**只需调 `intentP`。**

> **可控杠杆**：`INTENT_BASE` / `INTENT_PER_DRIBBLING`。要把通过率从 ~1.8%
> 提到目标量级，需提高约 **4~5 倍**（即 `INTENT_PER_DRIBBLING` 由 0.03 → ~0.12~0.15，
> 或把门槛改成对 `dribbling` 更敏感的形式）。
> **但改它必然改变成功率与核心/普通差异** ⇒ **必须回到
> `_beat-param-sweep.mjs` 重扫，不能手调**。这正是第 5 步 SA 标定的内容。

⇒ **主因是"意图门槛 × 3 秒冷却"的乘积效应，不是 softmax 竞争。**
softmax 竞争只造成 722→202 的收窄，而**探针侧本来也没打算让每个几何命中都尝试**。

**这意味着修法与 §6.4.1 的结论相反**：

| 修法 | §6.4.1 的判断 | 干净读数下的判断 |
|---|---|---|
| **(a) 提高入池权重** | "唯一可走" | **无用** —— 被选中的已经有 202.7 次，权重再高也过不了意图门槛 |
| **(b) 提高 `intentP`** | "方向反了" | **方向对，且是唯一杠杆** —— 但它要**数值上**提高 `INTENT_BASE`/`INTENT_PER_DRIBBLING`，不是"抬门槛" |

⚠️ 注意 (b) 的措辞：§6.4.1 说"抬门槛只会更少"是把 `intentP` 当成**上界筛选**了；
实际上 `intentP` 是**尝试概率**（`:1211` 是 `random() >= intentP` 就放弃），
**调高它 = 更愿意尝试 = `beat` 更多**。**§6.4.1 的方向判断是错的。**

**结论**：杠杆是 `INTENT_BASE`/`INTENT_PER_DRIBBLING`（§6.4.3 已量化为 **~2.6×**，
即 `INTENT_PER_DRIBBLING` 0.030 → ~0.110），**但这不是"照着数字改"** ——
它会**直接改变成功率与核心/普通差异** ⇒ 必须扫描 **三项判据**（频次/成功率/属性差），
不能只按频次调。**这正是第 5 步 SA 标定的内容。**

### 7.5 ✅ 第 5~6 步：护栏带宽测定与定值（2026-09-19）

| 3/场 | 5 |

⇒ **24 场规模只能判「大幅消失 / 大幅爆表」，判不了 1/场 级偏移。**
护栏因此定 ±1.25（≈±2SE）而非更窄 —— 更窄的红线在 24 场下会被普通噪声顶破，
那不是判决，是掷硬币。**这一点必须写在护栏旁边**，否则后来者会误以为它更灵敏。

**护栏落地**：`scripts/beat-guardrail-audit.mjs`（已注册进 `verify.mjs`）。
默认 24 场，自己显式打开开关跑（原语默认关闭，否则读数恒 0 会顶破下沿）。
**读数**：24 场 **3.625** beats/场，落在 `[2.68, 5.18]` 内（距基线 −0.305）。
**反假通过已验**：把上沿压到 1.0 ⇒ `EXIT=1` 且打印具体越界信息；恢复后转绿。

**归档**：`docs/measurements/probe-beat-guardrail-noise-2026-09-19.txt`。

### 7.6 ✅ 2026-09-20：开进标准档的前置「给进球补护栏」已闭环（探针口径侧）

上一节把「先给『进球』补护栏」写为开进标准档的**真正前置**。本条记录它已完成，
**并纠正了原计划里的一个错误做法**。

**原计划**（§7.3 与 AGENTS「进球护栏只有一种口径」的长程动作）：
> 按 v251/v252/今日**三点** 2.35~2.50 定带。

🔴 **这个做法本身就是本仓反复吃亏的那个坑**（AGENTS.md「护栏纪律」：
带宽必须由实测批间 SD 决定，不许拍脑袋）。三点定带会给出 `[2.2, 2.7]`，
**半边只有 0.25**，而它**从没人验过相对噪声有多宽**。

**实际做法**（改为先测噪声）：
新探针 `scripts/_goals-noise-calibration-probe.mjs`，逐字沿用
`_beat-noise-calibration-probe.mjs` / `_box-seconds-rebaseline-probe.mjs noise`
的**方法型**（N 批互不重叠种子窗口 × 批内 m 场，先测批间 SD，再按 2SE 定带宽）。
8 批 × 12 场 = 96 场，种子 372000..372095，能力 15、双方同构（探针口径）：

| 量 | 读数 |
|---|---:|
| 进球/场 基线（双方合计） | **2.854** |
| 逐场 SD `SD_match` | **1.583**（单场 0~8，长尾，零球场占 4.2%） |
| 批间 SD `SD_batch`（12 场/批） | **0.471**（批内均值 2.000~3.583，极差 1.583） |

带宽推导（不手调）：
```
读数 ±2SE（12 场批）= 2 × SD_batch = 0.942
半边 = max(0.942, 工程下限 0.25) = 0.95（向上取到 0.05 的整数倍）
band = [2.854 − 0.95, 2.854 + 0.95] = [1.90, 3.80]
```

🔴 **关键发现：三点原方案给出的 `[2.2, 2.7]`（半边 0.25）比实测噪声窄 3.8×。**
它过去"没报警"只是因为那几次读数恰好落在 2.35~2.50 —— **纯属运气**。
只要有任意一次 12 场读数漂到 2.8 或 2.1，它就会误报。
**这是 boxSec `850` / 直塞 `[0.5, 12]` 的同型复发，本次已修。**

**落地**：`_final-third-movement-calibration-probe.mjs` 的
`PROBE_BAND.goals`：`[2.2, 2.7]`（软标注）→ `[1.90, 3.80]`（96 场噪声标定）。
旧值保留为 `goalsLegacySoft` 仅作留档，**不再参与判定**。
打印文案里的「软标注 / 历史值域」措辞一并改为「护栏」。

**归档**：`docs/measurements/probe-goals-noise-calibration-2026-09-20.txt`。

⚠ **判决力边界（必须连同护栏一起读）**：`SD_match = 1.583` ⇒ 判 1 球/场 需
~21 场/组、判 0.5 球/场 需 **~81 场/组**。而 `_final-third` 探针默认只跑 **6 场**
⇒ **它连 1 球/场的效应都判不了**。本带的定位是
**「防大幅回归」的红线，不是「能判 0.5 球」的仪器**。

⚠ **口径边界**：本条只补了**探针口径**。审计口径的 `[2.5, 3.3]`
（`match-realism-audit.mjs`，能力 13、含强弱、24 场）**早已存在且未动**。
两口径各自有带，**不可互相判定**。

`beat` 对「进球」的**影响方向**要等 §5.5 表 1~6 的完整重标定跑完才有数据
