# 审计口径缺陷：角球后窗口被跨场残留反转成「≥18 秒前的角球」（2026-09-17）

**状态**：已修，已验收。**引擎源码一行未改**（唯一改动在审计脚本 `scripts/match-realism-audit.mjs`）。
**缓存不用升**（`sw.js` / `index.html` / `js/main.js` 均未动）。

---

## 1. 结论先说

`match-realism-audit.mjs` 的 `cornerShots` / `cornerGoals` **测的不是「角球后 18 秒内」**，
而是「**上一次记录到的角球之后、含大量在它之前发生的事件**」。后台 24 场实测：

| 口径 | cornerShots 每场 | 占全部射门 | cornerGoals 每场 | 占全部进球 |
|---|---:|---:|---:|---:|
| **修复前（仓库里的口径）** | **8.83** | **34.87%** | **1.21** | **44.62%** |
| **修复后（真正的 18 秒窗口）** | **1.17** | **4.61%** | **0.17** | **6.15%** |
| 倍率 | **7.57×** | | **7.12×** | |

**34.9% 的射门、44.6% 的进球**曾被判为「角球后」。**86.3% 的被误计射门，
其比赛时间早于那条被引用的角球时刻**——判据不是「放宽」了，是**方向反了**。

⚠️ **这不是统计口径的灰度问题，是方向性问题**：修完之后**没有一件既有的结论需要推翻**，
但「角球还原度」这条线的**全部现状数字此前是用一把坏尺量的**。

## 2. 根因

`scripts/match-realism-audit.mjs` 的三行（修复前的行号 251 / 272 / 286 / 300）：

```js
for (let match = 0; match < matches; match++) {   // ← 每场循环
  ...
  const recentShots = [];
  const recentCorners = { home: -Infinity, away: -Infinity };   // ⚠ 在循环**内**（见下）
  for (const event of engine.events) {
    ...
    if (event.t - recentCorners[event.team] <= 18) totals.cornerShots++;
    ...
    if (event.t - recentCorners[event.team] <= 18) totals.cornerGoals++;
    ...
    else if (event.type === "corner") {
      totals.corners++;
      recentCorners[event.team] = event.t;
    }
```

关键事实链：

1. **`event.t` 每场从 0 重新计**。`engine.js:5034` 的 `_emit` 写 `t: this.t + (this._emitTimeOffset || 0)`，
   而 `this.t` 是**本场的比赛秒**。一场 90 分钟的比赛，事件时间落在 `[0, 5400]`。
2. `recentCorners[team]` 一旦被写入，就**只增不减**，取值是「最近一次角球的比赛秒」。
3. 判据是 `event.t - recentCorners[team] <= 18`。若这一项在**本场没有更早的角球**时被求值，
   它读到的是别处的读数。
4. **原实现把 `recentCorners` 声明在 `for (match)` 之外**（这是历史形态；本次修复把它移进循环），
   于是第 2 场起它仍持有**上一场**最后一次角球的 `t`（实测约 2700）。
   本场事件 `t ∈ [0, 2700]` → `t - 2700 ∈ [-2700, 0]` → **全部 ≤ 18 成立** → 全部被计。

**判据语义因此变成了「在某个未来的角球之前」**——一个时间上的反因果条件。
这也解释了为什么它**看起来一直"有效"**：它总是返回一个非零的数，且随比赛量线性增长
（`cornerShots ≈ 0.35 × shots`），从不报错、从不触发护栏空转。

## 3. 证据

新增诊断探针 `scripts/_corner-window-audit-check.mjs`。它**不建统计模型**，
而是在**同一批比赛**上并排跑两套计数：

- **A 路**：逐字复刻仓库里的判据（含跨场残留）。
- **B 路**：每场一份干净状态（正确口径）。
- **C 路**：只统计「事件时间早于被引用的角球时刻」的射门数——**污染指纹**。

引擎构造（种子 `165000+match`、能力 13、4-3-3、`timeScale`/`separationPasses`）
与 `match-realism-audit.mjs` **逐字相同**，因此 A 路读数必须与审计自己的输出相等——**它确实相等**：

```
审计脚本自己输出（8 场后台）：  corners 3.75  cornerShots 0.88  cornerGoals 0.13
探针 B 路（8 场后台）：         corners 3.75  cornerShots 0.88  cornerGoals 0.13
```

**A 路在 8 场读到 8.00/场、在 24 场读到 8.83/场**——即「探针 A 路 ≈ 审计修复前的报告值」。
`/tmp/mra-orig.mjs`（未打补丁的原版）与修复版在**同一命令下输出逐位相同**
（都是 `goals 2.25 / corners 3.75 / cornerShots 0.88 / cornerGoals 0.13`），
证明补丁**不改变任何聚合结果**，只改变角球三项的口径。

复现：

```bash
node scripts/_corner-window-audit-check.mjs --matches 24            # 后台档
node scripts/_corner-window-audit-check.mjs --matches 24 --profile standard
```

## 4. 为什么以前没被发现（三条，都值得记）

1. **`cornerShots` 的护栏只设了下限**：`match-realism-audit.mjs:464`
   是 `cornerShots >= 0.5`。一个**系统性偏大的**读数永远满足下限，**永远不会报红**。
   与 `goals`（有上下界）不同，这条断言对口径错误**结构性失明**。
2. **它从不产生"空转"信号**。一个恒为 0 的量会立刻暴露；一个总是非零、且随规模线性增长的量
   看起来完全正常。
3. **`cornerShots` 不在冻结参考快照里**。`STANDARD_PROFILE_REFERENCE_24` 九项
   （goals / shots / passes / passCompletionPct / fouls / openGoalShots /
   goalkeeperClaims / goalkeeperChallenges / strongPointsPerMatch）**不含角球三项**，
   所以标准档的「快照自查」也不会碰它。

⚠️ **推论（比本次缺陷本身更重要）**：**凡「只设单侧边界的护栏」+「不在快照里」+「量级随样本线性」的量，
都需要一次独立的口径对账**，不能靠护栏红了才发现。
本次是靠**读代码**发现的，不是靠审计报红。

## 5. 这次修复**没有**推翻任何既有结论——但改变了这条线的"现状基线"

`AGENTS.md`「🅰️ 角球真实参照值总表」第五节那张差距分解表，用的正是这两个量：

| 指标 | 文档里的引擎值 | 文档里的真实值 | 文档比值 |
|---|---:|---:|---:|
| 角球 每队每场 | 3.02 | 5.14 | 59% |
| 每个角球产生射门 | 24.8% | 38.5% | 64% |
| 每个角球产生进球 | 2.15% | 4.1% | 52% |
| 角球进球占全部进球 | 4.5% | 9.8~14.2% | 约 1/3 |

**结构结论全部仍然成立**：

- 「数量只有真实 59%」用的是 `corners` 事件数——**那条计数是对的**，未受影响。
- 「只修一半到不了」是把数量比与威胁比相乘得到的——**乘法关系与分母无关**。
- `0.59 × 0.52 ≈ 0.31` 对上「4.5% vs 13.9% 的 32%」——两处都仰赖**角球进球占全部进球**这一比值，
  而它的分子分母在修复前后**同比缩小**（1.21→0.17、总进球不变），比值本身对口径不敏感。

**但"现状"的绝对值要按新口径重读**（后台 24 场，本次实测）：

| 指标 | 修复后引擎值 | 真实值 | 比值 |
|---|---:|---:|---:|
| 角球 每队每场 | **2.33** | 5.14 | **45%** |
| 每个角球产生射门 | 4.61% ÷ (4.67/2) = **1.97%** | 38.5% | **5.1%** |
| 每个角球产生进球 | 6.15% ÷ 2.335 = **2.63%** | 4.1% | **64%** |

⚠️ **这里出现了一个必须由下一个接手者判定的矛盾**：新口径下
**「每角球射门率」只有真实的 5.1%**，而**「每角球进球率」却是真实的 64%**——
两者不可能同时成立，除非**射门事件与进球事件在这 18 秒窗口里被记到了不同的角落**
（最可能：进球事件带 `t + _emitTimeOffset` 偏移，落在窗口外，而它对应的射门在窗内，或反之）。
**在把这个矛盾查清之前，不要把上面这三行当标定基准用。** 本次只负责把口径修正并留证。

## 6. 修复内容

`scripts/match-realism-audit.mjs`，18 行增 / 3 行改，**全部集中在角球窗口这一处**：

1. `recentCorners` 保留在每场循环内（原本就在），**加注释说明为什么必须在那里**。
2. 新增 3 行 helper，把判据**单向化**：

```js
const cornerAfter = (event, window) =>
  event.t - recentCorners[event.team] >= 0 &&
  event.t - recentCorners[event.team] <= window;
```

3. 两处判据改成 `if (cornerAfter(event, 18))`。

**为什么是「单向化」而不是「换 kNN」**：单向化把语义钉死为「事件之前发生过、且 ≤18s 内」，
与意图一致，且**不需要任何新的阈值实测**。做 kNN 会引入「取最近 k 个」这个需要标定的选择，
而现有数据不支持标定它。**够用即止。**

**为什么保留 `recentCorners` 的赋值**：它是 `cornerAfter` 的输入；只是不再对外暴露语义。
（曾考虑删掉赋值并在 helper 里传参，但那会让两处调用点各写一套状态维护，反而更容易错。）

## 8. 给下一个接手者

1. **`cornerShots` / `cornerGoals` 现在才是可用的**。此前所有引用它们的结论
   （含 `AGENTS.md` 第五节）都是坏尺量出来的。**结构结论可用，绝对值要按第 5 节重读。**
2. **第 5 节那个矛盾（射门率 5.1% 对进球率 64%）必须先查清**，
   才能把这两个量接进标定。建议的第一步：把角球后窗口内的**逐事件序列**打出来，
   看进球事件相对其对应射门事件的 `t` 差。
3. **护栏要补双侧**：`cornerShots >= 0.5` 只有下限，对口径错误结构性失明。
   建议加一条上限，取值需要先有干净基线（现在是 1.17/场）。
4. **把 `cornerShots` / `cornerGoals` 纳入冻结参考快照**，否则它们仍然逃过快照自查。
5. 本节的三条通用教训（单侧护栏失明、非零量不暴露口径错、快照之外的量不受保护）
   已同步写入 `~/.workbuddy-ai/skills/sim-change-validation/SKILL.md`。
