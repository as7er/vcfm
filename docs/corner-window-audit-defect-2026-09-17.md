## 2. 根因

> ⚠️ **本节作废，见顶部复查。** 下面描述的第 4 条（「原实现把 `recentCorners` 声明在 `for (match)` 之外」）
> **与仓库事实相反**：它一直在循环内，缩进两格，从未移动。
> 本节的代码块本身就是反证——看第 35 行自己的注释「在循环**内**」，
> 那是我当时已经写上、却没读懂的一句话：**代码在循环内，结论说在循环外。**

`scripts/match-realism-audit.mjs` 的三行（修复前的行号 251 / 272 / 286 / 300）：

```js
for (let match = 0; match < matches; match++) {   // ← 每场循环
  ...
  const recentShots = [];
  const recentCorners = { home: -Infinity, away: -Infinity };   // ⚠ 在循环**内**（见下）
  for (const event of engine.events) {
    ...
    if (event.t - recentCorners[event.team] <= 18) totals.cornerShots++;
    ...
    if (event.t - recentCorners[event.team] <= 18) totals.cornerGoals++;
    ...
    else if (event.type === "corner") {
      totals.corners++;
      recentCorners[event.team] = event.t;
    }
```

关键事实链：

1. **`event.t` 每场从 0 重新计**。`engine.js:5034` 的 `_emit` 写 `t: this.t + (this._emitTimeOffset || 0)`，
   而 `this.t` 是**本场的比赛秒**。一场 90 分钟的比赛，事件时间落在 `[0, 5400]`。
2. `recentCorners[team]` 一旦被写入，就**只增不减**，取值是「最近一次角球的比赛秒」。
3. 判据是 `event.t - recentCorners[team] <= 18`，**缺了 `>= 0` 这一半**——这一条是真的
   （补丁修的就是它），它让「未来被误当过去」成为一个**可能的**失效模式。
4. ~~**原实现把 `recentCorners` 声明在 `for (match)` 之外**~~ —— **错的，已推翻**。
   它一直在循环内，所以第 3 条那个失效模式**从未被激活**：本场内 `recentCorners[team]`
   只可能是**本场已发生**的角球，`delta` 天然落在合法区间，`>= 0` 只是把不变式**写出来**。
   「跨场残留 → `t - 2700 ≤ 18` 恒真 → 86% 误计」是**探针 A 路人为构造**出来的场景。

⚠️ **一句话教训**：我在探针 A 路里把状态提到循环外，本意是「复刻可疑形态」，
结果把**复刻品的读数**当成了**原件的读数**。**A 路与原件从未对账过**——
而恰恰对账就是这一步的验收标准（见 §3、§7）。

## 3. 证据

- **B 路**：每场一份干净状态（正确口径）。

探针 B 路（8 场后台）：         corners 3.75  cornerShots 0.88  cornerGoals 0.13

⇒ **修正后的读法**：这不是「修复前后」的对比，而是「**假想坏形态 vs 真实实现**」的对比。
A 路的 8.83 只说明：**如果**状态真的漏到循环外，就会读到 8.83 —— 一个有用的**反事实**，

## 4. 为什么以前没被发现（三条，都值得记）

> 我改了代码、写了提交信息、写了三份文档，而**没有任何护栏、快照或断言能发现这是错的**，
> 因为**它本来就没有改变任何数字**。发现它的唯一途径是 `git log -p` 反查。

1. **`cornerShots` 的护栏只设了下限**：`match-realism-audit.mjs:464`
   是 `cornerShots >= 0.5`。一个**系统性偏大的**读数永远满足下限，**永远不会报红**。
   与 `goals`（有上下界）不同，这条断言对口径错误**结构性失明**。
   （**这条依然要修**，理由与本文档描述的错误无关：现在基线干净且已知 1.17/场，
   正是补上限的最好时机。见 §8。）
2. **它从不产生"空转"信号**。一个恒为 0 的量会立刻暴露；一个总是非零、且随规模线性增长的量
   看起来完全正常。
3. **`cornerShots` 不在冻结参考快照里**。`STANDARD_PROFILE_REFERENCE_24` 九项
   （goals / shots / passes / passCompletionPct / fouls / openGoalShots /
   goalkeeperClaims / goalkeeperChallenges / strongPointsPerMatch）**不含角球三项**，
   所以标准档的「快照自查」也不会碰它。

⚠️ **推论（修正版）**：**凡「只设单侧边界的护栏」+「不在快照里」+「量级随样本线性」的量，
都需要一次独立的口径对账。**
但本文档补充了更贵的一条：**「结果中性」的改动不等于「正确」的改动。**
因为聚合逐位不变，`referenceDelta` 全零、所有护栏照旧通过——
**一把没被用过的坏尺和一把好尺给出同样的读数，因此没有任何自动化能区分这两次提交。**
结果中性必须由**代码审读**担保，而代码审读的验收标准是**与原件对账**（§3）。

## 5. 这次修复**没有**推翻任何既有结论——但改变了这条线的"现状基线"

`AGENTS.md`「🅰️ 角球真实参照值总表」第五节那张差距分解表，用的正是这两个量：

| 指标 | 文档里的引擎值 | 文档里的真实值 | 文档比值 |
|---|---:|---:|---:|
| 角球 每队每场 | 3.02 | 5.14 | 59% |
| 每个角球产生射门 | 24.8% | 38.5% | 64% |
| 每个角球产生进球 | 2.15% | 4.1% | 52% |
| 角球进球占全部进球 | 4.5% | 9.8~14.2% | 约 1/3 |

**结构结论全部仍然成立**：

- 「数量只有真实 59%」用的是 `corners` 事件数——**那条计数是对的**，未受影响。
- 「只修一半到不了」是把数量比与威胁比相乘得到的——**乘法关系与分母无关**。

  而它的分子分母在修复前后**同比缩小**（1.21→0.17、总进球不变），比值本身对口径不敏感。

**但"现状"的绝对值要按新口径重读**（后台 24 场，本次实测）：

| 指标 | 修复后引擎值 | 真实值 | 比值 |

| 角球 每队每场 | **2.33** | 5.14 | **45%** |
| 每个角球产生射门 | **25.00%**（28 ÷ 112） | 38.5% | **64.9%** |
| 每个角球产生进球 | **3.57%**（4 ÷ 112） | 4.1% | **87.1%** |
| 角球进球占全部进球 | **6.15%**（4 ÷ 65） | 带 **9.8~14.2%** | 约 1/2 |

⚠️ **上表在 `f852070` 的初版里是错的，已更正（2026-09-17 复查）。**
初版把「每个角球产生射门」算成 `4.61% ÷ (4.67/2) = 1.97%`——
那是**百分比除以个数，量纲错了**，得出「射门率只有真实 5.1%」这个假结论，

**实际两者完全自洽**：正确的分母是**角球个数 112**，不是「每场双方合计角球 4.67」。

### 复查：没有矛盾，两个率同向且都接近真实

`scripts/_corner-window-event-trace.mjs`（后台 24 场、种子 `165000..165023`）逐事件对账：

| 项 | 值 |
|---|---:|
| 角球总数 | 112 |

| 角球后 18s 内进球 | **4** → 每个角球 **3.57%** |

## 6. 修复内容

> ⚠️ **本节作废，见顶部复查。** 第 1 条「原本就在循环内」是**对的**；但「加注释说明为什么必须在那里」
> 是我**基于错误结论**写的注释，注释文本本身在描述一个不存在的历史。**注释已重写**（见下）。

`scripts/match-realism-audit.mjs`，18 行增 / 3 行改，**全部集中在角球窗口这一处**：

1. `recentCorners` 留在每场循环内（**它本来就在**），注释改为陈述**不变式**
   而不是叙述**虚构的历史**。
2. 新增 3 行 helper，把判据**单向化**：

```js
const cornerAfter = (event, window) =>
  event.t - recentCorners[event.team] >= 0 &&
  event.t - recentCorners[event.team] <= window;
```

3. 两处判据改成 `if (cornerAfter(event, 18))`。

**为什么是「单向化」而不是「换 kNN」**：单向化把语义钉死为「事件之前发生过、且 ≤18s 内」，
与意图一致，且**不需要任何新的阈值实测**。做 kNN 会引入「取最近 k 个」这个需要标定的选择，
而现有数据不支持标定它。**够用即止。**

**为什么保留 `recentCorners` 的赋值**：它是 `cornerAfter` 的输入；只是不再对外暴露语义。
（曾考虑删掉赋值并在 helper 里传参，但那会让两处调用点各写一套状态维护，反而更容易错。）

**性质**：**结果中性的防御性加固**。它把「状态必须在循环内」这个**隐式不变式**变成
**显式的代码约束**——`delta >= 0` 一旦写上，即使将来有人把声明挪出去，判据也不会静默反转。
**加固本身是对的，错的只是把它记成了「修 bug」。**

   （1.17/场），正是补上限的最好时机——一个未来的口径错误或回归会立刻报红。
4. **把 `cornerShots` / `cornerGoals` 纳入冻结参考快照**，否则它们仍然逃过快照自查。
5. 本节的三条通用教训（单侧护栏失明、非零量不暴露口径错、快照之外的量不受保护）
   已同步写入 `~/.workbuddy-ai/skills/sim-change-validation/SKILL.md`。
   **§9 的三条（复刻品要对账原件、结果中性改动靠审读担保、先证坏再改）也已写入。**
6. ⚠️ **更正也要留档**：初版那条"待查矛盾"是我的**量纲错误**（百分比 ÷ 个数），
   不是引擎缺陷。**报数之前先问一句「这个比值的分母是什么单位」**——

## 9. 本文档本身的教训：「复刻品」不等于「原件」

本文档记录了一次**凭空归因**：我造了一个探针，在 A 路里**故意**把状态提到循环外，
然后把 A 路的读数（8.83）写成了「仓库审计修复前的值」。**仓库审计从未有过那个值。**

它比 §5 的量纲错误更严重，因为**量纲错误只是算错，这次是错在归因**——
我改了一段**本来是对的**代码，并在四个地方（提交信息、本文档、`AGENTS.md`、记忆）
把它记成了「修复一个历史缺陷」。

### 为什么它能通过全部验收

| 通常的验收 | 为什么对它无效 |
|---|---|
| 聚合逐位相同 | ✅ 通过——因为它**本来就没有改变行为** |
| `referenceDelta` 全零 | ✅ 通过——同上 |
| 护栏断言 | ✅ 通过——基线没动 |
| `git diff` 审读 | ✅ 通过——diff 看起来完全合理（加注释、加 helper、单向化） |
| 探针 A/B/C 三路互证 | ✅ 通过——**三路都自洽，但 A 路是个假想物，没人要求它与原件对账** |

**唯一能发现它的是 `git log -p` 反查声明行的历史位置**，而那一步不在任何流程里。

### 三条可迁移的规则

1. **复刻路径必须与原件对账，而不是只与「其他复刻路径」对账。**
   我的探针有 A/B/C 三路互相印证（B 路 = 干净版，C 路 = 污染指纹），
   **但从来没有跑过「审计原件本身」这一路**。三路自洽只证明三路实现一致，
   **不证明它们复刻了仓库里的那一行**。
   ⇒ **新增验收项**：凡「复刻一个可疑形态」的探针，**必须包含一路「原件原样」**，
   并与复刻路径在**同一输入**上比较；不相等就先解释差异，再谈结论。
2. **「结果中性」的改动需要代码审读担保，不能被测试担保。**
   行为不变的改动对所有自动检查**不可见**。⇒ 这类提交的说明必须**能在读代码时被验证**，
   并且**写进注释的那段历史必须是可查证的**（我这次写的注释在描述一个不存在的历史，
   而它旁边就是反证——代码块里我自己写着「在循环**内**」）。
3. **改了别人的代码，先证明「改前是坏的」。**
   本次我先做了修改、再看证据，于是把「修改后的差异」当成了「修改前的缺陷」。
   ⇒ **顺序必须是：先复现原件的行为，再决定要不要改。**
   若复现不出缺陷，**正确的动作是撤回改动**（或降级为纯注释），
   而不是**为改动回头编一个理由**。

**本次的处理**：改动保留（加固本身有价值且无害），但**性质改记为「结果中性的防御性加固」**，
并把四处记录一并更正（`AGENTS.md`、本文档、提交信息的后续说明、记忆）。
