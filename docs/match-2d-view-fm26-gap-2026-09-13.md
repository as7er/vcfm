# 2D 比赛画面：完整性核查与 FM26 差距（2026-09-13）

## 0. 两个不同的问题，必须分开回答

用户问「2D 比赛画面是不是没有 BUG 了」。这个问题实际混了两件不同的事：

| 问题 | 口径 | 本轮结论 |
|---|---|---|
| **A. 画面有没有完整性缺陷**（瞬移、穿模、振荡、重叠、显示偏离） | 阈值判定 | **干净**：整场 3397 帧采样、十类异常全部为 0 |
| **B. 画面像不像 FM26 / 真实足球**（阵型、跑位、比例） | 与外部参照比 | **不像，但差距被上一轮高估**：引擎侧复现后，唯一稳健的差距是**进攻三区纵向被拉长约 60%** |

**A 通过不等于 B 通过。** 运动完整性监控器只判「物理不可能的事有没有发生」，
不判「跑位像不像足球」。34% 的近静止率不是它定义的异常，所以它不会报警。

> **阅读本文必须先看这条警告**：§2.1 那张表里的「覆盖面积 2.2 倍」「横向宽度 1.48 倍」
> 是**录屏估计的伪影**，已被 §2.4 的引擎侧复现推翻。凡引用本文，**只引 §2.4 及以后**。

## 1. A：完整性核查（本轮实测）

### 1.1 修掉了一个真实存在的漏数缺陷

`MotionIntegrityMonitor.auditSummary()` 原先用 `this.history.length` 当「本场累计」，
而 `history` 会被 `maxHistory`（默认 2000）截断；`frames` / `incidents` 又会被
`_trimFrames` 按 12 秒时间窗裁掉。后果：

- `auditSummary().totalIncidents` 在异常多的比赛里会**少报**；
- `status().frames`（被 `main.js:1123 updateMotionCaptureUI` 用作按钮可用性）
  报的是**窗口内**帧数，不是本场帧数。

复现证据 `scripts/_motion-report-probe.mjs`（注入 30 次瞬移、`maxHistory: 20`）：

```
修复前语义：historyRetained 20  →  会被当成 totalIncidents = 20
修复后实测：historyRetained 20, totalIncidents 30, byType.player-teleport 30
```

修复方式：在 `_addIncident` 里累加**不受截断影响**的计数器
（`totals` / `totalsSevere` / `firstAt` / `lastAt` / `totalIncidents` / `framesTotal`），
并新增 `logMotionReport()` 输出按类型分组的表。
**不改任何阈值、不改判定分支、不动引擎。**

### 1.2 整场真浏览器比赛的结论

`node scripts/match-continuity-browser.mjs` 退出 0，证据
`.tmp-continuity/visual-1789321895885/`（新增 `motion-report.json`）：

```
clock 90'   framesDriven 6797   framesSampledTotal 3397   totalIncidents 0
severe 0    warnings 0          byType {}
```

**十类异常（invalid-coordinate / player-teleport / player-acceleration /
player-oscillation / player-target-churn / player-overlap / support-target-crowding /
owner-ball-gap / ball-teleport / display-divergence）全部为 0。**

四条 `console` 与浏览器错误为 0；主裁峰值速度 3.8 m/s 未越限；画布非空、无横向溢出。

### 1.3 这条结论的边界（不要外推）

- **只覆盖阈值内的缺陷。** 阈值本身宽松：球员速度 >12.2 m/s、重叠 <0.55 m 持续 >0.3 s
  才算。合规但难看的跑位不在覆盖范围。
- **一场、一种子。** 是单场证据，不是分布。要变成回归目标需多场扩样。
- **引擎级审计另有一组非零结果**：`scripts/match-motion-integrity-audit.mjs`
  后台档 6 场出现 `player-oscillation` 5 次、`player-target-churn` 4 次（标准档 2 场为 0）。
  这两类**从未被浏览器审计断言过**（它只断言四个 severe 类型），所以属于「有数据、无门禁」。
- `js/matchview-replay.js`（`ReplayManager`/`ReplayUI`）**没有任何运行时入口 import**，
  只有 `scripts/replay-ui-audit.mjs:3`、`module-test.html:178`、`sw.js:60` 预缓存引用它；
  运行时回放走 `matchview.js` 自己的 `replayEvents`（`:8458`）。即
  **`replay-ui-audit` 每次通过，验证的是一段真实应用不执行的代码。**

1. **§2.1 表里的「横向宽度 53.0 m」「覆盖面积 3996 m²（2.2 倍）」在引擎侧复现不出来。**

   不是队形整体变胖，而是被沿球场长向拉长、没有紧凑的 team block。
3. **「重心平移不缺」需要降级**：band 口径下 14.9~15.2 m vs 15.5 m（一致），
   但 role 口径下 19.5~19.6 m vs 15.5 m（高 26%）。**在无法确定 FM26 侧口径前，
   这条不能再说「不缺」**，只能说「band 口径下一致」。
4. 移动差距也复现：速度低 18~21%（视频侧估 30%，略高估）、近静止约 1.95 倍。

**⚠ 最近邻距离这一行不可用于对账。** FM26 的 7.26 m 来自 `cmp4_metrics.py`，
而该脚本 FM 侧只检出 13/22 人——**漏检会让最近邻距离系统性偏大**，
所以 7.26 m 是上偏估计。但引擎侧的精确值本身有意义：
**全场最近邻中位 2.19~2.21 m，正好压在 §3.3 那条 1.94 / 2.99 m 的身体间距下限上**，
而同队最近邻是 3.20 m。也就是说 VCFM 球员不是「散开」，而是**贴着几何下限挤在一起**，
最近的邻居通常是**对手**（贴身盯防）。这与「散」的直觉相反，也再次说明
目测与极值统计都不可靠。

**读法：**

全队长度 **59.85 m**。**实测的 60.0 m 与模板的 59.85 m 几乎相等**——

这与 `AGENTS.md:3105-3107` 的 v238 诊断**逐条对上**：
- v238 记进攻三区 58.9 m、己方 39.5 m、中场 41.9 m（band 口径）；
- 本轮 band 口径复测 83.9 / 35.9 / 38.3 —— **进攻三区对不上**（83.9 vs 58.9），

  即 v238 的 58.9 m 是「**剔门将后的 DEF→ATT 跨度**」，而它写的 39.5/41.9 是同一口径的另两区。
  本轮按 role 口径的进攻三区长度是 63.4 m，与 58.9 m 同量级（差 7.6%）。
- 成因也一致：`_applyExplicitShapeAnchor`（`engine.js:915-936`）在 `:919` 对

  `a.ty = clamp(a.baseY + (b.y - a.baseY) * pull, 3, 97)`、`pull = clamp(1 - d/40, 0, 1) * 0.2`
  （`engine.js:4880-4882`）——**只有 20% 的跟球浮动，没有任何队形压缩或整体平移**。

**结论：唯一稳健、可复现、且成因已定位的差距是「进攻三区纵向被拉长约 60%（63 m vs 30–40 m 估计）」。**
其余（横向 +10~12%、面积 +22%、速度 −18~21%、近静止 ×1.95）都属于
`AGENTS.md:3108` 说的「**边缘偏离不足以单独支撑改动**」。

### 3.3 标记尺寸不是随手定的，它绑在引擎的身体间距上

`js/matchview.js:3411` 注释明说半径要「与模拟层 2.85~3.35 的中心间距匹配」。
而引擎的最小身体间距是**椭圆**（`js/sim/engine.js:103-121`）：

- 横向（沿边线） `2.85 × 0.68 = 1.94 m`
- 纵向（沿球门方向） `2.85 × 1.05 = 2.99 m`

对照标记直径 3.37~3.54 m：**横向相邻两人合法间距 1.94 m，标记直径是它的 1.7~1.8 倍**，
纵向 2.99 m 时也略重叠。也就是说「标记会重叠」是当前参数下的必然结果，
`matchview.js:3411` 那句「旧半径 9px 会让直径大于碰撞距离」的意图在纵向成立、横向不成立。

### 3.4 这个间距下限是载荷，不是笔误

`engine.js:109-120` 记着两组实测：

- 压成各向同性 **1.94 m**：进球 **2.29**（护栏 2.5~3.3）、转化率 **7.9%**（护栏 9~15）、
  直塞 **0.25**（下限 0.5）——纵向下限从 2.99 掉到 1.94，防守者能坐进纵向传球线，
  进攻产出整条塌掉。
- 压成 **1.10 m**：进球 3.04、转化 10.8% 都好看，但**强弱分离塌了**：
  强队 1.79 → **1.29** 分/场、净胜球 +12 → **−4**。身体能贴到 1.1 m 时，
  弱队光靠贴身就能捂住强队。

结论原文：**「引擎的进攻产出依赖纵向那 2.99m，而贴身防守被同一个数挡着」**
（实测最近防守者距离中位 2.76~2.83 m 正好压在 2.99 m 上）。**要动必须成对动。**

### 3.5 项目已经踩过并纠正过「为画面改物理」

`engine.js:5167-5171` 记录：禁区内曾把间距下限从 2.85 提到 3.35 场地单位
（沿球门方向合 3.52 m），**动机就是让 2D 画面小禁区的圆点不糊成一团**。
代价是后卫在禁区内物理上无法贴身（战术目标只要求离球 3.05 m，几何下限 3.52 m，取大）。
已纠正，并写下原则：**「身体半径不会因为球进了禁区就变大，这里统一用同一个下限；
圆点是否重叠是渲染层的事。」** 这与 `AGENTS.md` 的最高设计原则一致。

### 3.6 另一处已知不一致

引擎球门 `GOAL_X0 44`~`GOAL_X1 56` = 12 格 × 0.68 = **8.16 m**，真实 7.32 m，
**宽 11.5%**。渲染已按引擎真值画（`css/style.css` 球门 `left:44%;width:12%`），
所以画面与引擎一致，但两者一起偏离真实。

## 4. 结论：为什么改渲染层到不了 FM26

按 §2.4 / §2.5 的引擎侧复现，**唯一稳健、可复现、且成因已定位**的差距是
**进攻三区纵向被拉长**（63 m vs 30–40 m 估计，或 DEF→ATT 跨度 60 m）。
其余两项（速度低 18~21%、近静止 ×1.95）复现稳定但属边缘偏离，成因与它同源：

| 症状 | 成因层 | 位置 |
|---|---|---|
| **进攻三区队形被拉成 60~63 m**（静态模板 59.85 m） | **中卫线纵向目标是常量** `baseY + dir*7`（→33.6 m），无球位项 | `_chooseAttackOffBallTarget` `engine.js:3788-3793` / `:4019` |
| 近静止 31.8%（FM26 16.2%） | 目标点本来就近（已证明 96.3% <1.5 m） | 同上（`engine.js:3734`） |
| 速度中位低 18~21% | 同上：不是走不快，是没被指派更远的跑位 | 同上 |
| 无法贴身、无法做小范围配合 | 身体间距椭圆下限 1.94/2.99 m | `_separateAgents` |
| 标记看起来偏大 | 绑在上述下限上 | `matchview.js:3414` |

**渲染层能改的只有最后一行，而它是「间距下限」的从属结果。**
把标记画小会让画面与引擎不一致（`engine.js:5167-5171` 已明确否决这种反向做法）。

**两条被本轮作废/降级的旧结论：**
1. 「队形散 2.2 倍」（覆盖面积）→ 引擎侧同口径只有 **+22%**，作废。
2. 「重心平移不缺」（15.3 vs 15.5）→ 只在 cmp6 的 8 m 门将带口径下成立；
   按引擎侧应有的 role 口径是 **19.6 vs 15.5（+26%）**，降级为「口径未定」。

因此「把 2D 画面做得和 FM26 一样或更好」的**唯一有效路径是先修引擎的决策层**，
即那条尚未完成的主线：**建出缺失的快速进攻通路（无球冲刺、纵深插入、拉开空间）**，
使身体间距下限可以下调而不塌进攻产出。渲染层在本轮只做了「让它可观测」。

**⚠ 下一步的改动风险已被 `AGENTS.md:3147` 明确标注**：
「修这个要加的是 team block 的纵向平移 + 长度压缩，**会显著改变比赛轨迹**
（进球、射门、控球），必须跨 n=24/n=48 复核并重跑全套比赛审计。」

### 4.1 回归网已落地（`scripts/attack-shape-compaction-audit.mjs`）

改引擎之前先把这次量出的基线钉住，否则无法判断改动是变好还是变坏。
新审计已登记进 `verify.mjs` **默认**套件（4+4 场、约 60s）。

**为什么选「进攻三区纵向长度」当断言指标**（而不是 `AGENTS.md:1852` 原先建议的三个）：

| 候选指标 | 为什么不用 |
|---|---|
| 单队覆盖面积 | FM 参照值（1821 m² / 2.2 倍）**是录屏伪影**，同口径实测只大 22% |
| 最近队友距离 | FM 参照值（7.26 m）**不可对账**（`cmp4` 只检出 13/22，漏检使其偏大） |
| 近静止占比 | 属 `AGENTS.md:3148` 说的「边缘偏离不足以单独支撑改动」 |
| **进攻三区纵向长度** | **稳健、成因已定位**，且两档一致（结构性属性） |

**断言方向很重要**：阈值按「现状 + 余量」设，所以**改好（长度变小）通过、改坏（长度变大）失败**；
另有下限防止「把队形压成一团」的塌陷式改法。六个方向全部做过**反向验证**
（把阈值往坏的方向调，六个都按预期失败并给出可读消息）：

1. 进攻三区长度 ≤ 68 m（基线 63.3~63.8）
2. 己方/中场三区长度 ≤ 45 m（基线 37.0~37.8）
3. 三区长度下限 ≥ 20 / 25 m（防塌陷）
4. 进攻三区 ≥ 中场 × 1.15（基线比 ~1.68，结构性质）
5. `all − role` ≥ 10 m（证明门将确实在 `all` 里、且被 `role` 剔掉；基线 ~22 m）
6. 进攻三区 DEF→ATT 跨度 ∈ [30, 70] m（基线 ~60）
7. 标准/后台两档差值 ≤ 6 m（证明是结构性属性，不是档位噪声）

**阈值收敛路径**：等 team-block 压缩真正落地后，
把上限从 68 收紧到接近目标（~40 m），审计就从「防恶化」变成「守目标」。
