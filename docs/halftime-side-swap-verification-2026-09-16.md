# 下半场不换边 —— 验证报告（2026-09-16）

> 用户报告：
> **「比赛时，下半场的时候，是不是双方会交换场地？好像目前只有进球庆祝后才会交换场地。
> 是不是漏了中场休息双方交换场地的逻辑？」**

## 0. 结论

**不是「漏了」，是引擎里从头到尾就没有「半场」这个概念。**
用户观察到的「进球庆祝后交换场地」也是误读 —— 进球后**没有换边**，
那是一次**双方各自回到自己固定半场**的开球摆位，只是**上半场时两队本来就在正确的一侧**，
所以看起来像「换回去」。

三处确凿证据（`scripts/_halftime-side-swap-probe.mjs`，2 场全场 90 分钟）：

| 判据 | 实测 |
|---|---|
| `_kickoff` 摆位坐标 | **上半场开球与下半场开球逐位相同**：`homeY=73.0 / awayY=25.0` |
| 引擎事件 | **从未发出 `ht`**（全场只有 4 个 `goal`）⇒ 引擎不知道「中场」存在 |
| 重启类型 | 只有 `freekick / goalkick / corner / offside`，**没有半场重启** |
| 上下半场 y 均值 | home `60.74 → 56.00`（**−4.74**，噪声量级）；away `49.38 → 47.75` |

## 1. 代码层证据

### 1.1 `attackDir()` 是纯函数，没有「半场」参数

`engine.js:791-794`：

```js
/** 该队进攻方向：主队朝 y 小(-1)，客队朝 y 大(+1) */
attackDir(team) {
  return team === "home" ? -1 : 1;
}
```

同族的 `targetGoalY`（`:796-798`）、`_inOwnPenaltyArea`（`:801-807`）、
`_offsideLineY`（`:5195`）**全部只接收 `team`，没有一处接收「半场」。**

**全仓搜索 `swapEnds` / `secondHalf` / `halfTime` 的实现：0 处。**
（`halfTime` 只出现在 i18n 文案与 `matchview-fsm.js` 的 UI 状态机里。）

### 1.2 引擎没有比赛时长常量

`grep -rn "MATCH_SECONDS" js/` ⇒ **0 处**。
`MATCH_SECONDS` 只存在于探针脚本里（写作 `SIM.MATCH_SECONDS ?? 5400` 的兜底读法，
读到的是 `undefined` ⇒ 恒取 5400）。

⇒ **引擎自身不知道一场比赛有多长，自然也不会在 45 分钟处做任何事。**

### 1.3 半场划分只存在于「解说文案层」

`match.js:1410 / :1655`、`js/sim/adapt.js:773`：

```js
const hi = tEnd <= 45 * 60 + 1 ? 45 : 90;
```

这是决定解说里写「45'」还是「90'」的**标签计算**，与引擎状态无关。

### 1.4 `_kickoff` 每次都摆回「home 在 y 大侧」

`engine.js:7878-7887`：

```js
for (const a of this.agents) {
  if (a.sentOff) continue;
  a.x = a.baseX;
  // 常规 baseY 是运动战纵深，前锋已在对方半场；开球时压缩回己方半场。
  a.y = a.team === "home" ? 50 + a.baseY * 0.48 : a.baseY * 0.48;
  if (a.team !== team) {   // 非开球队退出中圈
    if (a.team === "home") a.y = Math.max(a.y, 59.5);
    else a.y = Math.min(a.y, 40.5);
  }
  ...
}
```

- home：`y = 50 + baseY * 0.48` ⇒ 后卫 `50+72*0.48 = 84.6`（己方 y 大侧）✅
- away：`y = baseY * 0.48` ⇒ 后卫 `28*0.48 = 13.4`（己方 y 小侧）✅

**这个式子不含任何「半场序号」，所以每次调用（开场 / 进球后 / 任何开球）结果完全一致。**

### 1.5 `_kickoff` 的调用点只有两处，都是「home 或进球方」

- `engine.js:628` 构造函数：`this._kickoff("home")`
- `engine.js:1817-1821` 进球后：`const side = this.kickoffTeam || "home"; this._kickoff(side);`

`this.kickoffTeam` **恒为 `"home"`**（构造时 `:628` 之后再未赋值）⇒
**进球后永远是 home 队开球，摆位也永远是「home 在 y 大侧」。**

## 2. 为什么用户会看到「进球后交换场地」

用户的感受是真实的，只是归因反了：

```
比赛进行中：球在场上滚动，球员的 y 随球大幅漂移（实测两队 y 中位数
            长期挤在同一侧，如 15' 时 home 86.5 / away 86.7）
进球后 _kickoff：两队被**瞬间按回各自的固定半场**
            （home 73.0 / away 25.0，见下表的「每次开球」列）
```

⇒ 从「双方都挤在某一侧」突然变成「分居两侧」，**视觉上就非常像一次换边**。
而它其实是 `_kickoff` 的**硬置摆位**（也就是前几轮修掉的「整队瞬移」在进球开球时的表现）。

**佐证**：探针记录的四次开球中，第 51.1' 那次（下半场开球）与第 1.2' 那次
**坐标逐位相同**（`homeY=73.0 / awayY=25.0 / homeX=59.0 / awayX=50.0`）。
下半场开球**没有**任何不同。

| 场 | 时刻 | 开球方 | homeY | awayY | homeX | awayX |
|---|---|---|---|---|---|---|
| 1 | 0.9' | away | 75.0 | 25.0 | 50.0 | 59.0 |
| 1 | 1.2' | home | 73.0 | 25.0 | 59.0 | 50.0 |
| 1 | **51.1'** | home | **73.0** | **25.0** | **59.0** | **50.0** |
| 1 | 59.8' | away | 75.0 | 25.0 | 50.0 | 59.0 |

## 3. 顺带查到的一件更值得注意的事

① 表里那一列 `homeY + awayY`（我原本设计来判「是否分居两侧」，和应 ≈ 100）：

```
 0'  72.8 / 25.2  → 和  98.0   ✅ 分居两侧
 5'  26.2 / 19.7  → 和  45.8   ⚠ 同侧（都在 y 小侧）
15'  86.5 / 86.7  → 和 173.2   ⚠ 同侧（都在 y 大侧）
20'  88.4 / 88.2  → 和 176.6   ⚠ 同侧
45'  89.7 / 83.0  → 和 172.7   ⚠ 同侧
```

**在 18 个采样点里，有 11 个的「和」偏离 100 超过 30** —— 即**两队经常整条线挤在球场的同一侧**。
这与「换边」无关（`baseY` 是固定的），而是**运动战中两队都被球吸引、队形随球整体平移**的结果。
它可能正是用户平时感觉「场地不对劲」的另一个来源，**但本轮未深查**（需单独的探针）。

## 4. 这是否算缺陷？—— 需要用户决定

**从足球规则看，这是缺陷**：真实比赛下半场双方必须交换场地，
这是写进规则的（IFAB 场地条件与比赛程序），且它直接影响**战术**（顺风/逆风、阳光、
以及「哪一方在哪个半场施压」）。

**但从本项目现状看，补它并非「补一个 if」**：

1. **引擎的坐标系是「队固定朝向」而非「场固定朝向」。**
   `attackDir(team)` 返回常量，`baseY` 是固定槽位，`_offsideLineY`、`targetGoalY`、
   `_inOwnPenaltyArea` 全都建立在「home 恒向 y 小进攻」之上。

   **好消息**：`attackDir` 的**方向读取**全部走函数调用，共 **11 处调用点**
   （`engine.js:870 / 1201 / 1257 / 1302 / 1390 / 1488 / 1602 / 1637 / 2312 / 2528 /
   3051 / 3098 / 3132 / 3185 / 3415 / 3741 / 3794 / 3955 / 4605 / 5004 / 6207 /
   6547 / 6688 / 6778 / 7298 / 7652 / 7899 / 7932`），
   **没有一处把方向硬编码成常量**。

   **坏消息（本轮新发现，成本比预想高）**：**「team → 球门 y」的映射被硬编码复制了至少 10 处**，
   完全绕过 `targetGoalY`：

   | 行 | 写法 |
   |---|---|
   | `1202` | `a.team === "home" ? SIM.AWAY_GOAL_Y : SIM.HOME_GOAL_Y` |
   | `1787` | `agent.team === "home" ? SIM.HOME_GOAL_Y : SIM.AWAY_GOAL_Y` |
   | `2118` | `a.team === "home" ? SIM.HOME_GOAL_Y : SIM.AWAY_GOAL_Y` |
   | `3957` | `ownGoalY = a.team === "home" ? HOME_GOAL_Y : AWAY_GOAL_Y` |
   | `4597` / `4801` / `5107` / `5170` | 同上（`ownGoalY`） |
   | `5729` / `5872` | `gk.team === "home" ? HOME_GOAL_Y : AWAY_GOAL_Y` |
   | **`5182-5183`** | `clamp(SIM.HOME_GOAL_Y - b.y, 0, 100)` —— **直接当坐标算距门距离** |

   ⇒ **换边必须同时把这些点改成「按当前半场取球门」**，漏一处就是一个静默错位的分支
   （不会报错，只会让某个判定在下半场反着来）。

2. **它会改随机流与所有既有标定。** 翻转 `dir` 会改变每一个依赖方向的分支选择
   （`drop`/`else`、套边、越位投影、门球去向……），进而改变 `this.random()` 的消费顺序。
   ⇒ **必须全量重跑 `verify.mjs` + 复核进球率 / 强弱分离 / beat 带宽。**
   这是一次**完整的重标定**，不是小改。

3. **`_kickoff` 也要跟着改**（`:7882` 的 `50 + baseY * 0.48` 要按当前半场选式子），
   否则下半场开球会把两队摆错半场 —— 那会是一次更严重的瞬移。

4. **`matchview` 的 `SEGMENT_CUT_MS` 淡场正好可以用来讲「下半场开始」这次换边** ——
   这是现成的、已建好的机制，不需要新写法。

5. **还要先决定引擎是否知道「半场」。** 目前引擎**完全没有比赛时长概念**
   （`MATCH_SECONDS` 在 `js/` 下 0 处），所以：
   - 要么给 `SimEngine` 传入 `halfSeconds`（并处理加时/不同赛制）；
   - 要么让调用层在 45 分钟处**显式调一个 `_swapEnds()`**。
   **两种都改变引擎的公开契约**，需先定。

## 5. 建议的推进顺序

1. **先补护栏与「统一入口」（必做）**：
   - 把 10 处硬编码的 `team → 球门 y` 全部收敛到 `targetGoalY` / 新增的 `ownGoalY(team)`
     （这是**纯重构，不改行为**，可先用逐位对比验证：改造前后同种子跑一场，
     所有读数必须逐位一致）。⚠ 不做这一步就换边，等于在 10 个地方各埋一个隐患。
   - 写只读审计：断言 `attackDir` 在下半场确实翻转；断言 `_kickoff` 在下半场
     把 home 摆到 y 小侧；断言全仓 `HOME_GOAL_Y` / `AWAY_GOAL_Y` 的直接引用
     只剩收敛后的入口（防止将来又长回来）。
   本项目已多次吃「先改后标定」的亏。
2. **单独一个 PR 实施**，只改 `attackDir` + `_kickoff` + 球门入口，配全量 `verify.mjs`
   与进球率/分离度复核。
3. **`matchview` 侧**：下半场开场复用 `SEGMENT_CUT_MS` 的淡场，
   把它讲成「下半场开始」而不是一次瞬移。

**⚠ 本轮未实施任何改动**（纯验证）。

## 6. 量测边界

- 2 场、种子 `391000..391001`、全场 5400 模拟秒、默认 4-3-3 / 双方能力 15。
- 「两队 y 中位数」用非门将球员；`medianY` 对 10 名外场球员取中位。
- 采样间隔 300 模拟秒（5 分钟），每场 18 个采样点。
- **未验证**：真实比赛时长参数（不同联赛的补时）、替补登场后 `baseY` 是否变化、
  以及「两队挤同侧」那件事的成因（另需探针）。
- **未在浏览器端验证**渲染层是否另有一套换边逻辑（本轮只查了 `js/` 源码与引擎实测）。
