## 3. 本次改了什么

### 3.1 🔴 交接 §4.1 的根因被实测推翻

它说：「`_kickoff` 刻意不设 `restartType` ⇒ `restartFrame` 为假 ⇒ `relocate()` 永不武装
⇒ 22 人一起硬瞬移」。

**实际**：`_kickoff` 末尾有 `this.deadBallUntil = this.t + 0.9`（`engine.js:8351`），
而 `motionContextOf`（`engine.js:492-496`）把 deadBall 算进 `discontinuity`
⇒ 开球后 0.9 秒内 **`restartFrame` 为真，缓动可以武装**。

**真根因（实测）**：整队级重启搬运（角球 / 门球 / 开球）把 **21~22 人**
在**一个 0.1 s 帧内**搬走 **40~76 m**；而 `relocate()` 的缓动是
**固定 700 ms 的 ease-out cubic**（首帧 7%、两帧 76%）⇒ 等效 **~258 m/s**。
缓动**确实在跑**（实测占 3.45% 的帧），只是摊不平 60 m。

### 3.2 修法（`js/matchview.js`，**引擎零改动**）

段内整队摆位改走**段首那套「硬置 + 淡场剪辑」**：
`n >= 3 && maxM >= 25 m` ⇒ `_playSegmentCut()` + 一步到位 + 不给 `relocate` 武装。

- 依据是**本仓库自己早就写下的一句话**（`matchview.js:1218-1220`）：
  「缓动本身也是错的解法 —— 45 m 位移摊到 0.7 s 等于 64 m/s 的扫掠」。
- 此前**只有段首**这样处理 ⇒ 同一个角球，拿到自己的高光窗就是剪辑、
  落在扑救/射门窗**内部**就是 0.7 s 扫掠 —— **同一事件两种呈现，本身就是缺陷**。
- 判据是**距离**不是人数：2 m 摆位摊到 700 ms 只有 3.6 m/s（**必须**继续走缓动）。
- 顺带修 `_playSegmentCut()` **缺去抖**（整队摆位每个渲染帧都会判到，
  旧实现把满遮 91 ms 拖成 190 ms）。

### 3.3 实测

| | 修复前 | 修复后 |
|---|---|---|
| 全部帧里「有实体在缓动」 | 229 / 6646 = **3.45%** | **0 / 10522 = 0.00%** |
| 运动战帧里「有实体在缓动」 | 0.00% | 0.00%（护栏保持） |
| >6 m 位移帧**未被淡场遮住**的 | （测不到，见下） | **0 / 10** ✅ |

新增 `scripts/_restart-snap-census.mjs`（确定性整场普查 + **同进程双跑指纹自检**）：
4 场里**可见的**超物理位移帧对 **28 次**（约 7 次/场），**全部**是整队级 40~76 m，
**全部带 restart/discontinuity 标记**（无标记 **0** 次）。

🔴 **为什么上一轮卡住（重要方法论）**：
`_restart-placement-probe.mjs` 的 `dt >= 0.08` 那道门把**缓动摊开的小步**全滤掉了
（修复前一次摆位被摊成 10 个 ~2.6 m 的小步，每步 `dt` 只有 0.011~0.019 s）
⇒ **它只看得见「一步到位」，看不见「被摊开的扫掠」**。
**量「有没有瞬移」必须同时看位移与淡场遮没遮住。**

### 3.4 规格护栏按新规格重写了 3 块（`scripts/match-continuity-audit.mjs`）

- 整队摆位：从「缓动 0.7 s 到位」改成「落剪辑 + 一步到位 + 球与人同帧 + 幂等」；
- 段内边界：从「插值期间球权留在原持球者」改成**更强**的
  「几何与球权必须同帧一起换，不允许混合态」；
- historical fixture（实测该帧对 **n=22、maxM=45.53 m**）：从「插值期间停在出发点」
  改成「**不允许任何中间几何**」。

⚠ **覆盖没有减少** —— 小范围摆位那套缓动性质（按模拟时间推进、球与球员共用一条过渡）
仍由 `small` 块（1.8~2.5 m）与 historical fixture 块把关。

## 5. 用户三个新提问：**已全部查证，一条未改**（交接 §5）

### ① 点球命中率是不是按门将 / 主罚者能力设的？——**是，但基线偏低**
唯一公式 `js/sim/engine.js:7319`：
```js
penSkill = finishing*0.38 + shooting*0.24 + decisions*0.22 + kicking*0.10 + (isCore ? 0.015 : 0)
save     = 0.55*reflexes + 0.28*handling              // 无门将时 0.2
pScore   = clamp(0.77 + (penSkill - 0.6)*0.34 - save*0.22, 0.55, 0.9)
r = random();  r < pScore ⇒ 进球；否则按 (1-pScore) 再劈 70% 扑救 / 30% 打偏
```
- **读门将也读主罚者**；**不读** `composure`/`penalties`（这两个属性在本游戏里不存在）。
- 只抽**一次**随机数；**没有**射门方向↔扑救方向配对（`saveSide` 是 outcome 之后
  抽的动画参数）；天气/德比/主客场/体能都不进这条式子。
- 量级：门将 1→20 ⇒ 72.1% → 61.0%（−11.1pp）；主罚者 1→20 ⇒ 55.0% → 73.9%（+18.9pp）；
  上夹 `0.9` 是**死代码**，下夹 `0.55` 会真咬住。
- **真实俱乐部 400 组实测平均 67.09%**，而现实约 75~80%，
  **且仓库自己的点球 xG 硬编码就是 0.76**（`match.js:1200`、`match-analysis.js:40`）
  ⇒ 引擎实际转化率**与它自己声明的 xG 不一致**。用户的感觉成立。
- **最小改动（需拍板）**：`0.77 → ≈0.85` ⇒ 67.1% → ≈75.3%，
  **斜率不变（能力区分度一点不减）、判罚频次完全不动**。
- ⛔ 不要动 `norm()`（牵动整套标定）；⛔ 不要动判罚侧
  （`match-realism-audit.mjs:495` 的 0.1~0.5/场信封是钉住的）。
- 附带：v1 概率引擎的 `penaltyConversionChance`（`match.js:1119-1128`）算 73.86%，
  **与 v2 差 6.8 pp**（无文档规定该不该对齐）；淘汰赛「点球大战」是纯抛硬币
  （`match.js:3436`），不读任何能力。

### ② 为什么没见过边线球？——**引擎整场产生 0 次**，不是「被平淡过渡掉了」
- `engine.js:7621-7626` 的 `b.x <= 0 || b.x >= 100` **不可达**：
  球 90% 时间黏在球员脚下、球员坐标夹在 `[1,99]`（目标位更紧 `3..97`），
  **全引擎没有任何一处把球瞄向边线**；实测整场 `|x-50|` 最大值只有 **45.8 / 50**。
  实测 **17 场 × 90 分钟 = 0 次**。把步长放粗到 0.3/0.5 s 就出现了 ⇒ **数值边距问题**，
  属**静默失效**（对照：进球线分支命中 282 次）。
- **UI 侧零消费者**：`buildHighlightWindows` 不加窗、`pickFlavorEvents` 的 `caps`
  白名单丢弃、`defaultFlavorText` **没有 `case "throwin"`**
  ⇒ 将来接线会直接显示「45' 球队名」这种垃圾文案。
- ⇒ **两个独立缺口**：ⓐ 让球真能出边线；ⓑ 三处消费者同时补。
- 同类先例：`adapt.js:501` 的注释写着「**用户反馈「从没见过角球画面」**——旧版高光窗根本不含角球」。

### ③ 赛前没有首发预览？——**确实没有**，但数据在那一刻全部可得
