# 中场前插名额可以被一名已离场球员占住（2026-09-15）

> 这是 HEAD 自身的缺陷，与任何候选补丁无关。本轮之前它从未被测过。

## 1. 结论

`js/sim/engine.js:4179` 的 `_isPrimaryMidRunner` 从**包含已离场球员**的池子里选
「本队唯一的中场前插名额」，判定写成 `mids[0]?.id === a.id`。于是当评分最高的中场
被罚下（或伤退）时，`mids[0]` 就是那名离场球员，**场上没有任何中场拿到名额**。

名额门控着两条写成「恰好一名」的规则，于是双双退化成「零名」：

- `:3799-3801`：注释原文「最后三区限制中央前插名额：三名前锋 + **一名**最适合前插的中场。
  其他中场在球后形成两层接应」。名额无人持有 → **每一名中场都被压到球后**。
- `:3699`：非主力中场的接应点若落在对方禁区内直接否决。名额无人持有 →
  **任何中场都不能从这条路径进入对方禁区**。

修复是把池子限制为「真的能跑的人」，一行条件。已按候选流程测量并接入正式源码。

## 2. 为什么这是缺陷（三条独立论据）

1. **违反了代码库自己对 `sentOff` 的契约。** `js/sim/engine.js:6191`
   （`_commitInjury` 内）的注释原文：「复用罚下减员：退出决策/跑位/发球候选，
   场上真实少一人」。`_isPrimaryMidRunner` 的池子正是「跑位候选」，
   却没有过滤这个标志。
2. **兄弟规则已经过滤了。** `:3579-3581` 是同一套「球后两层接应」概念的另一处实现，
   它写的是 `!m.sentOff && (!m.injuredOff && !this._isPrimaryMidRunner(m))`。
   同一份事实、两种写法——`:4181` 是那个不一致的。
3. **`mids[0]?.id === a.id` 的语义依赖池子非空。** 池子一空就没有任何持有者，
   这是「要么选对人、要么谁也不选」，不是「偏好排序变了」。最高设计原则
   （AGENTS.md）明确禁止「只影响某个界面的隐藏能力或特殊加权」。

另外，伤退复用了罚下标志（`:6190-6191` 同时置 `injuredOff` 与 `sentOff`），
所以两种减员走的是同一条路径；探针里 `defectInjured` 恒为 0 就是这个原因。

## 3. 测量（HEAD）

`scripts/_primary-mid-slot-audit.mjs`（本轮新建）。它**直接问引擎**「这一 tick 有没有
中场拿着名额」（调用 `_isPrimaryMidRunner`），而不是复算规则；最后三区的判定复用
引擎自己的口径 `prog = |ball.y − ownGoalY| / 100 > 0.64`（`:3748-3768`）。

| | 后台 24 场 | 标准 8 场 |
|---|---:|---:|
| team-ticks | 864000 | 864000 |
| 名额正常持有 | 854991 | 864000 |
| **名额无人持有** | **9009（1.0427%）** | 0 |
| 其中球在最后三区 | **2807（0.3249%）** | 0 |
| 受影响场次 | **2 / 24** | 0 / 8 |
| 单场最多缺陷 ticks | **5854** | 0 |
| 全场红牌 / 其中中场 | 12 / 3 | 0 / 0 |

两个要点：

- **触发后是持久的，不是一闪而过。** 一旦那名中场被罚下，`mids[0]` 在**剩下整场**
  都是他。`maxDefectTicksInMatch = 5854` 就是一场比赛里从红牌到终场的那一段
  （后台档 18000 ticks/场）。也就是说：**2/24 = 8.3% 的后台比赛里，
  这条规则在相当长的一段时间内是关着的。**
- **标准档 8 场一次都没触发**，因为那 8 场根本没有红牌（`redCards: 0`）。
  所以它对真实性信封的影响可以忽略——这不是一个靠信封能发现的缺陷。
  3 张中场红牌只造成 2 场缺陷，是因为只有「被罚下的恰好是评分最高的那个」才触发；
  否则名额会顺位交给还在场上的下一名中场。

**口径提醒**：`2807` 是**暴露上界**（球在最后三区且名额无人持有的 team-ticks），
不是实际发生量——`:3801` 那段代码还要被真正走到。它的意义是
「这些 tick 上，规则把所有场上中场都压到了球后，而修复后会有**恰好一名**被允许前插」。

## 4. 修复

`js/sim/engine.js` 的 `_isPrimaryMidRunner` 池子加一个条件：

```js
const mids = this.agents
  .filter((m) => m.team === a.team && m.role === "MID" && !m.sentOff && !m.injuredOff)
  .sort(/* 评分不变 */);
```

只加过滤，**不改评分函数、不改任何阈值、不改跑速/能力**。
行为差异只出现在「评分最高的中场不在场上」这一种情况：
HEAD 是谁也不持有，修复后是顺位交给场上评分最高的中场。

候选：`scripts/_primary-mid-slot-candidate.mjs`（`--import` 注入，不改磁盘源码）。

## 5. 验收

### 5.1 名额探针：缺陷清零，且落地版与候选逐位一致

同一批种子（后台 22901–22924、标准 22911–22918）：

| | HEAD | 修复 |
|---|---:|---:|
| 后台 `defectTicks` | 9009 | **0** |
| 后台 `defectFinalThirdTicks` | 2807 | **0** |
| 标准 `defectTicks` | 0 | 0 |
| 后台红牌 / 中场红牌 | 12 / 3 | 12 / 3 |

红牌数不变，说明修复没有改变比赛事件本身，只是把名额顺位交给了还在场上的中场。
另外，**落地后的逐场输出与 `--import` 候选逐位相同**
（`landed per-match == candidate per-match: true`），所以「候选测出来的东西」
就是「落进去的东西」。注意落地源码的 SHA-256 与候选的注入结果不同
（`7c32f7f4…` vs `3b7b464b…`），差异只是落地版多了一段注释，
所以这层等价关系是靠**行为比对**建立的，不是靠哈希。

### 5.2 实际后果（把「暴露」变成「观察到的差异」）

| 指标（后台 24 场） | HEAD | 修复 |
|---|---:|---:|
| 球在最后三区时，场上中场平均人数 | 1.6933 | 1.6935 |
| — 只在**缺陷** tick 上 | **1.1984** | （已无缺陷 tick） |
| — 只在**正常** tick 上 | 1.6978 | 1.6935 |

缺陷期间场上中场平均 **1.1984** 人，正常时 **1.6978** 人——**少约 0.5 人（−29%）**。
逐场看，两场受影响：seed 22901（1144 个最后三区缺陷 tick，平均 1.2028）、
seed 22920（1663 个，平均 1.1954）。

整体平均几乎没变（1.6933 → 1.6935），因为缺陷只覆盖 2807 / 311662 = **0.9%** 的
最后三区 tick。所以**这是一个真实但稀有的缺陷**：不触发时完全无影响，
触发时在剩下整场里持续压低中场的前插人数。

## 6. 顺带修掉：v255 的缓存版本号只改了一半

第一次跑 `verify --full` 时被 `scripts/cache-audit.mjs` 拦下：

```
AssertionError: index.html and sw.js cache names must match
+ actual   'vcfm-v254'
- expected 'vcfm-v256'
```

查下来**这不是本轮引入的**。`868479d`（`chore: bump the offline cache to v255`）
只改了 `sw.js` 的 `CACHE` 和 `AGENTS.md` 的记录，**没有同步**：

- `index.html`：`CURRENT_CACHE`、`?v=254` ×3（style.css / main.js / sw.js）、
  `vcfm-sw-reloaded-v254` ×2
- `js/main.js`：`?v=254` ×5

而 `cache-audit.mjs:17` 正是断言这两个文件名必须一致，所以
**从 `868479d` 起 `verify` 的 cache-audit 一项一直是红的**——
AGENTS.md 里「verify --full 退出 0」的记录早于这个提交。

本轮升到 v256 时一并对齐，`node scripts/cache-audit.mjs` 退出 0：

```json
{ "cache": "vcfm-v256", "queryReferences": 8, "assets": 99,
  "entryPoints": 4, "reachableModules": 93 }
```

**教训**：升缓存版本要同时改四处（`sw.js` 的 `CACHE`、`index.html` 的
`CURRENT_CACHE`、两处 `?v=` 查询串、`vcfm-sw-reloaded-v` 刷新键），
外加 `AGENTS.md` 顶部的记录。只改一处会让 `verify` 直接红，而且因为它是
套件里较早的一项，后面全部不跑——很容易被误读成「改坏了引擎」。

## 7. 同类的次要不一致（本轮不改，留档）

`:3802`（最后三区规则内部算 `rank` 用的池子）也漏了同一个过滤：

```js
const mids = this.agents
  .filter((m) => m.team === a.team && m.role === "MID")
  .sort((m, n) => String(m.id).localeCompare(String(n.id)));
const rank = Math.max(0, mids.indexOf(a));
```

它只影响 `rank`，进而影响非主力中场后撤的距离 `b.y - dir * (15 + rank * 3.5)`——
离场球员会把场上球员的 rank 抬高，让后者多退 3.5 米的整数倍。这是**间距**上的
小偏差，不构成规则语义的破坏（不会出现「一名 → 零名」），所以本轮不动它，
以免把一行语义修复和一处间距调整混在同一次验收里。
