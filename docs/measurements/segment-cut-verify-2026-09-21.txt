读数（45s 采样，直播）
----------------------
ENTRIES:
  { mode:"cut", gapSec:0.1,  t0:0.1,  hasClass:true }
  { mode:"cut", gapSec:25.7, t0:39.7, hasClass:true }
CLASS: framesWithCutClass=39 / totalFrames=2329 (1.7%)  stuckRuns=0
MODES: first=0  cut=2  ease=0
ERRORS: []

判据与结论
----------
- **淡场会触发**：两次切段都挂了 `.mp-seg-cut`。
- **不会卡住**：stuckRuns=0（class 没留在场上把球场涂黑）。
- **缓动分支仍是死的**：ease=0。真实间隔 25.7s ≫ 一帧，走 cut，与
  `_segment-gap-census.mjs` 的 129.5~956.8 比赛秒一致。
- **`first=0` 不能当「开球闪了一下」**：钩子是在 `#screen-match` 已经
  active 之后才打上的，开球那一次 `_enterSegmentTransition` 没采到。
  第一条 gapSec=0.1 是直播开始后探针看到的第一段，不是真正的 kick-off。

  🔴 **勘误（2026-09-21 晚，见 `segment-boundary-displacement-2026-09-21.txt`）**：
  上面这条解释**被推翻**。真因不是「钩子打晚了」——
  `scripts/_segment-boundary-displacement.mjs` 在点 `#btn-sim-live` **之前**就装了钩子，
  仍然抓到开球那次 `t0=0.1` 被判成 `cut` 并闪了淡场。
  真因是 `js/matchview.js:1236` 的 finite 守卫失效：
  `_segLastEndSimT` 初值 **`null`**，而 `Number(null) === 0`、`Number.isFinite(0) === true`
  ⇒ 守卫拦不住初值 ⇒ `gapSec = 0.1 − 0 = 0.1 ≠ 0` ⇒ 判 `cut`。
  **即：每场开球都会多闪一次淡场（真 bug，未修）。**
  `MODES: first=0` 正是这个 bug 的读数，不是探针的问题。
