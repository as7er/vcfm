中场体能「逐人连续消耗」—— 候选方案不成立 + 替代方案 + 跑动距离噪声标定
==========================================================================
（2026-09-21，v275 之后）

用户已拍板（2026-09-17）：「修根因：逐人连续消耗」。候选方案是
**「同步路径结算时读引擎内 `agent.fitness`（个体连续值）回写 `player.fitness`」**。

本轮先建基线再动手，**实测结论是这条候选方案不够用** —— 按项目纪律
「当新证据推翻既定决定时停下来报告」，本文就是那份报告 + 替代方案的标定。


[0] 结论（一句话）
------------------
1. **候选方案修不好可见症状**：引擎侧个体差异实测只有 **spread 0.39**（总耗 4.84），
   回写到面板口径后四舍五入**仍是全 87**。根因在更上游 ——
   引擎的逐人耗能模型本身几乎没有个体差异。
2. **引擎里有个真实信号被白白浪费**：每个 agent 的**实际跑动距离**
   （实测 GK 2.95 / DEF 8.89 / MID 9.90 / ATT 9.32 km，队内 max/min **3.889×**，
   与现实足球一致）。按它占比分摊球队总耗能 ⇒ **面板 86~89**（现状全员 87），
   **球队均值逐位不变 ⇒ 零重标定**。
3. 已按护栏纪律完成**噪声标定**（48 场）：主指标带宽 **[3.32, 4.46]**，
   判决力足够（辨出 Δ=0.3 只需 4 场）。


[1] 候选方案为什么不够用（实测）
--------------------------------

### 探针：`scripts/_halftime-fitness-display-probe.mjs`（本轮改造）
原版假球员只给 `attrs: {}` ⇒ **同值档** ⇒ 引擎的个体差异在构造上就被抹掉，
「引擎侧也没差」这个结论是探针自己造出来的。改造三处：
1. `generatePlayerAttributes(p, p.ovr)` + `ensureFootballProfile(p)`。
   ⚠ `ensureFootballProfile` **不生成 stamina**（实测全员 stamina 都是默认 0.600 ⇒ 仍是同值档），
   必须走 `generatePlayerAttributes` 这条「新建世界」路径。
2. 基线必须在 `createMatchSession` **之后**取 —— `defaultTactics().lineup` 是空数组，
   首发建会话时才自动挑；之前那版基线是**空集合**，于是全部以 `?? 100` 兜底，
   把「90 → 87（−3）」错读成「100 → 87（−13）」。
3. 加读数：引擎侧 spread / `stamina` 倍率 / `fsm` 分布。

### 改造后的实测（完整属性档，上半场 45 分钟）
| 口径 | 读数 |
|---|---|
| 面板（`club.players[].fitness`） | **全员 87（取值种类数 = 1）**，赛前 90 ⇒ 扣 **3 点** |
| 引擎（`agent.fitness`） | min 84.94 / max 85.33 / mean 85.11 ⇒ **spread 0.39** |
| 引擎 `stamina`（norm 后） | 0.728 ~ 0.888 ⇒ 耗尽倍率 **1.064×** |

⇒ 把引擎的个体偏差缩放到面板口径：`3.00 ± 0.24` ⇒ **86.76 ~ 87.24 ⇒ 四舍五入还是 87**。
**症状不变。**

### 根因：引擎耗能公式里的个体项被压到几乎没有
`engine.js:5851`：
```js
const workRate = a.fsm === "press" ? 1.35 : a.fsm === "carry" ? 1.12 : 1;
const drain = dt * (0.0014 + pressing * 0.00018) * workRate * (1.18 - (a.attr.stamina || 0.5) * 0.35);
```
- `pressing` 是**球队级**（不区分个人）；
- `workRate` 只区分「press / carry / 其他」三个**瞬时**状态，不累计；
- `stamina` 被 `norm()` 压到 0.728~0.888，再乘 0.35 系数 ⇒ **总倍率只有 1.064×**。

⇒ 引擎的模型里**根本没有「这个球员这场跑了多少」这个量**，再怎么回写也搬不出差异。


[2] 替代方案的数据基础：跑动距离（引擎里已有的真实量）
------------------------------------------------------

### 探针：`scripts/_fitness-distance-calibration-probe.mjs`（本轮新建，**只读**）
用 `eng.timeStep`（标准档 = `SIM.DT` = **0.1s**，与生产同档）驱动 `eng.step()`，
每步累加每个 agent 的 `|Δ位置|`，米制换算与引擎 `pitchDistanceMetres` **完全一致**：
`hypot(dx * 68/100, dy * 105/100)`。

⚠ 两个口径坑（都踩过）：
- **步长不能为了跑得快改大**：`_activeStepDt` 会影响 `samplingReach` / `stallLimit` /
  `contactStep` ⇒ 改步长等于**换了一套物理**。第一版用 0.5s 跑出 `max/min = 2.72`，
  改用生产档 0.1s 后是 **3.889** —— 差异主要来自这里。
- **首发要显式指定**：`defaultTactics().lineup` 是空数组，自动挑选实测**不会挑到门将**
  （会把一名后卫放进 GK 槽）⇒ 第一版「门将跑 4.28km」测的是个改行的后卫。
  行为没错（引擎按 role 处理），但标定口径应该用真门将。

### 实测（48 场，96 个球队观测，种子 900000..900047，耗时 240.8s）
| 指标 | 比赛级（n=48） | 球队级（n=96） |
|---|---|---|
| 队内 max/min 比值 | **均值 3.889 · SD 0.287** · 范围 3.445~4.636 | 均值 3.889 · SD **0.723** · 范围 2.806~5.314 |
| 球队场均跑动 | 8.766 km · SD 0.393 | 8.766 km · SD 0.487 |
| 门将占球队均值比 | **0.337 · SD 0.024** | 0.337 · SD 0.064 |
| 队内 CV（SD/均值） | 0.256 · SD 0.015 | 0.256 · SD 0.015 |

按角色均值（96 个观测合并）：**GK 2.95 · DEF 8.89 · MID 9.90 · ATT 9.32 km**
（GK 范围 2.02~4.00、DEF 6.97~11.55、MID 8.31~10.88、ATT 7.24~11.22）

**这组数字与现实足球一致**（中场 ~10km、中卫 ~9km、门将 ~3km），
而且它是引擎每帧本来就有的量，**不是新造的隐藏指标**。

### 🔴 方法学要点：伪重复会把带宽算宽一倍半
主客两队共享同一场比赛的条件 ⇒ 96 个「球队观测」**不是 96 个独立样本**。
实测：球队级 SD **0.723** vs 比赛级 SD **0.287**（**2.5×**）。
若拿球队级 SD 定带，带宽会从 ±0.57 变成 ±1.45 —— **判决力直接废掉**。
⇒ **护栏带宽必须用「以比赛为批单位」的 SD。**


[3] 护栏（带宽由实测批间 SD 决定，不是拍脑袋）
----------------------------------------------
| 指标 | 中心 | 2×SD | 建议带 |
|---|---|---|---|
| **主：队内 max/min 比值** | 3.889 | 0.574 | **[3.32, 4.46]** |
| 辅：门将占球队均值比 | 0.337 | 0.048 | [0.29, 0.38] |
| 辅：队内 CV | 0.256 | 0.029 | [0.226, 0.285] |

**判决力**（`n = (2×SD/Δ)²` 场比赛）：SD = 0.287 ⇒
辨出 Δ=0.3 需 **4 场**、Δ=0.5 需 **2 场**。
⇒ 这条护栏**带宽窄到可以在很小的样本上判决**（与 beat 护栏「24 场只够判大幅变化」形成对比）。


[4] 反事实：按跑动距离占比分摊球队总耗能
----------------------------------------
现状：上半场每人固定扣 **3 点**（实测 `player.fitness` 90 → 87，3 次整点结算 × 1 点）
⇒ 球队总量 = 3 × 11 = **33 点**。改成按**逐人**跑动距离占比分摊同一总量：

| 分位 | 应扣 |
|---|---|
| min（门将） | 0.77 |
| p10 | 2.51 |
| 中位 | 3.18 |
| p90 | 3.68 |
| max | 3.86 |

- **面板取值 86 ~ 89**（现状是全员 87；**均值仍是 87**）
- **球队均值扣减 3.000 = 现状 3.000** ⇒ **零重标定**（按比例分摊，总量守恒）
- 极值比 5.03×（门将 0.34× 球队均，跑最多的球员 3.86）

⚠ 反事实**必须用逐人距离**，不能用「角色均值」：
第一版用 4 个角色均值当分母 ⇒ 均值算出来是 8.25 而不是 3（等于又做了一次团块）。
⚠ 面板基准是**赛前体能**（90）不是 100：第一版写成 `100 - drain` ⇒ 把「86~89」错报成「96~99」。


[5] 顺带量出的一个口径不一致（值得单独记）
------------------------------------------
| 口径 | 上半场扣减 | 用途 |
|---|---|---|
| 面板 `player.fitness` | **3.00 点** | 中场面板显示、换人建议、评分 |
| 引擎 `agent.fitness` | **4.84 点** | **跑速**（`playerRunSpeed`）、**疲劳伤病**（`_tickFatigueInjury`） |

⇒ 引擎实际耗能是面板记账的 **1.61×**。两者是两套独立记账
（引擎那份注释写着「引擎内体能只影响本场运动；正式球员体能记账仍由 match.js 负责」），
但面板显示的「体能」和真正决定球员跑不跑得动、会不会拉伤的那个数**不是一个数**。
本项**未改**，仅记录。


[6] 方案 D（**已实施**，2026-09-21）
-----------------------------------
### 实现
1. **引擎侧（纯计数器，不参与任何物理/决策）**
   - agent 加 `runMetres`，在位移更新后累加 `pitchDistanceMetres(Δx, Δy)`
     （换算与引擎同源：内部 100×100 ↔ 球场 68m × 105m）。
   - `substituteAgent` 里重置为 0（换上的球员用**新身体**）。
   - `resyncSimAfterHalfTime` 里**按 id** 搬运：该函数下面按**槽位序号**重绑
     `a.id = p.id`，不搬的话接替同一槽位的另一名球员会继承前者的跑动距离。
   - ⚠ 验收断言：`runMetres` 在 `engine.js` 里**只写不读**（3 处：初始化 / 累加 / 换人重置）
     ⇒ 这是「引擎物理不受影响」的**静态证明**。
2. **`match.js` 侧**
   - 抽出 `settleFitnessDrain(state, club, sk, extra)`，**四处**调用点统一走它
     （高光流 `finishMinuteSideEffects` / 异步逐分钟 / 同步路径 / 概率引擎
     `runMinutesSync`）。旧实现是三份复制粘贴 + 一处独立实现。
   - 口径：`teamTotal = perPlayer × 人数`（`perPlayer = max(1, round(fitW + extra))`，
     **与旧实现完全一致**），按 `runMetres` 占比分摊。
   - 回退：无 `simEng` / 跑动全 0 ⇒ `Math.round(Math.max(30, fitness - perPlayer))`
     （**与旧实现逐字相同**）。

### 🔴 实施中发现的两个坑（都值得单独记）

**坑 1：引擎在分钟循环开始前就把整段跑完了。**
`runSimPeriodRaw` 一次性推进到 `toMin`，所以 minute 15 那次结算读到的
**已经是整段的累计值**，而 30/45 两次的「本窗口增量」恒为 **0**
（实测日志：min15 有值、min30/45 全是 0）⇒ 第一版按「增量」分摊会退化成等额。
⇒ 改用**累计值**分摊。这是安全的：分摊只取决于**队内分布**，而分布在同一场里稳定
（48 场标定 max/min 3.889，比赛级 SD 0.287）。附带好处：不需要任何额外状态
⇒ 读档后引擎重建（`runMetres` 全 0）自动走回退。

**坑 2：耗能量级太小，整数分辨率装不下个体差异。**
`perPlayer` 实测只有 **1 点**（`max(1, round(fitW))`，默认战术 `fitW < 1.5`），
`teamTotal = 11` 摊到 11 人 ⇒ 平均每人 1 点。而队内跑动差异是 3.9×，
落在整数上只有 {0,1,2} —— **实测取整后 11 人全是 1**，机制等于没生效。
试过「最大余数法」也救不了：那是**保总量**，不是**保分辨率**。
⇒ 分摊值**保留小数**。`Σ drain` 仍精确等于 `teamTotal`（实数运算）
⇒ 球队均值仍逐位不变，只是「队内分布」终于表达得出来。
面板/提示读到的都是 `Math.round(...)`（已核对 10+ 处消费点），显示不受影响。

### 实测验收（`scripts/fitness-distance-share-verify.mjs`，已进 `verify.mjs`）
| 判据 | 读数 |
|---|---|
| 赛前 Σ → 中场 Σ | 990 → **957.0000**（差 **33.0000**，精确守恒） |
| 面板取值种类 | **1 → 3**（旧实现恒为 1） |
| 面板显示值 | **86 ~ 89**，均值仍是 **87** ⇒ 零重标定 |
| 排序 | 跑动最少的门将体能最高、跑动最多的中场最低 |
| 概率引擎路径（无 `simEng`） | 仍等额（取值 87）、仍整数 |

### ⚠ 诚实标注：可见差异受**既有耗能量级**限制
每人每半场只扣 3 点（`perPlayer=1` × 3 次结算）⇒ 面板极差只有 **3 点（86~89）**。
机制上差异是 3.9×（门将 2.8km vs 中场 9.8km），但**绝对量**被总量口径压住了。
要更大的可见差异属于「**体能经济**」改动（调大 `perPlayer` 或延长结算间隔），
会动到换人阈值/伤病率/评分 ⇒ **需要单独一轮标定**，本次不做。
