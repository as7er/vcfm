整队摆位瞬移：根因定位与修法（2026-09-22 傍晚 · v286）
================================================================================

用户原话
--------
「开角球的时候，球员还是会瞬移到目标站位；中场暂停回归阵容站位的时候也是瞬移。」
（交接 docs/handoff-2026-09-22b.md §4 把它列为第一优先，并给出了一条**未经验证**的根因）

一句话结论
----------
交接 §4.1 的根因（「`_kickoff` 不设 `restartType` ⇒ `restartFrame` 为假 ⇒ 缓动永不武装」）
**被实测推翻**。真正的根因是：整队级重启搬运（角球/门球/开球）把 21~22 人
在**一个 0.1 s 帧内**搬走 **40~76 m**，而 `matchview.relocate()` 的缓动是
**固定 700 ms 的 ease-out cubic** ⇒ 首帧就走掉 7%、两帧 76% ⇒ 等效 **~258 m/s**。
缓动**确实在跑**（实测占 3.45% 的帧），但它在 700 ms 里摊不平 60 m。
修法：段内整队摆位改走**段首那套「硬置 + 淡场剪辑」**（本仓库对段首早已下过同一结论）。

--------------------------------------------------------------------------------
1. 交接 §4.1 为什么是错的
--------------------------------------------------------------------------------
`js/sim/engine.js:8253 _kickoff` 末尾有：
    this.deadBallUntil = this.t + 0.9;      // engine.js:8351
而 `motionContextOf`（engine.js:492-496）：
    const deadBall = !!(eng.deadBallUntil && eng.t <= eng.deadBallUntil + 1e-6);
    discontinuity: !!(deadBall || celebrating || eng.pendingPenalty)
⇒ 开球后 **0.9 秒内 `motionContext.discontinuity === true`**，
而 `matchview.js:486` 的 `restartFrame = !!(sim.ball?.restartType || sim.motionContext?.discontinuity)`
⇒ `restartFrame` **为真**，缓动**可以**武装。交接那条推断没有实测支撑。

中场那一帧的真实情况（普查探针实测，2 场样本）：
  H1 末帧 → H2 首帧：**隔 433.2 / 498.7 / 625.4 s**，最大位移 **92.4~94.4 m**，
  22 人全部 >2m，`restart=null`、`disc=true`。
⇒ 间隔远大于 `sceneCut` 的 0.55 s 阈值 ⇒ **本来就判成段首剪辑**（硬置 + 淡场）。
  它走的是「剪辑」路径，不是「缓动没武装」。
  另外 `applyHalfTimeSwap`（`js/match.js:1510`）在 `runSimPeriodRaw`（`:1518`）**之前**调用，
  所以 22 人那次硬吸附发生在**任何 H2 帧被录制之前** —— 帧流里根本不存在这一跳。

之所以「看起来像瞬移」：H1 最后一个高光窗可能停在 2267 s（38′），
H2 首帧在 2700.1 s —— 中间隔着 433 秒比赛时间与一次中场面板。
观众看到的是「H1 的运动战画面 → 淡场 → 全新的开球阵型」，
那就是剪辑。**这一条本轮没有单独的浏览器证据**（探针只采到 220 s），
留作待办（见 §6）。

2. 新增普查探针（确定性、整场、不需要浏览器）
--------------------------------------------------------------------------------
`scripts/_restart-snap-census.mjs 4`
它把整场（H1+H2）的录制帧流在 Node 里重放，回答三件浏览器探针做不到的事：
  ① 每一次「超出物理上限的位移帧对」都列出并标注语义（这是缓动能否武装的全部依据）；
  ② 区分「落在 play 段内（观众看得见）」与「落在段首剪辑上（被淡场吃掉）」；
  ③ 事件覆盖：角球/界外球/进球各多少次、多少次落进高光窗。

⚠ 第一版**不可复现**：`createWorld(userClubId, name)` 不接种子，两轮跑的是**不同的比赛**
  （`fx_7286_svl85` vs `fx_7286_r8sor`）。已修：把 `Math.random` 换成确定性 PRNG
  （`makeRng(0x5f3a71c9)`），并加**同进程双跑指纹自检**。
  按 AGENTS.md 的铁律：做任何测量实验前先证明模拟可复现；本次自检 ✅ 全绿。

判据为什么是「超物理上限」而不是固定米数：见 `_restart-placement-probe.mjs` 头部两个坑
（固定 6 m 会漏掉缓动摊开的小步；固定速度门槛会被 dt≈0.009 s 的噪声污染）。
这里用 `位移 > 10 m/s × dt`，物理上限取 `RELOCATE_PLAYER_MAX_SPEED_MPS = 10`。

读数（4 场，每场双跑指纹一致）
------------------------------
  细播占比 4.5%（只有 4.5% 的模拟时间会被播；其余是 skip）
  段内超物理位移帧对（**可见**）**28 次**，约每场 7 次
    · 全部 21~22 人「>2 m」，最大位移 **40.0 ~ 76.9 m**，dt 均为 0.10 s
    · **无标记的 0 次 / 有标记的 28 次**（`restart=goalkick` 或 `corner`，或 `disc=true`）
    · ⇒ 交接说的「缓动没武装」在这一类上不成立；缓动**武装了**，只是摊不平
  段首剪辑 53 次，位移 >2 m 的 53 次（中位 50.3 m）
  中场边界 4/4 场：隔 433~625 s、92~94 m、22 人、restart=null、disc=true

按重启类型分布：**goalkick 最多**（门球 / 出底线后），其次 corner，
  还有「进球庆祝后回中圈」那一类（restart=null + disc=true，约 41 m）。
  ⇒ 用户点名的是角球，但同类里**门球更频繁**。

3. 修法（js/matchview.js，表现层；引擎零改动）
--------------------------------------------------------------------------------
新增判定（模块级常量 + 两个纯函数）：
    const PLACEMENT_CUT_MIN_METRES = 25;    // 700 ms 摊不平的距离
    const PLACEMENT_CUT_MIN_ENTITIES = 3;   // 不是单人异常
    placementShiftOf(fromPlayers, byTarget, maxSpeedMps, dtSec) → { n, maxM }
    isWholeTeamPlacement(shift) = shift.n >= 3 && shift.maxM >= 25

判据为什么是**距离**而不是人数：一条 2 m 的摆位摊到 700 ms 只有 3.6 m/s（完全合理，
必须继续走缓动）；60 m 摊到 700 ms 是 86 m/s。25 m 取自实测分布的空档：
可见的整队搬运全在 40~76 m，而小范围摆位实测都在 3 m 以内
（`match-continuity-audit` 的 historical fixture 是 `< 3` 格 ≈ 2.5 m）。

两个调用点（判据同源，不重复实现）：
  · `applySimSnapshotLerped`：录制帧对判到整队摆位 ⇒ `t = 1`（**钉到 fb**，
    不让线性插值在一个帧跨度内扫过整个缺口）＋ 跳过 `heldIds` 按住逻辑
    ＋ 把 `placementCut: true` 透传给 `applySimSnapshot`；
  · `applySimSnapshot`：`opts.placementCut` 或（直接快照路径）用**显示坐标**现判；
    判到就调 `_playSegmentCut()` —— 与段首**同一个函数、同一套 CSS**，
    且在**硬置之前**同步触发 ⇒ 浏览器下一次绘制时淡场已在 0% 关键帧（opacity 1）。
  · `relocate()` 的武装条件加 `!placementCut`。

顺带修一处：`_playSegmentCut()` 加去抖（`_segCutAt`）。
  整队摆位是**每个渲染帧**都会判到的（一个 0.1 s 录制帧对里有约 6 个渲染帧），
  旧实现每次 remove + 强制重排 + add 会把 `@keyframes` 重置回 0%，
  「满遮 91 ms」被拖成「满遮 190 ms」—— 两倍长的黑屏。

⚠ 不改引擎。理由是 `js/matchview.js:1218-1220` 早就写过同一句话：
  「缓动本身也是错的解法 —— 45 m 位移摊到 0.7 s 等于 64 m/s 的扫掠」，
  段首一律走剪辑。此前**只有段首**这样处理：同一个角球，拿到自己的高光窗就是剪辑，
  落在扑救/射门窗内部就是 0.7 s 扫掠 —— 同一事件两种呈现，本身就是缺陷。

5. 顺带记录：三个用户提问的查证结论（交接 §5，此前一条都没查）
--------------------------------------------------------------------------------
① 点球命中率是不是按门将/主罚者能力设的？——**是**，但基线偏低。
   唯一公式：`js/sim/engine.js:7319`
     penSkill = finishing*0.38 + shooting*0.24 + decisions*0.22 + kicking*0.10 + (isCore ? 0.015 : 0)
     save     = 0.55*reflexes + 0.28*handling          （无门将时 0.2）
     pScore   = clamp(0.77 + (penSkill - 0.6)*0.34 - save*0.22, 0.55, 0.9)
     r = random()；r < pScore ⇒ 进球；否则按 (1-pScore) 再劈 70% 扑救 / 30% 打偏
   · **读门将**（reflexes 0.55 / handling 0.28）**也读主罚者**（四项加权）；
     **不读** `composure`/`penalties` —— 这两个属性在本游戏里不存在。
   · 只有**一次**均匀随机抽取；**没有**射门方向↔扑救方向配对（`saveSide` 是 outcome 之后
     抽的动画参数，不参与判定）；天气/德比/主客场/体能都不进这条式子。
   · 量级（确定性二分，与代码 pScore 逐位一致）：门将 1→20 ⇒ 72.1% → 61.0%（−11.1pp）；
     主罚者 1→20 ⇒ 55.0% → 73.9%（+18.9pp）；上夹 0.9 是**死代码**，下夹 0.55 会真咬住。
   · **真实俱乐部 400 组实测：平均 67.09%**（P10 63.5% / P90 70.9%），
     而现实基准约 75~80%，且本仓库自己的点球 xG 硬编码就是 **0.76**
     （`js/match.js:1200`、`js/match-analysis.js:40`）—— **引擎实际转化率与它自己声明的 xG 不一致**。
     ⇒ 用户「命中率偏低」的感觉**成立**。
   · 最小改动（**需拍板，本轮未改**）：把 0.77 → **约 0.85** ⇒ 平均 67.1% → ≈75.3%，
     斜率不变（能力区分度一点不减），点球**频次**不动（判罚侧完全没碰）。
     ⛔ 不要动 `norm()`（牵动整套标定）；⛔ 不要动判罚侧（`match-realism-audit` 的
     0.1~0.5/场信封是钉住的）。
   · 另有一条：v1 概率引擎的 `penaltyConversionChance`（`js/match.js:1119-1128`）算出来 73.86%，
     **与 v2 差 6.8 pp**；淘汰赛「点球大战」是纯抛硬币（`js/match.js:3436`），不读能力。

② 为什么没见过边线球？——**引擎整场没有产生过界外球**，不是「被平淡过渡掉了」。
   · 引擎代码存在：`js/sim/engine.js:7621-7626`（`_resolveBounds` 里 `b.x <= 0 || b.x >= 100`
     ⇒ `_restart("throwin", …)`），摆位/事件/越位豁免全都写了。
   · 但实测 **17 场 × 90 分钟 = 0 次**。原因：球 90% 时间黏在球员脚下，
     球员坐标夹在 `[1,99]`（目标位更紧），**全引擎没有任何一处把球瞄向边线**；
     实测整场 `|x-50|` 最大值只有 **45.8 / 50** ⇒ 判据**不可达**。
     把步长放粗到 0.3/0.5 s（数值余量变化）界外球就出现了 ⇒ 这是**数值边距**，
     不是「设计如此」，属**静默失效**。对照：进球线分支命中 282 次。
   · 同时 **UI 侧零消费者**（全仓 grep：`buildHighlightWindows` 不加窗、
     `pickFlavorEvents` 的 `caps` 白名单丢弃、`defaultFlavorText` **没有 `case "throwin"`**
     —— 缺这一条将来接线会直接显示「45' 球队名」这种垃圾文案）。
   · ⇒ 两个独立缺口：ⓐ 让球真能出边线（谁踢、往哪踢）；ⓑ 三处消费者同时补。
   · 本仓库已有一条同类先例：`js/sim/adapt.js:501` 的注释写着
     「角球：半场最多 3 次（**用户反馈「从没见过角球画面」**——旧版高光窗根本不含角球）」。

③ 赛前没有首发预览？——**确实没有**，但数据在那一刻全部可得。
   · 现在赛前只有：计分条（PRE）、`#match-pre-brief` 简报（唯一提到「首发」的地方是
     一行「首发体能均 X% · 阵型 Y」，**没有一个人名**）、队内讲话卡、
     一块**只画号码不画姓名**的球场（`.mp-name` 在赛前被 CSS 强制隐藏）、评论流简报行。
   · 仓库里**没有**可复用的「11 人首发列表」函数。最接近的是战术页 `#pitch` 的
     `.tac-slot` 块，但绑死在拖拽/角色交互上；第二接近的是 `renderHtSubSelects`
     的一行文案格式。
   · 数据全部可得：`club.tactics.lineup` + `getLineupPlayers` +
     `assignPlayersToFormationSlots`（与引擎/球场同一套）。
   · **重要旁证**：`matchview.mount()`（`js/matchview.js:1689-1690`）**无条件**
     `autoLineup(home); autoLineup(away);`，而它在 `openMatch` 里被调用 ⇒
     **进比赛界面会覆盖用户在战术页手工排的首发**。这与 `createMatchSession` 的
     `forceAuto: club.id !== userClubId`（尊重用户首发）**互相矛盾**。
     ⟶ 这是**另一个待处理的缺陷线索**（未改，见 §6）。
   · 最小改动路径（**需拍板，本轮未改**）：在 `openMatch()` 的
     `await ensureMatchPitch(true)`（`main.js:10324`）之后、`showScreen("match")`（`:10335`）
     之前，往**已存在的** `#match-pre-brief` 面板追加一段纯字符串的双方首发块
     （复用 `.tac-bench-chip` 视觉 + `renderHtSubSelects` 的文案格式）。
     开赛时 `hidePrematchBriefPanel()` 会连它一起收起，不必另写生命周期。
     ⚠ 主要风险：手机横屏 `#match-pre-brief` 是 `max-height: min(36vh, 300px)` 且内滚，
     再加 22 行会把**赛前讲话（必填交互）推到需要滚动的位置** —— 滚不到就是功能挡路。
     建议两列或 `<details>` 默认折叠。
     ⚠ AI 队只是「预计首发」：`createMatchSession` 会先 `aiTuneTactics`（可能改阵型）
     再强制重排；用户队基本等于最终 11 人。
