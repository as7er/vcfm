终场体能改为按跑动距离分摊（2026-09-21，v278，方案 E）
======================================================

## 这份文档回答什么

用户 2026-09-19 报的「各队员体能显示不对」有两半。**中场那一半**已由方案 D
（`settleFitnessDrain`）按跑动距离分摊修掉，见
`docs/measurements/halftime-fitness-per-player-2026-09-21.txt`。

**本文是另一半**：终场那一笔扣减（`finalizeMatch` → `drainFitness`）**从没被改过**，
一直是逐人掷骰子。

上一份交接（`docs/handoff-2026-09-21b.md` §5 B）把「体能经济量级」列为待用户拍板的两条路
（① 调大 `perPlayer` ② 延长结算间隔）。**本轮实测证明这两条都不是问题的所在** ——
量级已经是对的，坏的是**分配方式**。见 §5 的对比表。


## 1. 事实：终场那一笔是掷骰子

`js/match.js`（修前）：

```js
function drainFitness(club, isHome, state) {
  ...
  for (const p of getLineupPlayers(club)) {
    if (sent.has(p.id)) continue;
    const drain = 4 + Math.floor(rng() * 6) + Math.round((fitW - 1) * 4);
    p.fitness = Math.round(Math.max(35, p.fitness - drain));
  }
  ...
}
```

`4 + Math.floor(rng() * 6)` ⇒ **逐人独立掷骰，4~9 点，均值 6.5**，
与 `runMetres`（引擎每帧累加的真实跑动距离）**完全无关**。

量级对比（一整个 90 分钟）：

| 来源 | 均值 | 分配方式 |
|---|---:|---|
| `settleFitnessDrain`（`minute % 15 === 0` → 15/30/45/60/75/90，共 6 次） | **6.0 点** | 方案 D：按跑动距离（已修） |
| `drainFitness`（终场一次） | **6.5 点** | **掷骰子（本次修）** |
| 合计 | ≈ 12.5 点 | 赛前 90 → 赛后 ~77.5 |

⇒ 终场这一笔**比中场那 6 点还大**，而且它是**唯一**还带噪声的那一半。

## 3. 修法（`js/match.js` 的 `drainFitness`）

只改**分配方式**，不改总量口径：

```js
const xi = getLineupPlayers(club).filter((p) => p && !sent.has(p.id));
const runById = new Map();
for (const a of state.simEng?.agents || []) {
  if (a?.id != null) runById.set(a.id, Number(a.runMetres) || 0);
}
const work = xi.map((p) => runById.get(p.id) ?? 0);
const sumWork = work.reduce((s, v) => s + v, 0);

if (xi.length && sumWork > 0) {
  // 球队总量：与旧实现同分布（每人一次骰子，再求和），只改分配方式
  let teamTotal = 0;
  for (let i = 0; i < xi.length; i += 1) {
    teamTotal += 4 + Math.floor(rng() * 6) + Math.round((fitW - 1) * 4);
  }
  for (let i = 0; i < xi.length; i += 1) {
    p.fitness = Math.max(35, (Number(p.fitness) || 100) - (work[i] / sumWork) * teamTotal);
  }
} else {
  // 回退：与旧实现逐字相同（含 rng 调用顺序）
  ...
}
```

### ⚠ 三条不变量（都不是「看起来对」，是设计约束）

1. **球队总量与旧实现同分布**：仍是「每人一次骰子、再求和」⇒ 场均扣减、
   赛季体能经济、换人阈值（`<62` / `<65`）、伤病率（`<55`）、评分（`1 + fitness*0.005`）
   的标定**都不需要动**。这是它比「调大 `perPlayer`」便宜一个量级的根本原因。
2. **rng 消耗次数与旧实现相同**（两支路都是「非罚下球员各一次」）⇒ **不平移后续的
   全局随机流**。回退分支更是与旧实现**逐字相同**。
3. **拿不到引擎数据就退回旧行为**：概率引擎路径本来没有 `simEng`；读档续赛时
   `ensureSimEngine` 重建的引擎 `runMetres` 全 0。（与方案 D 同一套回退约定。）

⚠ 分摊值**保留小数**、不再 `Math.round` —— 与方案 D 同一理由：量级只有个位数，
整数分辨率装不下队内 3.9× 的跑动差异。面板/提示读到的都是 `Math.round(...)`，
且 `main.js:5244` 本来就会归一化非整数体能。
⚠ 触到 35 下限的球员会少扣 ⇒ 此时球队总量不再精确守恒（与方案 D 的 30 下限同理）。


## 4. 修后复测

### 4.1 受控证据：**同一轮内**的「实际 vs 按跑动反事实」配对

⚠ 先说清楚方法论：**探针当前不可逐位复现**（见 §9），所以「修前跑一轮、修后跑一轮」
得到的是**两轮独立采样**，不是受控 A/B —— 判据就是那个**本该逐位不变的对照组**
（中场结算）在两轮里给出了 0.890 与 0.941。**不要把它当成同场比赛的前后对照。**

真正受控的比较在**每一轮内部**：同一场比赛、同一批骰子总量、同一个跑动向量，
只有「怎么分配」不同。探针两侧同时给出这两个数：

| 口径 | 修前那一轮的实测 | 修前那一轮的按跑动 | **修后那一轮的实测** | 修后那一轮的按跑动 |
|---|---:|---:|---:|---:|
| 与跑动的 Spearman | -0.007 | 1.000 | **1.000** | 1.000 |
| 队内 SD | 1.53 点 | 1.89 点 | **1.82 点** | 1.82 点 |
| 队内极差 | 4.83 点 | 7.34 点 | **7.06 点** | 7.06 点 |
| 总量守恒偏差 | 1.42e-14 | — | 1.42e-14 | — |

**这张表怎么读：**

- 修前那一轮里，实测（掷骰）与反事实（按跑动）**差距巨大**（-0.007 vs 1.000；
  极差 4.83 vs 7.34）⇒ 分配方式确实在起作用，这是**同一场比赛**的配对，不受复现性影响。
- 修后那一轮里，实测**已经等于**反事实（1.000、7.06 vs 7.06）
  ⇒ 实现做的正好是反事实所描述的事。
- 跨轮的总量（8 场场均）与守恒偏差两轮都在同一量级（1.42e-14 / 2.84e-14），
  且回归检查（§4.2）在**定死种子**下断言了严格比例分摊 ⇒ 结论不依赖跨轮可比性。

⇒ 「累」与「跑得多」从**掷骰子**变成**因果**；均值不变（零重标定），**极差不缩反增**。

|---|---:|---:|
| 终场那一笔 vs 跑动 | -0.007 | 1.000 |
| 整场总扣减 vs 跑动 | 0.481 | 0.980 |

### 4.2 回归检查：`scripts/fitness-finalize-drain-verify.mjs`（新增，已挂 `verify.mjs`，约 30 秒）

**19/19 通过**（本次运行读数；判据都是结构性的，不依赖具体种子）：

- **静态 8 项**：`drainFitness` 真的读 `state.simEng` / `runMetres`；比例分摊行**未**套
  `Math.round`；回退分支逐字保留；`rng()` 恰好 2 次（两支路各一）；
  **球队总量是逐人累加 `xi.length` 次**（这条是补的 —— 见下方「已修的假通过缝隙」）。
- **空间路径 7 项**：逐人「扣减 / 跑动」比值**恒定**（实测同一场内 min == max，
  差 < 1e-9 ⇒ 严格比例分摊）；球队总量仍落在旧骰子区间 `[44, 99]`（实测 79.000 / 77.000）；
  逐人均值 7.09（判据 `|mean − 6.5| < 1.5`）。
- **回退路径 4 项**（把全体 `runMetres` 清零，比删 `simEng` 更贴近生产）：
  体能仍是**整数**（实测取值 73~84 ⇒ 确实走了旧分支）；
  扣减呈掷骰散布（**≥3 个不同取值**，实测 11 个互不相同）；
  这条是补的 —— 原先只断言「不是同一个值」，区分不了「旧实现逐人掷骰」与
  「等额分摊 + `Math.round`」（后者 11 人**完全相同**）。

### 已修的假通过缝隙（code-reviewer 2026-09-21 指出）

原版只把「零重标定」钉成**区间** `[4n, 9n]` + **`rng()` 出现次数 2** + 均值，
于是「**只抽一颗骰子再乘人数**」这种退化解会**全绿通过**（它恰好 2 处 `rng()`、
也落在 `[4n, 9n]`、也是 6.5），但每个球员扣减完全相同 —— 正是本次要修的缺陷。
已补一条形状断言钉住「累计是在 `xi.length` 次循环里做的」。
（`rng()` 计数是**文本**代理，不是行为断言；这条局限已写进检查脚本的注释。）


## 5. 为什么不是交接里列的那两条路

| | 改什么 | 球队总量 | 要重标定？ | 对「相关性」 | 对现实性 |
|---|---|---|---|---|---|
| ① 调大 `perPlayer` | 均值 87 → 84 或更低 | **变** | 换人/伤病/评分 + 赛季恢复 | 改善 | **变差**（压到 70 以下） |
| ② 延长结算间隔 | 6 次并成 3 次 | **变小**（`round(1)` 次数少了） | 否 | 不变 | 不变 |
| **③ 改 `drainFitness` 分配（本次）** | 分配方式 | **不变** | **否** | 0.481 → **0.980** | **变好** |

- **①**：per-match 面板扣减 ≈ 12.5 点、90 → ~77.5，**现实足球一场下来主力正是 75~80**
  ⇒ 量级已经对了，抬上去反而会撞 `<65` / `<62` / `<55` 三处既有阈值。真要做也要另起一轮标定。
- **②**：在总量守恒的写法下**既不改均值也不改极差**（分摊是按比例，线性）。
  它真正的价值是**提高 `round()` 的分辨率** —— 把间隔按分钟数折进 `perPlayer` 后，
  `fitW + extra` = 1.45 vs 1.52 会变成 2.9 vs 3.04，这才让 **C 线的 `weather.pace` extra
  终于跨得过取整边界**。⇒ 它该归到 C 线，不是 B 线的选项。

## 9. 🔴 已知局限：探针当前**不可逐位复现**（未定位）

`AGENTS.md` ④ 的铁律是「做任何测量实验前，先证明模拟可复现（同输入跑两次对比 md5）」。
**本轮的探针没有满足它**，这是 code-reviewer 2026-09-21 抓到的，如实记在这里。

### 现象

同一份代码、同一份输入连跑两次，**整场就不是同一场比赛**：

| 观察 | 第 1 次 | 第 2 次 |
|---|---:|---:|
| 首场 DEF `h_d3` 跑动 | 13.58 km | 13.08 km |
| 首场 ATT `h_a2` 跑动 | 14.47 km | 13.24 km |
| 全场换人事件数 | 7 | 8 |

⇒ 由此得出的判据：那个**本该逐位不变的对照组**（中场结算 vs 跑动的相关性）
在修前/修后两轮给出 **0.890 / 0.941**。它一旦漂移，就说明两轮不是同场比赛。

### 已经排除的

1. **`Math.random`** —— 探针现在进程内换掉了它（`Math.random = mulberry32(20260921)`），
   **仍然不一致**。
2. **`fixture.matchSeed`** —— 探针现在显式给了，**仍然不一致**。
   （`random.js:30` 的 `ensureMatchSeed` 本来就是由 `(season, day, id, home, away, competition)`
   哈希而来，不用 `Math.random`；给 `matchSeed` 只是把这条链钉死。）
3. **球员属性生成** —— `generatePlayerAttributes` 全文没有随机调用；探针的球员 id 也是写死的。
4. **时钟** —— `js/match.js` 全文没有 `performance.now` / `Date.now`；
   引擎的随机是播种的（`engine.js:530` 用 `opts.random`，`ensureSimEngine` 传 `state.random`）。

### 还没排除的（下一步）

- `aiTuneTactics`（AI 球队改战术）与 `ensureMatchLineup(forceAuto: true)` 那条链上
  有没有别的环境依赖源。
- 引擎/适配层里是否有**对象枚举顺序**或**浮点累加顺序**上的非确定性。
- 最小复现：在**一个进程内**从同一 `makeWorld()` 建两个 session，比对 `runMetres`
  与 `state.random()` 的前几个值 —— 能在一次运行里定位到底哪一层开始分叉。

### 为什么结论仍然站得住

受控比较**不依赖**跨进程复现性：

- 探针在**同一轮内**同时输出「实际」与「按跑动反事实」，两者共用同一场比赛、
  同一批骰子总量、同一个跑动向量（§4.1）；
- `scripts/fitness-finalize-drain-verify.mjs` 用**写死的 `fixture.matchSeed`** 断言
  「扣减 / 跑动 比值恒定到 1e-9」与「总量守恒」—— 这是实现级断言，不受整场复现性影响。

⚠ **但跨轮的那些数字（0.890 → 0.941、8.00 → 13.47）都只能当量级参考，
不能当受控前后对照。** 引用时请连这句话一起引。
