「门将槽站的是后卫」排查（2026-09-22）
=======================================

来源
----
交接 `docs/handoff-2026-09-22.md` **第五优先**：
> **`createMatchSession` 可能覆盖显式首发**：v278 的探针显示**建会话之后门将槽
> 站的是一名后卫**（`h_d0(DEF)`），而队里有 2 名真门将且已显式排进首发。
> ……**另行排查，不要并进体能那条线。**


一、现象**已复现**
------------------
用 `_fitness-finalize-drain-probe.mjs` 同款建队（每队 2 名真门将）直接调
`createMatchSession`：

| 前置 | GK 槽 | 判定 |
|---|---|---|
| ① 不指定首发 | `h_d0(DEF)` | ❌ |
| ② **显式指定首发** | `h_d0(DEF)` | ❌ |

⇒ 与交接描述一致，且**显式指定首发也拦不住**。


二、根因**不是**首发逻辑，是**报名名单**
------------------------------------------
链路（三层，每层单看都是对的）：

1. `createMatchSession` 把 `eligiblePlayerIds(world, club, fixture)` 作为
   `eligibleIds` 传给 `ensureMatchLineup`。
2. `eligiblePlayerIds` 只收 `playerCompetitionEligibility(...).eligible` 为真的球员。
3. 本脚本实测：**两名门将都 `eligible = false`，原因「未进入本赛事报名名单」**。

于是 `ensureMatchLineup` 走它的既有语义 ——
**「首发里某个位置的人不可用 ⇒ 换一个可用的人」**（这正是它该做的），
门将槽没有可用的门将，就落到兜底分支，取能力最高的未用球员 ⇒ 一名后卫。

### 再上一层：报名名单为什么会没有门将

`automaticPlayerIds`（`js/squad-registration.js:184`）按
`registrationScore` 从高到低填名额，**基本不看位置**：

```js
function registrationScore(player) {
  const positionFloor = player.pos === "GK" ? 0.3 : player.pos === "DEF" ? 0.2 : 0;
  return (Number(player.ovr) || 0) * 100 + (Number(player.potential) || 0) + positionFloor;
}
```

`ovr × 100` 的量级是 1300~1700，而门将那 **+0.3** 只在**完全同分**时才起作用
—— 对 0.1 点 ovr 的差距（=10 分）毫无保护。

非本土培养名额上限 17。**若某队非本土球员 > 17，排在最弱那批的就会被切掉**，
而门将一旦恰好在最弱那批，就会**整队一个门将都不剩**。


三、可达性：**真实世界里 0 / 2160，签人也签不出来**
----------------------------------------------------
普查脚本（含**正对照**）：

| 场景 | 结果 |
|---|---|
| **正对照**：合成阵容（23 人全非本土培养，门将 ovr 14/13 = 全队最弱） | 2 门将 / **0 合格** / 报名 17 人 ⇒ **检查抓得到** ✅ |
| **真实生成世界** 8 个种子 × 270 队 = **2160 队** | 报名排除全部门将的：**0** |
| **可达性**：真实球队连续签入非本土外场球员 3/6/9/12/15 人（squad 19→34） | 门将**始终合格**（`eligibleGks` 一直 = 2） |

⇒ **真实世界与「签人」路径都到不了这个状态。** 唯一触发过的场景是
**探针自己造的合成阵容**（它把两名门将的 ovr 设成全队最低）。

**所以：这不是当前的生产缺陷，而是探针构造的产物。**
交接里那句「而队里有 2 名真门将」是对的，但没说**那两名门将在该阵容里是最弱的** ——
这正是触发条件。


四、那「门将槽站后卫」到底算不算缺陷？——**不算**
--------------------------------------------------
逐层看，每一层都是**正确**的：

| 层 | 行为 | 判定 |
|---|---|---|
| `automaticPlayerIds` | 按能力分填名额、位置基本不参与 | 规则如此（`positionFloor` 0.3 是象征性的），**且真实世界不产出无门将名单** |
| `eligiblePlayerIds` | 只放行报名名单内的人 | ✅ 正确 |
| `ensureMatchLineup` | 首发里某位置的人不可用 ⇒ 换一个可用的 | ✅ 正确 |

而「全队门将都不可用时，由外场球员客串门将」**恰恰是现实足球会发生的事**
（门将伤停/停赛且没有替补）。⇒ **这是正确的降级行为，不是缺陷。**

⚠ 另：现实足球规则**并不要求**报名名单里必须有门将（只要求满足 25 人 / 17 名
非本土培养等名额限制）。所以「给 `automaticPlayerIds` 加一条『必须留门将』约束」
是在发明一条真实规则里没有的约束 —— **不做**。


五、结论与建议
--------------
1. **交接第五优先的措辞要修正**：不是「`createMatchSession` 覆盖显式首发」，
   而是「**该阵容里两名门将都没进报名名单** ⇒ 首发逻辑按规则把他换掉」。
   触发条件是**门将能力在该阵容里垫底**，而不是「建会话覆盖了首发」。
2. **不改任何代码**：三层行为都正确；真实世界不可达（0/2160），
   签人路径也不可达（squad 19→34 实测）。
3. **但加一条护栏**：`squad-registration-audit.mjs` 增加普查断言 ——
   在真实生成的世界里，**每支球队都至少要有 1 名门将进了报名名单**。
   它不改行为，只在「将来某次改动让报名逻辑开始丢门将」时报警。
   （这正是本轮该做而没做的那件事：**把一个「现在恰好成立」的性质钉住**。）

### 护栏本身的验证

| 项 | 结果 |
|---|---|
| 正常跑 | 1080 支球队，排除全部门将的 **0** 支，`exit 0` |
| **正对照**：临时把门将排除出 `automaticPlayerIds` 的候选 | **590 / 1080 支**被抓到，`exit 1` |
| 样本量断言 | `clubs > 500` —— 没有它，「0 例」可能只是没量到 |
| 还原 | `git diff js/squad-registration.js` **为空**，护栏恢复 `exit 0` |

**正对照是本护栏可信的前提**：没有它，「0 / 1080」既可能是「真的没有」，
也可能是「探针根本量不到」。


六、⚠ 本轮第二次「探针构造产物被写成产品缺陷」
-----------------------------------------------
上一次是移动端的**探针取点**（元素「存在」≠「点得到」）；
这一次是**合成阵容**（把两名门将设成全队最弱）造出了一个真实数据里到不了的状态。

**通则：报告一个缺陷前，先问「这个状态在真实数据里可达吗」，并用
「普查 + 正对照」回答。** 正对照（合成案例必须被抓到）是这张表可信的前提 ——
没有它，「0 / 2160」既可能是「真的没有」，也可能是「探针根本量不到」。
