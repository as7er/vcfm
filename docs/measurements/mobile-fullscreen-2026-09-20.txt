手机全屏观赛 + 「外壳比视口多 11px」口径修复（2026-09-20，v275）
============================================================

用户提议（原文）
----------------
「其实我在想，手机端横屏的时候，是不是可以引入比赛画面全屏的功能？」
「手机端就算 Safari 不支持，Chrome 支持也可以啊」


[0] 结论（一句话）
------------------
手机横屏「球场还是太小」的**根因不是 CSS 没调好，而是浏览器工具栏吃掉了 ~95px 高度**
（844×390 的手机横持后 `dvh` 只剩 ~295）。全屏是唯一能把那 95px 要回来的手段，
所以它不是一个「锦上添花的功能」，而是这个问题的**正解**。
实测收益（同一台等效 800×295 的真机口径）：球场 **206 → 301px（+46% 高度，面积 ×2.1）**。


[1] 为什么 95px 这么致命
------------------------
· 手机横持视口高 ~390px，浏览器地址栏 + 系统栏吃掉 ~95px ⇒ `100dvh ≈ 295px`。
· 球场盒比 93.45/68 ≈ 1.374（横长），按 contain 放进「可用高 − 控制条 58px」：
  `295 − 58 − 22(dock) ≈ 215` ⇒ 球场高只有 **~206px**。
· 进全屏后工具栏消失，`dvh` 直接等于屏幕高 390 ⇒ 同一公式给出 **~301px**。
· ⚠ 关键是：**横屏档的高度公式一个字都不用改**（`calc(100dvh - 58px - 2*pad)`），
  `dvh` 自己就变大了。


[2] 支持面（2026-09 查证，决定方案形态）
----------------------------------------
| 环境 | `Element.requestFullscreen` |
|---|---|
| Android Chrome / Edge | ✅ |
| 桌面 Chrome / Edge / Firefox | ✅ |
| iPadOS Safari | ✅ |
| **iPhone Safari** | ❌ **不支持任意元素全屏**（只有 `<video>` 能全屏） |

⇒ 用户明确表态「Safari 不支持没关系，Chrome 支持也可以」。
⇒ 方案按**能力检测**（`document.fullscreenEnabled`）而不是按平台判断：
  不支持时按钮**默认 `hidden`，永远不摘掉** —— 宁可没有入口，
  也不要给一个「点了没反应」的按钮。
⇒ ⚠ **不做** `screen.orientation.lock("landscape")`：那会强行把竖持的手机转过去，
  属于「用户没要求的动作」，且锁方向在部分系统上会失败。
  竖持进全屏时页面本来就会显示「请横持手机」提示，用户自己转过去即可。


[3] 实现（4 个文件）
--------------------

### `index.html`
`.match-playback-bar` 里加 `#btn-match-fullscreen`，**带 `hidden`**。

### `js/main.js`
· `fullscreenSupported()` —— 读 `document.fullscreenEnabled` + `webkitRequestFullscreen` 回退。
  **不用 UA 字符串猜**。
· `currentFullscreenElement()` / `syncFullscreenUI()` —— 按钮显隐/文案/`aria-pressed`
  **全部由真实全屏状态推导**，不维护本地布尔标志位（用户按 Esc、系统返回手势都会退出）。
· `toggleMatchFullscreen()` —— 全屏宿主是 **`.match-layout.fmm-match`（整块比赛界面）**，
  **不是单块球场**：只全屏球场的话，进了全屏就点不到暂停/退出，用户被困住。
  切换后 `matchView.refreshLayout()` 重测画布。
· `bindMainOnce()` 里绑 click + `fullscreenchange` + `webkitfullscreenchange`
  （**挂在 `document` 上**，不是按钮上）。
· `showScreen()` —— **离开比赛界面时退出全屏**（同上：否则满屏上没有任何返回入口）。

### `css/style.css`
```css
.match-layout.fm-match.fmm-match:fullscreen,
.match-layout.fm-match.fmm-match:-webkit-full-screen {
  position: fixed !important; inset: 0 !important;
  width: 100% !important; height: 100% !important;
  max-height: none; overflow: hidden; margin: 0; border-radius: 0;
  padding-left: env(safe-area-inset-left, 0px);   /* 横屏刘海在左右 */
  padding-right: env(safe-area-inset-right, 0px);
  background: var(--bg, #0d131c);
}
.fmm-match-bar .btn[hidden] { display: none !important; }
```

### `js/i18n.js`
`match.fullscreen` / `match.fullscreenHint` / `match.fullscreenExit` /
`match.fullscreenExitHint`，**中英各一份**。


[4] 三个坑（都是「看起来像没生效」的那种）
------------------------------------------

### 坑 1：`[hidden]` 被任何 `display` 声明压掉 ⇒ 隐藏的按钮照样显示
UA 样式表 `[hidden] { display: none }` 特异性 **(0,1,0)**；
`.fmm-match-bar .btn.icon-btn { display: inline-grid }` 是 **(0,3,0)**。
⇒ `hidden` 为真，按钮**照样显示**。
**伪装**：`hidden` 明明写在标签上，静态读代码完全看不出来。
**修法**：显式 `.fmm-match-bar .btn[hidden] { display: none !important; }`。
**验证**：断言必须**同时**测 `hidden === true` **且** `getComputedStyle().display === "none"`
—— 只测前者等于没测。

### 坑 2：`:fullscreen` 的 `position: fixed` 会被自己的 `position: relative` 顶掉
横屏档给 `.match-layout.….live-kick` 写了 `position: relative`（特异性 0,4,0）。
**author 样式优先于 UA 样式** ⇒ UA 的 `:fullscreen { position: fixed; inset: 0 }` 被顶掉；
而 `position: relative` 下 `width/height: 100%` 的百分比基准不再是视口
⇒ 全屏元素可能只有内容那么高。
**修法**：`:fullscreen` 块里用 `position: fixed !important; inset: 0 !important` 钉死。

### 坑 3：Playwright 里能自动验证吗？—— 能，但量不出「收益」
先写了个 20 行的能力探针（`scripts/_tmp-fullscreen-support-probe.mjs`），结论：
`chromium` 与 `msedge` 两个通道**都完整支持** —— `fullscreenEnabled: true`、
`requestFullscreen` 成功、`document.fullscreenElement` 正确、元素铺满视口、`exitFullscreen` 正常。
⇒ 机制（进/出、状态同步、按钮显隐、不溢出）**可以**自动验证。
⚠ 但 **`dvh` 的收益量不出来**：Playwright 的 `viewport` 是固定的，
进全屏前后 `innerHeight` 都是 390（= 已经是「全屏口径」）。
所以探针里 `②`（844×390）≈ **真机全屏**口径，`②b`（800×295）≈ **真机非全屏**口径，
两者的差才是全屏的真实收益。


[5] 附带修掉的：外壳比视口多 11px（`--fmm-shell-pad`）
-------------------------------------------------------

### 症状
横屏手机与桌面**都**稳定多出 11px 可滚动量（`scrollY = 11`）。
这在触摸端很显眼：整块比赛界面能被上下拖动 11px。

### 根因（一行）
`#screen-match.active { padding: 0.65rem }` —— **上下各占一次**（2 × 10.4 = 20.8px），
而 `.match-layout` 的高度公式写的是 `calc(100dvh - 0.6rem)` —— **只减了一次**。
⇒ 外壳总高 = 10.4 + 285.4 + 10.4 ≈ **306**，视口只有 **295**。
桌面同源：`#screen-match` 高 **1011** vs 视口 **1000**。

### 修法（不是把 0.6rem 改成 1.2rem）
抽变量让两边**同源**，以后动 padding 公式自动跟着变：
```css
:root { --fmm-shell-pad: 0.65rem; }
#screen-match.active { padding: var(--fmm-shell-pad); }
/* 所有高度公式 */
max-height: calc(100dvh - 2 * var(--fmm-shell-pad));
/* 横屏档只改这一个值：把 20.8px 还给球场 */
@media (pointer: coarse) and (orientation: landscape) { #screen-match.active { --fmm-shell-pad: 0.15rem; } }
```
⚠ 改完必须**连带**改 body 的高度公式（body 在外壳内容盒里）：
`height: calc(100dvh - 58px - 2 * var(--fmm-shell-pad))`。

### ⚠⚠ 量这个溢出时踩的坑（值得单独记住）
我写了两版「扫全文档元素 `getBoundingClientRect()`」的诊断，`overflowingCount` **都是 0**
—— 看起来「什么都没超界」。真相：**页面此时已经滚到底**（`window.scrollY = 11`），
所有 `rect.y` 被**整体上移** 11px ⇒ 每个元素的底边都恰好落在视口内。
第二版还自作聪明加了 `r.top + scrollH` —— 那是**把视口坐标与文档尺寸相加**，不是任何东西的底边。
**最后是 `section#screen-match` 自己的 rect（`y=-11 h=306`）一眼定案。**
⇒ 通则：量「谁溢出了」必须把**滚动容器自身的 rect** 也打出来，
并且列「**最接近底边的 15 个元素**」而不是只列「已越界的」——
门槛设成「必须越界」时，会被坐标系假象**整批滤掉**。
⇒ **「没找到」不等于「不存在」，先怀疑判据。**


[6] 实测数据（`scripts/mobile-pitch-adaptation-verify.mjs`，修复后全跑）
------------------------------------------------------------------------
| 用例 | 视口 | 球场 | 占视口高 | `scrollY` | 备注 |
|---|---|---|---|---|---|
| ① 竖持 | 390×844 | 0×0（已藏） | — | 0 | 提示 367×282 可见 |
| ② 横持 | 844×390 | **414×301** | 77% | **0** | ≈ 真机**全屏**口径 |
| ②b 横持矮屏 | 800×295 | **283×206** | 69.8% | **0** | ≈ 真机**非全屏**口径 |
| ③ 桌面 | 1440×1000 | 1042×758 | 76% | **0** | 规则未误伤桌面 |

**全屏的真实收益**（② − ②b，同一台手机）：
球场高 **206 → 301px（+46%）**，面积 **×2.1**。

②c 全屏用例断言（全部通过）：
· 按钮 `hidden=false` 且 `display=grid`（支持全屏时必须真的可见）
· 点击后 `document.fullscreenElement` 是 `.match-layout`（整块比赛界面）
· `aria-pressed` 同步为 `true`；全屏下球场 414×301、比例 1.374、`scrollY=0`
· **控制条仍在视口内**（`bar.y+h = 385 ≤ 390`）且不压球场 —— 它是唯一退出入口
· 再点一次退出，`aria-pressed` 回 `false`
· 模拟 `fullscreenEnabled=false`（iPhone Safari 的真实情形）⇒ `hidden=true` **且** `display=none`

### 修复前后的代价对比（诚实标注）
| | 修前（N=58，外壳 padding 未计入） | 修后 |
|---|---|---|
| ② 球场 | 421×306 | **414×301** |
| ② `scrollY` | **11（可拖）** | **0** |

即：**用球场 −5px 换掉「整页可拖 11px」**。全屏则把这 5px 连本带利要回来（+95px）。

[8] v276 全屏入口可发现性（2026-09-21）
--------------------------------------
功能在 v275 已经能用，但控制条里 6 个图标键同色同尺寸（⏸ ⏭ ≡ 🔊 ↓ ⛶），
用户找不到全屏入口。修法：

· CSS：`#btn-match-fullscreen:not([hidden])` 用主题色（`--primary` + `--tab-active-*`）
  从灰键里拎出来。iPhone Safari 不支持时按钮仍 `hidden`，本规则因 `:not([hidden])`
  不会命中。
· JS：开赛后 toast 一次「点控制条右侧蓝色全屏键」
  （`vcfm-fullscreen-hint-seen`，点过全屏键或弹过一次后不再弹）。
  ⚠ 不能在进比赛界面时立刻弹：`toast()` 只有一条，开踢时的「赛前讲话」会盖掉它，
    且若先写 localStorage 再弹，被盖掉后也再不会弹。所以开赛后再弹、先弹再记；
    刚弹过队内讲话就延后 2600ms（toast 自己 2200ms）。
  赛后战报把控制条藏了 ⇒ 不弹；能力检测为假 ⇒ 不弹。
· 静态检查已加「独立高亮 / 首次提示 / i18n 新键」；浏览器探针 ②c 加了
  「必须在视口内」+「不得与暂停键同色」。

浏览器 ②c（2026-09-21，`VCFM_MOBILE_CASES=2`）已过：
全屏键 `color=rgb(37, 99, 235)` / `background=rgba(37, 99, 235, 0.12)`，
暂停键 `color=rgb(26, 36, 56)`；进入/退出全屏、控制条留在视口、
模拟 `fullscreenEnabled=false` 时按钮 `hidden` 且 `display:none`。


[9] 一句话总结
--------------
**「手机横屏球场太小」是浏览器 chrome 吃掉了 95px，不是 CSS 没调好；全屏是唯一解。
但不支持全屏的环境（iPhone Safari）宁可没有入口，也不要给一个点了没反应的按钮。
入口必须能被看见：同色同尺寸的图标键等于没有入口。**
